# 검증 깊이와 실행 집합

이 문서는 [wf-implement 검증](../SKILL.md#34-검증)이 소유하는 규칙의 표 부분이다. 검증 단계의 의미, 결과 판정, 실패 분류, 3튜플 귀속(테스트 집합·커밋 SHA·실행 명령)은 본문 §3.4가 정의하고, 이 문서는 **어느 시점에 어느 집합을 얼마나 깊이 실행하는지**를 정한다. 본문과 이 문서가 다르면 본문의 의미 규칙을 우선하고 이 문서를 고친다.

원칙은 하나다. **같은 테스트 묶음을 통과 후에 다시 실행하는 것은 그 사이에 코드가 바뀐 경우에만 한다.** 코드가 바뀌지 않았으면 기록을 인용한다.

## 1. 시점별 실행 집합

| 시점 | 실행 집합 | 조건 |
|---|---|---|
| TDD Red | 새 테스트 1개 | 항상 |
| TDD Green | 새 테스트 + [테스트 맵](../../wf-doc/references/templates.md#테스트-맵-test-map)의 관련 테스트 | 항상 |
| Refactor 후 | 테스트 맵의 관련 테스트 | 코드가 바뀐 경우만 |
| [자체 리뷰](../SKILL.md#35-자체-리뷰) 후 | 리뷰로 수정한 파일의 맵 테스트 | 수정이 있을 때만 |
| 작업 `completed` 전이 | [회귀 의무 목록](../../wf-doc/references/templates.md#작업-기록-work-log) 전량 | 항상. 이 작업의 유지 테스트를 목록에 추가하고 SHA를 기록 |
| [통합](../SKILL.md#36-통합) | 전체 테스트 스위트 1회 + 회귀 의무 목록 전량 | 사이클당 1회. 전체 스위트를 실행하는 유일한 시점 |
| [세션 재개](../SKILL.md#31-현재-상태-재확인) | 회귀 의무 목록 전량 | 목록의 마지막 성공 SHA가 HEAD와 다르거나 워킹트리에 미커밋 변경이 있을 때만. 같으면 인용 |
| Stop 훅 | 저장소 전역 게이트([`docs/quality-gates.md`](../../../docs/quality-gates.md)) + 열린 작업의 의무 목록 `유지` 행 | 트리 키(HEAD + 워킹트리 상태·diff)가 마지막 통과와 다를 때만. 에이전트가 아니라 훅이 실행하며, 실패는 종료 차단 |

시크릿 스캔은 세 열 모두에서 필수다 — 비밀 정보의 유출은 변경 규모에 비례하지 않기 때문이며, 이 항목만 "변경 파일만"의 예외로 저장소 전역을 대상으로 한다.

Stop 훅 행은 위의 여섯 시점과 성격이 다르다. 나머지는 에이전트가 수행하는 의무이고, 이 행은 **에이전트가 그 의무를 지켰는지 기계가 확인하는 층**이다. 둘은 대체 관계가 아니다 — 게이트가 조용했다는 것은 검증을 수행했다는 증거가 아니며, 게이트가 막았다는 것은 의무를 건너뛰었다는 증거다.

Green과 Refactor 후에 회귀 의무 목록 전량을 실행하지 않는다. 목록은 작업이 누적될수록 커지므로, 작업마다 전량을 돌리면 검증 시간이 작업 수에 비례해 늘어난다. 작업 단위의 회귀 방어는 테스트 맵이 맡고, 누적 방어는 `completed` 전이·통합·재개 세 시점이 맡는다.

## 2. 경로별 검증 깊이

`필수`는 생략할 수 없다. `조건부`는 괄호의 조건을 만족할 때만 수행하며, 수행하지 않으면 생략 이유를 작업 기록에 남긴다. `—`는 기본 생략이며 이유 없이 생략할 수 있다.

| 단계 | 경량 경로 | 정식 경로 — 소규모 (내부 구현, 승인 범위 안, 단일 컴포넌트) | 정식 경로 — 공개 계약·데이터 모델·보안·마이그레이션 변경 |
|---|---|---|---|
| §3.4-1 포맷·정적 분석 | 필수 (변경 파일만, 시크릿 스캔 포함) | 필수 (변경 파일만, 시크릿 스캔 포함) | 필수 (저장소 전체, 시크릿 스캔 포함) |
| §3.4-2 변경 영역 단위 테스트 | 필수 (테스트 맵의 관련 테스트) | 필수 (테스트 맵의 관련 테스트) | 필수 (테스트 맵의 관련 테스트) |
| §3.4-3 통합 테스트 | — | 조건부 (변경이 컴포넌트 경계를 넘는 경우) | 필수 |
| §3.4-4 인수 조건 시나리오 | — (인수 조건 없음) | 필수 (해당 작업의 인수 조건만) | 필수 (전체 인수 조건) |
| §3.4-5 비기능 검증 | — | 조건부 (기준선에 성능·호환성 목표가 명시된 경우) | 필수 (보안·호환성) + 조건부 (성능) |
| §3.4-6 빌드·실제 실행 | 조건부 (빌드 산출물이나 설정이 바뀐 경우) | 필수 1회 | 필수 |
| §3.5 요구사항·설계 블록 | — (범위 밖 변경 여부 1문항만) | 필수 | 필수 |
| §3.5 정확성·안정성 블록 | 조건부 (버그 수정인 경우) | 필수 | 필수 |
| §3.5 보안·운영 블록 | — | 조건부 (입력 처리·로그·비밀 정보에 닿는 경우) | 필수 |
| §3.5 품질 블록 | 필수 (디버그 코드·임시 파일 1문항 + 결정 사다리 1문항 + 인용 SHA 1문항) | 필수 | 필수 |
| 회귀 의무 목록 | — (경량 경로는 목록에 추가하지 않음. 기존 목록이 있으면 통합 시 실행) | 필수 (`completed` 전이·통합·재개) | 필수 |
| §3.6 통합 후 전체 스위트 | — (§3.4-2 결과를 최종 증거로 사용) | 필수 1회 | 필수 1회 |
| [wf-doc 자체 검토](../../wf-doc/SKILL.md#4-자체-검토) | 경량 경로 문서 항목만 | 필수 | 필수 |

경로 판정은 [wf-design 경량 경로 조건](../../wf-design/SKILL.md#적용-제외--경량-경로)과 [§4.2 중대한 변경](../SKILL.md#42-중대한-변경--구현-보류-후-재승인-필요) 목록을 그대로 사용한다. 세 번째 열의 조건에 하나라도 해당하면 세 번째 열을 적용한다. [§2.4](../SKILL.md#24-최소-구현-원칙--ponytail-full-모드)의 최소화 제외 영역(신뢰 경계 입력 검증, 데이터 손실 오류 처리, 보안·접근성)에 닿는 변경은 경량 경로로 판정되었더라도 세 번째 열을 적용한다.

다음 조건에서는 한 열 오른쪽(더 깊은 열)을 적용한다.

- TDD 사이클에서 Red→Green 전환이 두 번 이상 실패했다.
- [현재 상태 재확인](../SKILL.md#31-현재-상태-재확인)에서 기준선 이후의 저장소 변경이 변경 영역과 겹친다.
- 실패 분류에 "원인을 확인하지 못한 실패"가 남아 있다.

## 3. 회귀 의무 목록의 진입 조건과 상태

**진입 조건.** 목록에 추가하는 테스트는 **같은 커밋 SHA에서 두 번 통과**해야 한다 — Green 확인 시 한 번, `completed` 전이 시 한 번. 두 실행 사이에 코드가 바뀌었으면 `completed` 전이에서 두 번 실행한다. 조건을 충족하지 못한 테스트는 `보류(결정성 미확인)`으로 표기하고 통합의 전체 스위트에서만 실행한다. 보류 테스트가 이후 두 사이클에서 같은 SHA로 통과하면 `유지`로 올린다.

**크기.** 작업당 추가하는 유지 테스트는 [§2.4](../SKILL.md#24-최소-구현-원칙--ponytail-full-모드)의 "그 로직이 깨지면 실패하는 가장 작은 검증 하나" 원칙을 따른다. 목록이 작업 수의 세 배를 넘으면 자체 리뷰에서 축소 대상을 검토한다.

**상태 어휘.**

| 상태 | 의미 | 전이 |
|---|---|---|
| `유지` | 이후 모든 작업에서 통과해야 하는 의무 | 기본 |
| `대체(→DCR-NNN 또는 TASK-NN)` | 기준선 변경으로 테스트의 의미가 바뀌어 새 테스트가 의무를 이어받음 | DCR 승인과 같은 변경에서 |
| `폐기(이유)` | 보호 대상 코드가 제거되어 의무가 소멸 | 제거 작업의 `completed` 전이에서 |
| `보류(결정성 미확인)` | 진입 조건 미충족 | 두 사이클 연속 통과 시 `유지` |

`유지` 행을 통과시키려고 테스트를 수정·제외·삭제하는 것은 [§3.4](../SKILL.md#34-검증)의 "인수 조건을 완화하지 않는다"에 해당하는 위반이다. 회귀 사건을 `기존 실패`로 재분류하려면 마지막 성공 SHA보다 앞선 실패 증거가 있어야 한다.

## 4. 예산 신호 이후의 검증

세션 핸드오프 경고(컨텍스트 임계값 초과 신호)를 받은 뒤에는 다음을 적용한다.

- 진행 중인 계획 항목의 §3.4-1·2는 마친다. 새 계획 항목의 검증은 시작하지 않는다.
- §3.4-3~6과 §3.6 전체 스위트는 이번 세션에서 시작하지 않고, 작업 기록의 검증 절에 `미수행 — 예산 신호 후 인계`로 기록하며 인계 절의 다음 행동에 남긴다. 미수행 검증을 성공으로 간주하지 않는다([§2.5](../SKILL.md#25-완료의-증거)).
- §3.5는 품질 블록만 수행하고 나머지 블록은 다음 세션의 첫 행동으로 넘긴다.
- 회귀 의무 목록의 `completed` 전이 실행은 생략하지 않는다. 생략하면 다음 세션이 SHA 비교로 전량 재실행하게 되어 비용이 이월될 뿐이다.

이 규칙은 검증을 면제하지 않는다. 시점을 다음 세션으로 옮길 뿐이며, [완료 조건](../SKILL.md#5-완료-조건)은 모든 열의 필수 단계가 실제 수행된 뒤에만 충족된다.
