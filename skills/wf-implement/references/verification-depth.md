# 검증 시점·실행 집합·테스트 대장 전이

이 문서는 [wf-implement 검증](../SKILL.md#34-검증)이 소유하는 규칙의 표 부분이다. 3튜플 귀속·인용·실패 분류·관문의 의미는 본문 §2.4·§3.3~§3.6이 정의하고, 이 문서는 **어느 시점에 어느 집합을 실행하고 테스트 대장의 행이 어떤 조건으로 전이하는지**를 정한다. 본문과 다르면 본문을 우선하고 이 문서를 고친다. 대장의 형식은 [wf-doc 테스트 대장 템플릿](../../wf-doc/references/templates.md#테스트-대장-test-register)을 따른다.

원칙은 둘이다. 같은 테스트 묶음을 통과 후 다시 실행하는 것은 그 사이에 코드가 바뀐 경우에만 한다. 테스트를 지우는 쪽이 입증 책임을 진다.

## 1. 시점별 실행 집합

| 시점 | 실행 집합 | 조건 |
|---|---|---|
| TDD Red | 새 테스트 1개 | 항상 |
| TDD Green | 새 테스트 + 관련 행 | 항상 |
| Refactor 후 | 관련 행 | 코드가 바뀐 경우만 |
| [자체 리뷰](../SKILL.md#35-자체-리뷰) 후 | 리뷰로 수정한 파일의 관련 행 | 수정이 있을 때만 |
| TASK `completed` 전이 | 대장 `유지` 행 전량 | 항상. 이 TASK의 테스트를 등록하고 SHA를 기록 |
| [통합](../SKILL.md#36-통합) | 전체 테스트 스위트 1회 + `유지` 행 전량 + 재정비 관문 | 작업당 1회. 전체 스위트를 실행하는 유일한 시점 |
| DCR 승인 | 재정비 관문(`대체` 전이) | DCR이 보호 스코프의 의미를 바꿀 때 |
| [세션 재개](../SKILL.md#31-현재-상태-재확인) | `유지` 행 전량 | 마지막 성공 SHA ≠ HEAD 또는 워킹트리에 미커밋 변경이 있을 때만. 같으면 인용 |

**관련 행**은 대장에서 `보호 스코프`가 변경 파일·심볼과 겹치는 행이다. 대장에 없는 파일은 "관련 행 없음"으로 적고, 통합의 전체 스위트가 최종 그물이 된다. 전량 실행은 `completed` 전이·통합·재개 세 시점 밖에 두지 않는다 — 대장이 커질수록 작업당 비용이 비례해 늘기 때문이다.

## 2. 상태와 전이

| 상태 | 의미 | 진입 조건 | 허용 시점 |
|---|---|---|---|
| `유지` | 이후 모든 작업에서 통과해야 하는 의무 | 같은 SHA에서 2회 통과(Green 1회 + `completed` 전이 1회). 둘 사이에 코드가 바뀌었으면 전이에서 2회 실행 | TASK `completed` 전이 |
| `대체` | 기준선 변경으로 의미가 바뀐 테스트를 새 행이 이어받음 | DCR 승인. 대체 행 ID 기록 | DCR 승인 |
| `병합` | 같은 보호 스코프를 더 넓은 행이 흡수 | 관문 4조건 + 중복 증거. 흡수 행 ID 기록 | 재정비 관문 |
| `격리` | 통과를 신뢰할 수 없어 완료 판정·게이트에서 제외하되 계속 실행 | 같은 SHA에서 결과 불일치, 또는 실행 환경 원인으로 통과를 확인할 수 없음. 수정 후속 작업 기록 | 즉시 |
| `폐기` | 보호 스코프 소멸·동어반복·신호 없음으로 의무 소멸 | 관문 4조건 전부 + 사용자 승인 | 재정비 관문 |

진입 조건을 채우지 못한 새 테스트는 등록하지 않고 다음 `completed` 전이에서 다시 판정한다. 전이된 행은 삭제하지 않고 상태·분류·이유·일시를 남긴다. `유지` 행을 통과시키려고 테스트를 수정·제외·삭제하는 것은 [§3.4](../SKILL.md#34-검증) "인수 조건을 완화하지 않는다"의 위반이다. 회귀 사건(이전 성공 → 실패)을 `기존 실패`로 재분류하려면 마지막 성공 SHA보다 앞선 실패 증거가 있어야 한다.

## 3. 재정비 관문

시점은 통합과 DCR 승인이다. 순서:

1. 변경이 닿은 보호 스코프의 행을 **Breaking**(코드 변경 후 실패 → 수정), **Stale**(통과하지만 바뀐 동작을 더 이상 검증하지 않음 → `대체` 또는 폐기 후보), **Missing**(새 동작에 필요한데 없음 → 추가)으로 분류한다. Stale은 실행 신호가 없으므로 이 문항이 유일한 트리거다.
2. 폐기·병합 후보마다 아래 4조건을 검토한다. 하나라도 미달이면 `유지`.
3. 제안을 작업 기록 `### 테스트 대장 변경`에 적고 완료 보고 관문에서 일괄 승인받은 뒤 대장과 `## 재정비 기록`을 갱신한다. 변경이 없어도 재정비 기록에 1행을 남긴다.

| 조건 | 내용 |
|---|---|
| 분류 명시 | `중복`(같은 보호 스코프를 다른 행이 덮음) · `동어반복`(구현을 바꿔도 통과) · `자명`(의미 있는 단언 없음) · `신호 없음`(보호 스코프가 바뀌어도 실패할 수 없음) · `고아`(보호 스코프의 파일·심볼이 현재 트리에 없음) 중 하나와 사유 |
| 증거 | 중복: 커버리지 겹침 또는 뮤테이션 동치(도구가 없으면 단언 대조 기록). 동어반복·자명: 구현을 바꿔도 통과하는 실험. 고아: `git ls-files`·심볼 검색 결과 |
| 유일 검증 아님 | 그 행이 어떤 인수 조건의 유일한 검증이 아니다. 유일하면 대체 행을 먼저 등록 |
| 사용자 승인 | 완료 보고 관문의 일괄 응답 |

"한 번도 실패한 적 없음"은 단독 사유가 아니다. 그 테스트는 무가치가 아니라 하중을 받고 있을 가능성으로 취급한다.

## 4. 테스트 작성 체크리스트

[§2.4](../SKILL.md#24-최소-구현-원칙--ponytail-full-모드)의 작성 기준을 리뷰할 때 다음 냄새를 찾는다. 하나라도 있으면 고친 뒤 등록한다.

| 냄새 | 징후 |
|---|---|
| Assertion Roulette | 설명 없는 단언이 여러 개라 어느 것이 실패했는지 알 수 없음 |
| Magic Number | 의미를 알 수 없는 리터럴 기대값 |
| Lazy Test | 여러 테스트가 같은 대상을 같은 방식으로 호출 |
| Conditional Logic | 테스트 안의 if·for로 기대 결과가 갈림 |
| Empty / Trivial | 단언이 없거나 non-null·true 확인뿐 |
| Duplicate Assert | 같은 조건을 반복 단언 |

## 5. 검증 결과 기록

작업 기록 `## 검증 결과`의 결과 요약은 다섯 필드를 고정으로 적는다. 형식은 [wf-doc 합본 템플릿](../../wf-doc/references/templates.md#작업-기록-work-log)이 정한다.

| 필드 | 내용 |
|---|---|
| 총계 | N (성공 N / 실패 N / 미수행 N) |
| 기준 | 커밋 SHA · 워킹트리 clean 또는 dirty |
| 명령 | 묶음별 실제 실행 명령, 묶음마다 1줄 |
| 커버리지 | 도구가 내는 지표만(라인·분기·함수). 없으면 `N/A — 이유` |
| 산출물 | 형식명과 경로. 없으면 `없음` |

산출물은 세 층이다. **권장** — 러너가 내장 지원하면 결과는 JUnit XML, 커버리지는 Cobertura XML 또는 LCOV. **허용** — 내장 지원이 없으면 러너의 네이티브 기계 판독 형식(JaCoCo XML, Go coverprofile, TRX, NUnit XML, TAP)을 그대로 두고 형식명을 적는다. 변환 의무는 없다. 산출물은 생성물이므로 커밋하지 않는다. 검증 표의 `분류` 열은 결과가 `실패`일 때 §3.4의 네 가지 중 하나, 그 외 `—`이며 증거 열에는 SHA와 명령이 있어야 인용할 수 있는 기록이다.
