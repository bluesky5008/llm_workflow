# Workflow 2 — 계획 수립 + 구현 + 검증·리뷰 + 통합

목적: 승인된 요구사항과 설계를 구현하고, 완료 여부를 검증하여 안전하게 통합한다.

이 워크플로우의 문서를 만들거나 갱신할 때는 [wf-doc 공통 포맷](../wf-doc/SKILL.md)을 함께 적용한다. 이 스킬은 구현 산출물의 필요성·저장 위치·필수 내용·상태 전이·완료 판단을 소유하고, wf-doc은 문서 유형·머리말·절 구조·식별자·하이퍼링크·증거·변경 이력·인계의 표현 형식을 소유한다. 구현 계획, 작업 기록, 검증 결과와 완료 보고의 Markdown 골격은 이 스킬에서 다시 정의하지 않고 [wf-doc 문서 유형별 템플릿](../wf-doc/references/templates.md)을 따른다.

## wf-design과의 역할 경계

[wf-design](../wf-design/SKILL.md)은 **무엇을 왜 어떤 계약과 구조로 만들지** 결정하고 승인된 기준선을 발행한다. 이 스킬은 **그 기준선 안에서 어떤 작업과 코드로 구현하고 완료를 어떻게 증명할지** 소유한다.

> **정본:** 이 절이 wf-design ↔ wf-implement 경계의 정본이다. 상대 스킬에는 [요약](../wf-design/SKILL.md#wf-implement와의-역할-경계)만 두며, 경계를 바꿀 때는 이 절을 고치고 그 요약이 여전히 맞는지 확인한다.

| 중첩 영역 | wf-design 소유 | wf-implement 소유 |
|---|---|---|
| 문제·범위·성공 기준 | [요구사항, 인수 조건과 비기능 목표의 의미](../wf-design/SKILL.md#42-요구사항-정의) | 승인된 항목을 작업과 검증에 빠짐없이 매핑 |
| 저장소 조사 | 설계를 결정하기 위한 현재 동작·제약·영향 조사 | [계획 직전 기준선과 작업 트리의 변경·실행 가능성 재확인](#31-현재-상태-재확인) |
| 구조와 계획 | [아키텍처, 책임, 인터페이스, 데이터와 품질 속성](../wf-design/SKILL.md#43-sw-설계) | [작업 순서, 변경 파일, 의존성, 테스트와 롤백 계획](#32-계획-수립) |
| 프로토타입과 제품 코드 | 가설·범위·폐기 여부가 명시된 설계 실현 가능성 프로토타입 | 승인된 기준선을 충족하는 제품 코드와 유지할 테스트 |
| 구현 중 결정 | 제품 동작, 공개 계약, 데이터, 보안, 주요 책임과 장기 결정 | 승인 범위 안의 되돌릴 수 있는 내부 구현 세부사항 |
| DCR·ADR | [변경 분류, 대안·영향 분석, 재승인과 새 기준선](../wf-design/references/design-change.md) | 차이를 감지하고 영향받는 구현을 보류하며 증거·현재 코드 상태·초안을 인계 |
| 검증 | 검증할 동작, 인수 조건과 품질 목표, 검증 전략 | [구체적인 테스트 선택·실행, 결과 분류와 증거 기록](#34-검증) |
| 문서 | 요구사항·설계·ADR·DCR 기준선의 의미 | 작업 기록, 코드·설정·운영 문서 갱신과 구현 결과; 기준선 의미 변경은 wf-design으로 반환 |
| 승인과 실행 권한 | 설계 기준선의 승인·재승인과 효력 | 기준선 안의 로컬 구현 자율 진행; push·병합·배포·삭제는 별도 사용자 권한 필요 |
| 완료 | 승인된 구현 기준선을 발행하고 인계 가능 여부 결정 | [구현·검증·리뷰·통합의 완료와 증거](#5-완료-조건) |

경계 적용 규칙:

1. 승인된 기준선이 없으면 정식 구현을 시작하지 않는다.
2. 구현 계획은 승인된 설계를 작업 단위로 번역할 수 있지만 요구사항이나 핵심 설계를 추가·수정할 수 없다.
3. 승인 범위 안의 내부적이고 되돌릴 수 있는 구현 세부사항은 이 스킬에서 결정하고 이유를 기록한다.
4. 제품 동작, 인수 조건, 공개 인터페이스, 데이터 모델, 보안 정책, 주요 컴포넌트 책임 또는 되돌리기 어려운 결정을 바꿔야 하면 영향받는 구현을 보류하고 wf-design으로 반환한다.
5. 경계가 불분명하면 중대한 변경으로 취급하여 보류하고 wf-design의 분류를 받는다.
6. 설계 승인을 외부 시스템 변경이나 비가역 작업의 실행 승인으로 해석하지 않는다.

반환 흐름은 `차이 감지 → 영향받는 구현 보류 → 증거·코드 상태·DCR/ADR 초안 인계 → wf-design 분류·재승인 → 새 기준선 수신 → 계획 갱신·구현 재개` 순서를 따른다.

## wf-doc과의 역할 경계

[wf-doc](../wf-doc/SKILL.md)은 구현 내용을 결정하지 않고, 이 스킬이 결정하거나 확인한 내용을 사람이 읽고 AI가 재개할 수 있는 문서로 표현한다.

1. 무엇을 구현했고 검증 결과가 무엇이며 완료되었는지는 이 스킬이 결정한다. 결정된 내용을 어떻게 식별·배치·연결·인계할지는 wf-doc을 따른다.
2. wf-doc은 테스트를 실행하거나 구현 성공·완료를 선언하지 않는다. 템플릿을 채우려면 새로운 구현 판단이 필요한 경우 이 스킬로 돌아온다.
3. 이 스킬은 Markdown 골격, 공통 머리말 또는 링크 규칙을 별도로 복제하지 않는다. 문서 형식이 필요하면 [wf-doc 템플릿](../wf-doc/references/templates.md)을 참조한다.
4. 문서 머리말의 `completed`, 작업의 `completed`, 최종 결과의 `완료`를 같은 상태로 간주하지 않는다. 구현 결과와 작업 상태는 이 스킬의 판단이며 문서 상태는 wf-doc의 기록 상태다.
5. 최종 인계에는 이 스킬의 완료 조건과 [wf-doc 자체 검토](../wf-doc/SKILL.md#4-자체-검토)를 모두 충족해야 하지만 두 상태를 하나로 합치지 않는다.
6. 문서화 중 요구사항·설계 기준선의 의미 변경이 발견되면 wf-doc이나 이 스킬에서 결정하지 않고 wf-design으로 반환한다.

> **정본:** 중첩 기능별 소유권표(산출물, 계획, 작업 기록, 검증, 완료, 상태, 추적성, 인계, 품질 판단)는 [wf-doc의 wf-implement 경계표](../wf-doc/SKILL.md#wf-implement와의-경계)가 정본이다. 판단이 필요하면 그 표를 읽고, 경계를 바꿔야 하면 그 표를 고친 뒤 이 요약이 여전히 맞는지 확인한다.

## 1. 시작 조건

다음 입력이 준비되어 있어야 한다.

- 사용자가 승인한 요구사항 명세
- 사용자가 승인한 SW 설계
- ADR과 기술적 제약
- 측정 가능한 인수 조건
- 확인 가능한 저장소의 현재 상태

이 스킬은 승인 기록과 기준선의 존재·일관성을 확인하지만 요구사항이나 설계를 스스로 승인하지 않는다. 누락되거나 모호한 입력은 [wf-design 사용자 승인 관문](../wf-design/SKILL.md#8-사용자-승인-관문)으로 반환한다.

선행 단계: [wf-design](../wf-design/SKILL.md) — Workflow 1(요구사항 정의 + SW 설계)

승인된 기준선이 없거나 현재 저장소와 명백히 충돌하면 구현을 시작하지 않는다. 먼저 wf-design으로 기준선을 보완하고 사용자 승인을 받는다.

예외: wf-design의 적용 제외(경량 경로) 조건 — 동작·공개 인터페이스·데이터 모델·보안에 영향이 없고, 국소적이며 되돌리기 쉽고, 새 설계 결정이 필요 없는 작업 — 을 만족하면 요구사항 명세와 설계 문서 없이 시작할 수 있다. 이 경우에도 변경 범위 준수, 검증, 결과 보고는 생략하지 않는다.

## 2. 기본 원칙

### 2.1 기준선

사용자가 승인한 요구사항과 설계를 작업의 기준선으로 삼는다. 계획, 구현, 검증은 기준선의 관련 항목을 추적할 수 있어야 한다.

### 2.2 변경 범위

- 요청과 승인된 설계에 필요한 변경만 수행한다.
- 사용자가 만든 기존 변경과 관련 없는 파일을 보존한다.
- 범위 밖에서 발견한 문제는 임의로 수정하지 않고 별도 항목으로 보고한다.
- 새로운 요구사항이나 핵심 설계 변경을 구현 세부사항으로 위장하지 않는다.

### 2.3 자율 진행과 승인

다음 조건을 모두 만족하면 계획 수립 후 별도 승인 없이 구현을 계속할 수 있다.

- 승인된 요구사항과 설계 안에서 수행되는 변경
- 되돌릴 수 있는 로컬 변경
- 공개 인터페이스, 데이터 모델, 보안 정책을 중대하게 바꾸지 않는 변경
- 외부 시스템에 상태 변경을 일으키지 않는 작업

다음 작업은 사용자가 명시적으로 요청하거나 승인한 경우에만 수행한다.

- 원격 저장소에 push
- Pull Request 생성 또는 병합
- 패키지 게시
- 운영 환경 배포
- 외부 사용자나 시스템에 결과 전송
- 데이터 삭제와 되돌리기 어려운 마이그레이션

wf-design에서 받은 설계 승인은 위 작업의 실행 승인이 아니다. 설계 승인과 외부·비가역 작업 권한을 별도로 확인한다.

### 2.4 최소 구현 원칙 — ponytail `full` 모드

코드 작성은 ponytail 스킬의 `full` 모드를 기준으로 한다. 기본 강도는 `full`이며, 사용자가 명시적으로 지시한 경우에만 `lite` 또는 `ultra`로 바꾼다. ponytail 스킬이 설치되지 않은 환경에서도 아래 원칙을 동일하게 적용한다.

**우선순위: ponytail 스킬이 설치되어 있고 그 스킬의 지침이 이 스킬의 내용과 다르면 이 스킬의 내용을 우선한다.** 특히 강도 변경, 테스트 작성 방식, 최소화 예외 영역은 이 스킬의 규정을 따른다.

코드를 작성하기 전에 다음 결정 사다리를 위에서부터 검토하고, 성립하는 첫 번째 단계에서 멈춘다.

1. 애초에 만들 필요가 있는가? → 없으면 만들지 않는다 (YAGNI)
2. 이 저장소에 이미 있는가? → 기존 헬퍼, 유틸, 패턴을 재사용한다
3. 표준 라이브러리가 해결하는가? → 표준 라이브러리를 사용한다
4. 플랫폼 네이티브 기능이 해결하는가? → 그 기능을 사용한다
5. 이미 설치된 의존성이 해결하는가? → 그 의존성을 사용한다
6. 한 줄로 가능한가? → 한 줄로 작성한다
7. 그래도 필요하면 동작하는 최소한의 코드만 작성한다

사다리는 문제를 이해한 뒤에 적용하는 것이지 이해를 대신하는 것이 아니다. 작업을 끝까지 읽고 실제 코드 흐름을 추적하기 전에는 사다리를 오르지 않는다. 해법에는 게으르되, 조사에는 게으르지 않는다.

적용 규칙:

- 요청되지 않은 추상화, 새 의존성, 보일러플레이트를 추가하지 않는다.
- 추가보다 삭제를, 영리함보다 평범함을, 가능한 한 적은 파일 수를 선호한다.
- 문제를 이해했다는 전제에서, 동작하는 가장 짧은 diff를 선택한다.
- 증상 패치가 아니라 근본 원인을 수정하고, 공유 함수의 문제는 호출부가 아니라 그 함수에서 한 번 고친다.

다음 영역은 최소화의 대상이 아니며 철저함을 생략하지 않는다.

- 신뢰 경계에서의 입력 검증
- 데이터 손실을 막는 오류 처리
- 보안과 접근성

테스트는 다음 기준을 따른다. 사소하지 않은 로직에는 그 로직이 깨지면 실패하는 가장 작은 실행 가능한 검증 하나를 남긴다. 자명한 한 줄 변경에는 테스트를 요구하지 않는다. 저장소에 기존 테스트 체계가 있으면 그 체계 안에서 작성한다.

테스트를 남기기로 판정된 로직은 그 테스트를 구현보다 먼저 작성한다(TDD). 순서는 [3.3의 TDD 사이클](#33-구현)을 따른다. 테스트 우선은 테스트의 양을 늘리는 규칙이 아니다. 무엇을 테스트할지는 위 기준을 그대로 따르고 작성 시점만 앞당긴다. 위 기준이 요구하는 테스트의 작성은 결정 사다리 1단계(YAGNI)의 기각 대상이 아니다.

### 2.5 완료의 증거

- "완료"는 코드가 작성되었다는 뜻이 아니다.
- 완료 여부는 인수 조건과 검증 결과로 판단한다.
- 실행하지 못한 검증은 성공한 것으로 간주하지 않는다.
- 검증하지 못한 항목과 남은 위험을 최종 결과에 명시한다.

## 3. 진행 절차

### 3.1 현재 상태 재확인

계획을 작성하기 직전에 다음을 확인한다.

- 이전 세션에서 진행하던 작업 기록(`docs/work/<작업-ID>/`)이 있는가? 있다면 계획의 진행 상태와 미완료 항목부터 확인한다.
- 기준선 작성 이후 저장소가 변경되었는가?
- 사용자 또는 다른 작업의 미커밋 변경이 있는가?
- 관련 테스트와 빌드가 현재 어떤 상태인가?
- 요구사항과 설계가 실제 코드 구조에 여전히 적용 가능한가?

중대한 차이가 있으면 영향 범위를 분석하고 wf-design으로 기준선을 보완한다.

이 재확인은 승인된 설계를 다시 결정하는 단계가 아니다. 기준선 이후의 변경과 실행 가능성만 확인하며, 요구사항·설계의 의미를 수정해야 하면 이 단계에서 계획을 중단하고 wf-design으로 반환한다.

### 3.2 계획 수립

계획에는 다음 내용을 포함한다.

- 작업 단위와 수행 순서
- 각 작업이 충족할 요구사항과 설계 요소
- 수정하거나 추가할 주요 파일
- 작업 간 의존성
- 테스트와 검증 방법
- 위험이 높은 변경과 선행 확인 사항
- 데이터 마이그레이션 및 롤백 방법
- 문서와 운영 환경 변경

각 작업은 하나의 명확한 결과와 완료 조건을 가진다. 가능한 경우 독립적으로 구현하고 검증할 수 있는 크기로 나눈다.

각 작업의 검증 방법에는 선행 테스트(무엇으로 [TDD 사이클](#33-구현)의 Red를 시작할지)를 명시한다. 자동화할 수 있는 인수 조건은 어느 작업에서 실패하는 인수 테스트로 먼저 전환할지 계획에서 식별하고, 자동화할 수 없는 인수 조건은 [검증](#34-검증)의 시나리오 검증 대상으로 남긴다.

계획 문서의 절 구조, 작업 식별자와 링크는 [wf-doc 구현 계획 템플릿](../wf-doc/references/templates.md#구현-계획-plan)을 따른다. 이 절의 목록은 계획에 들어갈 의미상 필수 내용이며 별도의 문서 포맷이 아니다.

계획의 진행 상태는 작업 중 갱신한다 (`pending → in-progress → completed`). 동시에 여러 작업을 진행하더라도 한 작업의 책임과 결과가 모호해지지 않도록 한다. 계획을 트리로 구조화한 작업은 상태를 갱신할 때 같은 변경에서 [wf-tree](../wf-tree/SKILL.md)의 렌더링 규칙에 따라 트리 표현을 재생성한다.

계획 자체가 새로운 제품 결정이나 중대한 설계 결정을 필요로 하면 계획과 구현을 중단하고 wf-design으로 돌아가 기준선을 갱신·재승인받는다. Workflow 2 안에서 계획만 승인받는 것으로 설계 기준선 갱신을 대신하지 않는다.

### 3.3 구현

계획의 순서에 따라 작은 단위로 구현한다.

- 각 작업을 시작할 때 최소 구현 원칙(2.4)의 결정 사다리를 먼저 적용한다.
- 관련 코드와 테스트를 같은 작업 단위에서 함께 변경하되, 작성 순서는 아래 TDD 사이클을 따른다.
- 저장소의 기존 스타일과 구조를 따른다.
- 사용자 변경과 관련 없는 변경을 보존한다.
- 임시 우회책, 미완료 사항, 기술 부채를 숨기지 않는다.
- 공개 인터페이스, 설정, 마이그레이션이 바뀌면 관련 문서를 갱신한다.
- 각 작업 완료 시 가장 가까운 범위의 검증을 수행한다.

각 작업 단위는 다음 TDD 사이클로 구현한다.

1. **Red:** 2.4 기준으로 테스트가 필요한 동작에 대해, 그 동작이 없거나 잘못되면 실패하는 가장 작은 테스트를 먼저 작성하고 실행하여 의도한 이유로 실패하는지 확인한다.
2. **Green:** 결정 사다리(2.4)를 적용해 테스트를 통과시키는 최소 구현을 작성하고 성공을 확인한다.
3. **Refactor:** 테스트 성공을 유지하며 중복 제거와 구조 정리를 수행한다.

사이클을 적용할 수 없는 변경(자동 테스트가 불가능한 환경 의존 동작, 테스트 체계 부재 등)은 이유를 작업 기록에 남기고 [검증](#34-검증)의 후행 검증으로 대체한다.

버그 수정은 원인 코드를 고치기 전에 버그를 재현하는 실패 테스트를 먼저 작성한다. 자동 재현이 불가능하면 수동 재현 절차와 불가 이유를 기록한다. 이 규칙은 경량 경로의 단일 버그 수정에도 적용한다.

테스트가 없는 기존 코드의 동작을 변경할 때는 변경 전에 현재 동작을 고정하는 특성화 테스트(characterization test)를 변경이 닿는 범위에 비례해 작성한다. [역공학](../wf-design/references/reverse-engineering.md)으로 복원한 작업에서는 역공학 산출물의 검증 가능한 기대 동작(테스트 분석, `RR` 항목)을 특성화 대상 선정의 입력으로 사용한다.

구현 중 설계와 다른 선택이 필요한 경우 설계대로 구현할 수 없는 이유, 영향을 받는 요구사항과 인수 조건, 가능한 대안, 권장 변경과 위험을 기록한다.

단순한 구현 세부사항이면 계획과 문서를 갱신하고 계속한다. 요구사항이나 핵심 설계를 바꾸는 내용이면 해당 구현을 보류하고 DCR 및 ADR 초안을 작성한 뒤 [wf-design의 승인된 설계 변경 절차](../wf-design/references/design-change.md)로 돌아간다.

이 스킬은 차이를 감지하고 영향받는 구현을 보류하며 증거, 완료·진행·실험·미시작 코드의 상태와 DCR/ADR 초안을 인계하는 책임을 가진다. 변경의 최종 분류, 대안 결정, 사용자 재승인과 새 기준선 발행은 [wf-design DCR 절차](../wf-design/references/design-change.md)가 소유한다.

새 설계 기준선이 승인되면 유지할 구현, 수정할 구현, 되돌릴 구현, 추가·변경할 검증, 마이그레이션 및 롤백 작업을 구분하여 계획에 반영한다.

### 3.4 검증

검증은 변경 위험에 비례하여 다음 순서로 수행한다.

1. 포맷 및 정적 분석
2. 변경 영역의 단위 테스트
3. 컴포넌트 간 통합 테스트
4. 인수 조건 기반 시나리오 테스트
5. 성능, 보안, 호환성 등 관련 비기능 검증
6. 빌드 또는 실제 실행 확인

검증할 동작, 인수 조건과 품질 목표는 wf-design 기준선에서 가져온다. 이 스킬은 구체적인 테스트·명령·환경을 선택하고 실행하여 증거를 남기며, 구현을 통과시키기 위해 인수 조건을 완화하거나 의미를 바꾸지 않는다.

각 인수 조건에 대해 검증 방법, 결과와 증거를 기록한다. 검증 문서의 절 구조, 검증 식별자와 증거 링크는 [wf-doc 검증 결과 템플릿](../wf-doc/references/templates.md#검증-결과-verification)을 따른다.

TDD로 작성한 테스트는 최초 실패 실행과 구현 후 성공 실행을 모두 증거로 기록한다(실패→성공 전환). 검증 결과의 결과 값은 기존 어휘(성공·실패·미수행)를 그대로 사용하고, 구현 전의 의도된 실패는 결과가 아니라 증거·비고에 기록한다.

테스트 실패는 이번 변경으로 발생한 실패, 기존에도 존재한 실패, 실행 환경·외부 의존성으로 인한 실패, 원인을 확인하지 못한 실패로 구분한다. 기존 실패라고 판단하면 근거와 재현 방법을 남긴다. 실패한 검증을 단순히 제외하여 전체 성공으로 보고하지 않는다.

검증 결과와 증거 요약(실행한 명령, 테스트 이름, 핵심 출력)은 작업 기록의 검증 섹션에 남긴다. 대화에만 남긴 검증 결과는 세션이 끝나면 추적할 수 없다.

### 3.5 자체 리뷰

구현 완료 후 전체 변경 사항을 다시 검토한다.

**요구사항과 설계**

- 요구사항과 인수 조건을 모두 충족하는가?
- 승인된 설계와 구현이 일치하는가?
- 설계와 달라진 부분이 기록되었는가?
- 불필요하거나 범위 밖인 변경이 포함되지 않았는가?

**정확성과 안정성**

- 오류 처리와 경계 조건이 충분한가?
- 실패 시 데이터와 상태가 일관되게 유지되는가?
- 재시도, 동시성, 중복 실행 문제가 없는가?
- 기존 동작에 의도하지 않은 회귀가 없는가?

**보안과 운영**

- 인증, 권한, 입력 검증이 적절한가?
- 비밀 정보나 개인정보가 노출되지 않는가?
- 데이터 손실 또는 하위 호환성 위험이 없는가?
- 로그와 오류 메시지가 운영에 충분하고 안전한가?

**품질**

- 결정 사다리(2.4)를 통과하지 못하는 불필요한 코드, 추상화, 의존성이 남아 있지 않은가?
- 테스트가 구현 방식이 아니라 요구 동작을 검증하는가?
- TDD 사이클을 적용하지 못한 변경에 이유가 기록되었는가?
- 코드가 기존 구조와 스타일에 맞는가?
- 문서와 코드가 일치하는가?
- 디버그 코드, 비밀 정보, 임시 파일이 남지 않았는가?

리뷰에서 발견한 문제는 수정하고 영향을 받는 검증을 다시 수행한다.

### 3.6 통합

통합은 구현 결과를 저장소와 실제 사용 흐름에 완결된 상태로 반영하는 과정이다.

- 관련 코드, 테스트, 문서, 설정을 일관되게 갱신한다.
- 필요한 마이그레이션과 롤백 절차를 준비한다.
- 통합된 상태에서 최종 빌드와 테스트를 수행한다.
- 요구사항과 인수 조건의 충족 여부를 최종 확인한다.
- 남은 제한 사항과 후속 작업을 기록한다.

로컬 작업 트리에 변경 사항을 완결된 형태로 반영하는 것은 기본 작업 범위에 포함한다. 커밋, push, PR, 병합, 배포는 사용자의 요청 범위에 따라 수행한다.

## 4. 변경 관리

### 4.1 경미한 변경 — 이유를 기록하고 계속 진행 가능

- 내부 구현 세부사항
- 승인된 설계를 더 명확히 하는 문서 보완
- 인수 조건의 의미를 바꾸지 않는 테스트 보강
- 공개 계약에 영향을 주지 않는 코드 구조 개선

위 항목은 승인된 기준선의 의미와 계약을 바꾸지 않을 때만 이 스킬이 소유한다. 의미가 바뀌거나 판단이 애매하면 중대한 변경으로 전환한다.

### 4.2 중대한 변경 — 구현 보류 후 재승인 필요

다음 변경은 영향받는 구현을 보류하고 DCR 및 ADR 초안을 작성한 뒤 wf-design의 승인된 설계 변경 절차에 따라 사용자의 재승인을 받는다.

- 제품 동작이나 범위 변경
- 인수 조건 변경
- 공개 인터페이스 또는 데이터 모델의 중대한 변경
- 주요 컴포넌트의 책임 변경
- 새로운 보안 또는 개인정보 위험
- 비용, 배포, 호환성 위험 증가
- 기존 ADR을 뒤집는 결정
- 되돌리기 어려운 데이터 마이그레이션

이 목록은 wf-implement가 보류와 반환을 시작하기 위한 감지 기준이다. 변경의 최종 분류와 승인 여부는 wf-design이 결정하며, 판단이 애매하면 중대한 변경으로 취급한다.

## 5. 완료 조건

다음 조건을 모두 만족하면 작업이 완료된다.

- 계획된 작업이 모두 완료되었거나 제외 이유가 기록되었다.
- 구현이 승인된 요구사항과 설계에 일치한다.
- 각 인수 조건의 검증 결과가 기록되었다.
- 관련 자동화 테스트와 빌드가 성공했다.
- 실패하거나 수행하지 못한 검증이 명시되었다.
- 자체 리뷰에서 발견된 중대한 문제가 해소되었다.
- 코드, 테스트, 문서, 설정이 함께 통합되었다.
- 남은 위험, 제한 사항, 후속 작업이 공개되었다.

조건을 충족하지 못한 상태에서 작업을 중단해야 한다면 "완료"가 아니라 "부분 완료" 또는 "차단됨"으로 보고한다. 이때 작업 기록에 중단 사유, 보존한 변경과 그 상태, 되돌린 변경과 그 이유, 재개 조건과 다음 단계를 남긴다.

## 6. 최종 결과 보고

작업 결과에는 완료 상태, 완료한 내용, 주요 변경, 설계와 달라진 점, 검증 결과, 인수 조건 충족 여부, 통합 상태, 남은 위험·제한과 후속 작업을 포함한다. 검증 결과에는 성공 여부뿐 아니라 실제로 실행한 명령, 테스트 또는 확인 방법을 포함한다.

이 목록은 보고에 담아야 할 **의미상 필수 내용**이지 Markdown 포맷이 아니다. 전달 형태를 다음과 같이 구분한다.

- **대화형 보고:** 사용자에게 직접 전달하는 결과 요약이다. 위 내용을 작업 규모에 맞는 분량으로 전달하며, 템플릿 절 제목을 그대로 옮겨 적지 않는다. 경량 경로 작업은 완료 상태, 변경 내용, 실행한 검증, 남은 위험만으로 축약할 수 있다.
- **영구 완료 보고 문서:** `work-log.md`에 `completion` 유형을 합쳐 남기는 기록이다([§7 작업 기록과 저장 위치](#7-작업-기록과-저장-위치)). 절 구조와 문서 연결은 [wf-doc 완료 보고 템플릿](../wf-doc/references/templates.md#완료-보고-completion)을 따른다.

완료 보고 문서를 남길지는 이 스킬이 결정한다. 정식 경로에서는 남기고, 경량 경로에서는 [wf-doc 경량 경로 문서](../wf-doc/SKILL.md#28-경량-경로-문서)로 축약하거나 대화형 보고만으로 갈음할 수 있다. 어느 경우에도 실패·미수행 검증과 남은 위험은 생략하지 않는다.

## 7. 작업 기록과 저장 위치

구현 계획은 저장소 전체를 관통하는 현행 문서로 `docs/plan.md`에 두고, 작업 폴더 `docs/work/<작업-ID>/`에는 해당 작업의 작업 기록만 남긴다. 이 스킬이 소유하는 파일은 다음과 같다.

```text
docs/
└── plan.md            # plan — 저장소 현행 구현 계획 (계획 트리 포함)
docs/work/<작업-ID>/
└── work-log.md        # work-log — 이 작업의 작업 내역
```

- 검증 결과(`verification`)와 완료 보고(`completion`)는 별도 파일을 만들지 않고 `work-log.md`에 유형을 합쳐 기록한다. 공통 머리말의 `문서 유형`에 합친 유형을 쉼표로 나열하고 각 유형의 필수 절을 유지한다.
- 같은 위치의 `requirements.md`, `design.md`, `decisions.md`(결정 등록부)와 작업 폴더의 ADR·DCR 파일은 [wf-design 산출물](../wf-design/SKILL.md#6-산출물)이 소유한다. 이 스킬은 해당 파일을 링크로 참조하고 기준선의 의미를 바꾸지 않는다.

**작업 ID 발행:** 정식 경로에서는 wf-design이 발행한 작업 ID를 그대로 사용한다. 경량 경로처럼 wf-design을 거치지 않는 작업에서 기록을 남기기로 하면 이 스킬이 작업 ID를 발행한다. 문자열 문법은 [wf-doc 공통 머리말 규칙](../wf-doc/SKILL.md#23-공통-머리말-작성)을 따르며, 같은 작업이 나중에 정식 경로로 전환되어도 ID를 바꾸지 않는다.

계획의 진행 상태와 검증 결과는 대화가 아니라 이 기록에 갱신하며, 세션이 중단된 뒤 재개할 때 가장 먼저 읽는 재개 지점으로 사용한다. 경량 경로 작업은 기록을 생략하거나 축약할 수 있다. 축약할 때 유지할 최소 구성은 [wf-doc 경량 경로 문서](../wf-doc/SKILL.md#28-경량-경로-문서)를 따른다.

작업 기록에는 기준선과 현재 계획, 실제 수행 내용, 변경 파일, 발견과 결정, 실행한 검증, 설계와 달라진 점, 미완료 항목과 재개 지점을 포함한다. 기록의 Markdown 구조와 증거 링크는 [wf-doc 작업 기록 템플릿](../wf-doc/references/templates.md#작업-기록-work-log)을 따른다.
