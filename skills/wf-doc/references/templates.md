# 문서 유형별 템플릿

새 문서를 만들 때 공통 머리말 뒤에 해당 유형의 절을 추가한다. 이 파일은 **표현 구조만** 정의한다. 요구사항·설계·ADR·DCR·승인의 의미, 발생 조건, 충분성과 상태 전이 권한은 [wf-design](../../wf-design/SKILL.md)이 소유하고, 구현 계획·작업 기록·검증·완료의 의미, 실행과 판정 권한은 [wf-implement](../../wf-implement/SKILL.md)가 소유한다. 아래 필수 절은 결정된 정보를 기록하는 공통 슬롯이며, 절이 존재하거나 채워졌다는 사실만으로 내용의 충분성·승인·완료를 선언하지 않는다. 기존 저장소에 더 구체적인 템플릿이 있으면 절 이름은 보존하되, 이 파일의 필수 구조와 공통 머리말을 유지한다.

## 공통 머리말

모든 문서는 다음 순서로 시작한다. 필드의 작성 규칙(날짜 형식, 작업 ID 문법, 기준선 표기, `관련 문서`의 링크 조건, `요약`의 요건)은 [wf-doc 공통 머리말 작성](../SKILL.md#23-공통-머리말-작성)이 소유한다.

```markdown
# <문서-ID>: <문서 제목>

> 문서 유형: `<type>`
> 작업 ID: `<내용 소유자가 정한 작업 ID>`
> 상태: `<status>`
> 기준선: `<vN | draft | N/A — 이유>`
> 작성일: `<YYYY-MM-DD>`
> 최종 갱신: `<YYYY-MM-DD>`
> 관련 문서: [<문서-ID>: <제목>](<상대 경로>) 또는 N/A — 허용된 이유

## 요약

- 목적:
- 현재 결론 또는 상태:
- 다음 행동:
```

- 날짜는 ISO 8601 형식으로 쓴다. 시간이 판단에 필요하면 시간대가 포함된 `YYYY-MM-DDTHH:mm:ss±HH:mm`을 사용한다.
- 작업 ID는 `YYYYMMDD-<작업-슬러그>` 형식을 권장한다. 예: `20260725-login-rate-limit`. 내용 소유자가 발행한 기존 작업 ID가 있으면 형식을 바꾸기 위해 새 ID를 만들지 않는다.
- 완료 상태의 문서는 `다음 행동`에 `없음` 또는 명시적인 후속 작업을 기록한다.

## 공통 상태 규칙

| 문서 유형 | 일반적인 상태 흐름 |
|---|---|
| `requirements`, `design` | `draft → awaiting-approval → approved/rejected/on-hold → superseded` |
| `adr` | `proposed → approved/rejected/withdrawn → superseded` |
| `dcr` | `proposed → awaiting-approval → approved/rejected/on-hold → completed` |
| `approval` | `draft → completed` |
| `plan`, `work-log` | `draft → in-progress → blocked/completed` |
| `verification` | `draft → in-progress → completed` |
| `completion` | `draft → completed` 또는 `blocked` |
| `status` | `draft → awaiting-approval → approved/rejected/on-hold → in-progress → completed`, 완료 후 같은 목표의 작업이 추가되면 `in-progress`로 재개 |

승인 관문의 응답별 전이는 다음과 같다. 어떤 응답이 있었는지와 그 효력은 [wf-design 사용자 승인 관문](../../wf-design/SKILL.md#8-사용자-승인-관문)이 결정한다.

| 사용자 응답 | 대상 상태 | 이후 |
|---|---|---|
| 승인 | `approved` | 기준선 번호를 발행하고 인계 |
| 수정 요청 | `draft` | 보완 후 `awaiting-approval`로 복귀 |
| 거부 | `rejected` | 기준선을 발행하지 않고 이유를 기록 |
| 보류 | `on-hold` | 재개 조건 해소 시 `awaiting-approval`로 복귀 |

상태 흐름은 표현에 사용하는 일반 경로다. 실제 전이 조건과 권한은 내용 소유자 스킬을 따른다. 실제 사건 없이 단계를 자동으로 진행하지 않는다. 승인 취소나 재개처럼 표에 없는 전이가 필요하면 이유와 권한을 변경 이력에 기록한다.

## 공통 변경 이력 절

`requirements`, `design`, `adr`, `dcr`는 문서 끝에 다음 절을 필수로 둔다. 상태, 기준선 또는 승인 결과가 바뀔 때마다 행을 추가한다.

```markdown
## 변경 이력

| 날짜 | 변경 | 근거 | 상태 또는 기준선 | 작성자·승인자 |
|---|---|---|---|---|
| YYYY-MM-DD | 변경 요약 | 관련 DCR·대화·검증 | draft → approved | 이름 또는 역할 |
```

`plan`, `work-log`, `verification`, `completion`, `approval`, `status`에서는 선택 사항이다. 이 유형들은 시간순 기록이나 결정 필드에 사건이 남으므로, 별도 이력이 같은 내용을 반복하면 두지 않는다. 다만 완료된 `status`를 재개할 때는 이 절에 재개 사유와 추가된 작업을 기록한다(절이 없으면 추가한다). 필드 규칙은 [wf-doc 기존 문서 갱신](../../wf-doc/SKILL.md#3-기존-문서-갱신)을 따른다.

## 공통 문서 연결 절

모든 문서 유형은 공통 머리말의 `## 요약` 바로 뒤에 다음 절을 추가한다. 이 절은 문서가 짧아도 생략하거나 다른 절과 합치지 않는다. 유일한 예외는 [wf-doc 경량 경로 문서](../SKILL.md#28-경량-경로-문서)다.

```markdown
## 문서 연결

| 방향 | 관계 | 대상 문서 | 대상 항목 | 비고 |
|---|---|---|---|---|
| input | baseline | [REQ-작업-ID: 요구사항](./requirements.md) | FR-01, AC-01 | 승인된 입력 기준선 |
| output | refinement | [DESIGN-작업-ID: 설계](./design.md) | DES-01 | 이 문서를 구체화 |
```

링크 대상이 하나뿐이어도 표를 유지한다. 선행 문서가 없는 최초 요구사항 문서만 다음과 같이 기록할 수 있다.

```markdown
| 방향 | 관계 | 대상 문서 | 대상 항목 | 비고 |
|---|---|---|---|---|
| input | baseline | N/A | document | 루트 문서이며 선행 문서 없음 |
```

## 문서 유형별 필수 연결

이 표는 내용 소유자가 결정한 의미 관계를 어느 문서에서 링크로 표현할지 매핑한다. 요구사항·설계·ADR·DCR·승인의 관계는 [wf-design 문서 관계와 추적 범위](../../wf-design/SKILL.md#61-문서-관계와-추적-범위)를 따르며, 이 표가 새로운 관계를 만들거나 관계의 필요성을 독자적으로 결정하지 않는다. 대상 문서가 존재하는 시점부터 결정된 연결을 필수로 유지한다. 아직 생성되지 않은 후속 문서는 링크하지 않고, 생성할 때 양쪽 문서를 함께 갱신한다.

| 현재 문서 유형 | 반드시 연결할 문서 |
|---|---|
| `requirements` | 선행 요청·명세, 파생된 설계, 관련 승인 및 요구사항 변경 DCR |
| `design` | 요구사항 기준선, 관련 ADR/DCR, 승인 기록, 구현 계획 |
| `adr` | 결정이 적용되는 요구사항 또는 설계, 대체 전·후 ADR |
| `dcr` | 변경 대상 요구사항·설계·ADR, 승인 기록, 변경된 계획과 검증 결과 |
| `approval` | 승인 또는 거부 대상 문서와 기준선, 다음 단계 계획 또는 인계 문서 |
| `plan` | 승인된 요구사항·설계·ADR/DCR, 같은 작업 폴더의 작업 기록·검증 결과 |
| `work-log` | 구현 계획, 적용 기준선, 발생한 DCR, 검증 결과 |
| `verification` | 검증 대상 요구사항·인수 조건·설계·계획, 완료 보고 |
| `completion` | 승인된 기준선, 구현 계획·작업 기록, 검증 결과, 미완료 후속 문서 |
| `status` | 포함된 각 작업의 계획 또는 요구사항, 포트폴리오 승인 기록 |
| `test-register` | 각 행의 발행 작업(계획 또는 작업 기록), 재정비 기록이 가리키는 작업 기록의 테스트 대장 변경 절 |

각 연결은 현재 문서와 대상 문서 양쪽에 기록한다. 외부·읽기 전용·불변 문서라 역방향 링크를 추가할 수 없는 경우에만 단방향 연결 사유와 대체 추적 위치를 `비고`에 기록한다.

## 추적 식별자 목록

식별자의 층위 구분, 유일성, 발행 권한과 작업 범위 식별자의 링크 규칙은 [wf-doc 추적 식별자](../SKILL.md#추적-식별자)가 소유한다. 이 절은 접두사 목록만 둔다.

항목 ID — 문서 안의 개별 항목을 가리킨다.

```text
FR-01     기능 요구사항
NFR-01    비기능 요구사항
AC-01     인수 조건
DES-01    설계 요소
ADR-001   설계 결정
DCR-001   설계 변경 요청
TASK-01   구현 작업
VER-01    검증 항목
RISK-01   위험
Q-01      미해결 질문
TST-01    테스트 대장 행
```

문서 ID — 파일 하나를 가리킨다. 항목 ID와 구분되도록 다른 접두사를 쓴다.

```text
REQ-<프로젝트-슬러그>      requirements (저장소 현행 문서)
DESIGN-<프로젝트-슬러그>   design (저장소 현행 문서)
PLAN-<작업-ID>     plan (작업별 구현 계획)
WORK-<작업-ID>     work-log
VERIFY-<작업-ID>   verification
RESULT-<작업-ID>   completion
APR-<작업-ID>-NNN  approval
ST-<슬러그>        status (작업 상위 단위)
REGISTER-<프로젝트-슬러그>  test-register (저장소 현행 문서)
```

`adr`와 `dcr`은 문서 하나가 항목 하나에 대응하므로 `ADR-001`, `DCR-001`을 문서 ID로도 사용한다.

## 추적표

요구사항 → 설계 → 작업 → 검증의 연결을 `## 추적성`에 기록하는 권장 표다. 다른 파일에 있는 식별자는 해당 파일의 하이퍼링크로 만든다. 작업 규모에 맞게 열을 줄일 수 있지만, 존재하는 연결을 서술문 속에 숨기지 않는다.

```markdown
## 추적성

| 요구사항 | 설계 | 작업 | 인수 조건 | 검증 | 결과 |
|---|---|---|---|---|---|
| [FR-01](./requirements.md) | [DES-01](./design.md) | [TASK-01](./work/작업-ID/plan.md) | [AC-01](./requirements.md) | [VER-01](./work/작업-ID/work-log.md) | 성공·실패·미수행 |
```

## 인계 블록

워크플로우, 세션 또는 담당자가 바뀌는 문서에 두는 절이다. 어느 필드를 언제 채우고 축약하는지는 [wf-doc 인계와 재개 지점 작성](../SKILL.md#27-인계와-재개-지점-작성)이 소유한다.

```markdown
## 인계

- 다음 단계 또는 워크플로우:
- 시작 조건:
- 입력 문서와 기준선:
- 완료된 항목:
- 미완료 항목:
- 차단 요인:
- 다음 행동:
```

세션 인계에서는 인계 블록에 다음 필드를 추가한다. 작업 ID와 경로 외의 내용을 바꾸지 않는다.

```markdown
- 재개 프롬프트: 작업 <작업-ID> 재개 — <작업 기록 경로>의 인계 절을 읽고 "다음 행동"부터 진행하라.
```

## 정보 표지

한 절에서 성격이 다른 정보를 함께 다룰 때 쓰는 표지다. 사용 조건은 [wf-doc 본문 작성](../SKILL.md#25-본문-작성)이 소유한다.

```markdown
- 사실: 저장소 또는 실행 결과에서 직접 확인한 내용
- 해석: 사실로부터 도출한 판단
- 가정: 아직 확인되지 않았지만 진행을 위해 둔 전제
- 결정: 승인되었거나 문서가 권한을 가진 범위에서 확정한 선택
- 질문: 답변 전까지 미해결인 내용
- 위험: 발생 가능성, 영향, 대응이 필요한 내용
```

## 요구사항 (`requirements`)

문서 ID 권장값: `REQ-<프로젝트-슬러그>` (저장소 현행 문서)

필수 절:

```markdown
## 문제와 목적

## 대상과 시나리오

## 범위

### 포함

### 제외

## 기능 요구사항

| ID | 항목 | 내용 |
|---|---|---|
| FR-01 | | |

## 비기능 요구사항

| ID | 항목 | 내용 |
|---|---|---|
| NFR-01 | | |

## 인수 조건

| ID | 항목 | 내용 |
|---|---|---|
| AC-01 | | |

## 제약과 의존성

## 가정과 미해결 질문

## 위험

## 추적성

## 승인 기록

## 변경 이력
```

- 기능 요구사항·비기능 요구사항·인수 조건 절의 항목은 3열 표(`| ID | 항목 | 내용 |`)에 한 항목씩 나열한다. 표 셀에 담기지 않는 중첩 구조(하위 목록·코드 블록·여러 문단)가 필요한 항목은 표에 ID·항목명과 판단 가능한 한 줄 요약을 유지하고, 상세를 표 바로 아래 `#### <ID> 상세` 하위 절에 둔 뒤 요약에서 앵커 링크로 연결한다. 표에서 항목을 빼는 방식(목록 회귀)은 허용하지 않는다.
- 위험 절과 가정과 미해결 질문 절은 ID(`RISK-NN`, `Q-NN`)를 발행할 때 표 골격 `| ID | 위험 | 영향 | 완화 |`, `| ID | 질문 | 해소 조건 |`을 사용한다. ID를 발행하지 않는 간단한 서술은 계속 허용된다.

요구사항·인수 조건에 필요한 의미, 구현 제약과 승인 조건은 [wf-design 요구사항 정의](../../wf-design/SKILL.md#42-요구사항-정의)와 [승인 관문](../../wf-design/SKILL.md#8-사용자-승인-관문)을 따른다. 이 템플릿은 결정된 내용을 배치하고 연결하는 형식만 정의한다.

- `완료`는 상태가 `completed`인 항목에만 두는 조건부 필드다. 값은 날짜+시각 `YYYY-MM-DD HH:MM`(로컬)이며, 기입 시점과 값의 판정은 [wf-implement 계획 수립](../../wf-implement/SKILL.md#32-계획-수립)이 소유한다. 트리의 완료 시점 표기는 이 필드에서 파생된다([wf-tree 렌더링](../../wf-tree/SKILL.md#7-렌더링)).

- H2는 공통 머리말의 `## 요약`·`## 문서 연결`을 포함해 다음 8개이고 순서도 같다: 요약, 문서 연결, 기준선과 현재 계획, 수행 기록, 설계와 달라진 점, 검증 결과, 완료 보고, 인계. 현재 상태·미완료 항목·재개 지점 절은 두지 않는다 — 그 내용은 `## 인계`에 적는다.
- 수행 기록 항목은 TASK 하나가 `completed`로 전이할 때 한 번 확정해 쓴다. `결정과 이유`·`검증`·`결과`는 필수, `발견 사항`은 선택, `수행 내용`은 계획의 TASK 목표와 다르게 수행했을 때만 쓴다. `변경 파일` 필드는 두지 않는다 — 변경 파일은 git이 정본이며 미커밋 변경만 `## 인계`에 한 줄로 적는다.
- 기록은 오래된 사건부터 시간순으로 추가한다. 큰 diff나 로그를 붙이지 말고 증거 위치를 연결한다. 어떤 사건을 기록하고 설계 차이를 어떻게 처리할지는 [wf-implement 구현 절차](../../wf-implement/SKILL.md#33-구현)를 따른다.
- `## 검증 결과`의 명령은 실제 실행한 형태로 기록하고 핵심 출력만 요약한다. 비기능 검증은 별도 절 대신 표의 NFR 행으로 둔다. 결과 열에는 성공·실패·미수행만 쓰고 새 상태값을 추가하지 않으며, 구현 전의 의도된 실패(TDD)는 증거 열에 기록한다. 실패 분류와 결과 판정은 [wf-implement 검증](../../wf-implement/SKILL.md#34-검증)을 따른다.
- `### 결과 요약`의 다섯 필드와 증거 열의 SHA·명령은 필수다. 없으면 그 검증은 인용할 수 있는 기록이 아니다. 커버리지는 도구가 내는 지표만 적고 없으면 `N/A — 이유`, 산출물은 형식명(JUnit XML, Cobertura, LCOV, JaCoCo XML 등)과 경로를 적되 생성물이라 커밋하지 않는다. `분류` 열은 결과가 `실패`일 때 wf-implement §3.4의 네 가지(이번 변경 · 기존 · 환경 · 원인 미확인) 중 하나, 그 외는 `—`.
- `### 테스트 대장 변경`은 이 작업이 제안하거나 수행한 [테스트 대장](#테스트-대장-test-register)의 등록·전이만 담고 대장을 복제하지 않는다. 제안이 없으면 `없음`으로 적는다. 전이의 의미와 승인은 [wf-implement 재정비 관문](../../wf-implement/references/verification-depth.md#3-재정비-관문)을 따른다.
- `## 완료 보고`의 완료·부분 완료·차단 판단은 [wf-implement 완료 조건](../../wf-implement/SKILL.md#5-완료-조건)을 따른다. 남은 위험·재검증 조건은 `남은 위험과 제한`·`후속 작업`에 쓰고, 후속 작업에는 책임자, 우선순위 또는 시작 조건 중 필요한 정보를 포함한다. 상세 수행 기록을 반복하지 않고 핵심 결과와 링크를 제공한다.
- `## 인계`의 필드와 세션 인계 시 재개 프롬프트는 [wf-doc 인계와 재개 지점 작성](../SKILL.md#27-인계와-재개-지점-작성)을 따른다. 인계 절은 문서에 한 번만 둔다.

## 검증 결과 (`verification`)

문서 ID 권장값: `VERIFY-<작업-ID>` (검증 **항목** 식별자 `VER-01`과 구분한다)

독립 템플릿은 두지 않는다. 별도 파일로 둘 때만 [작업 기록 합본](#작업-기록-work-log)의 `## 검증 결과` 절(H3 4개)을 그대로 사용하며, 기록 규칙도 같다.

## 완료 보고 (`completion`)

문서 ID 권장값: `RESULT-<작업-ID>`

독립 템플릿은 두지 않는다. 별도 파일로 둘 때만 [작업 기록 합본](#작업-기록-work-log)의 `## 완료 보고` 절(H3 5개)과 `## 인계` 절을 그대로 사용하며, 기록 규칙도 같다.

## 포트폴리오 (`status`)

문서 ID 권장값: `ST-<슬러그>`

저장 위치: `docs/status.md` — 저장소 관통 문서(`requirements.md`·`design.md`)와 같은 위치에 둔다. 포트폴리오가 여럿이면 `docs/status-<슬러그>.md`로 구분한다. 진행 중인 작업만 담으며, 행의 추가·제거 시점은 [wf-implement 작업 기록과 저장 위치](../../wf-implement/SKILL.md#7-작업-기록과-저장-위치)가 소유한다.

```markdown
## 목표와 범위

## 작업 목록

| 작업 ID | 제목 | 상태 | 계획·기록 | 의존 | 다음 행동 |
|---|---|---|---|---|---|

## 계획 트리

<!-- generated -->

## 승인 기록

## 인계
```

- 포트폴리오의 생성 승인, 트리 구조·노드 유형과 갱신 규칙은 [wf-tree](../../wf-tree/SKILL.md)를 따른다. 이 템플릿은 결정된 내용을 배치하는 형식만 정의한다.
- `## 계획 트리` 절은 생성물이다. 손으로 수정하지 않으며 생성 시점은 [wf-tree 생성 시점](../../wf-tree/SKILL.md#생성-시점)을 따른다.
- 작업 목록의 상태는 각 작업의 실제 상태를 기록할 뿐이며, 이 문서가 작업 상태를 전이시키지 않는다. `계획·기록` 열은 그 작업의 `plan.md`·`work-log.md` 링크, `다음 행동` 열은 작업 기록 인계 절의 다음 행동 한 줄이다.
- 완료된 포트폴리오에 같은 목표의 작업이 추가되면 문서를 새로 만들지 않고 재개한다. 재개·신설 판단과 절차는 [wf-tree 포트폴리오 생성과 갱신](../../wf-tree/SKILL.md#8-포트폴리오-생성과-갱신)을 따르고, 재개 사유는 [변경 이력](#공통-변경-이력-절)에 기록한다.

## 테스트 대장 (`test-register`)

문서 ID 권장값: `REGISTER-<프로젝트-슬러그>` (대장 **행** 식별자 `TST-NN`과 구분한다)

저장 위치: `docs/test-register.md` — 저장소 관통 현행 문서. 생성·갱신 시점, 행의 상태·전이·관문의 의미는 [wf-implement 검증](../../wf-implement/SKILL.md#34-검증)과 [검증 시점·실행 집합·대장 전이](../../wf-implement/references/verification-depth.md)가 소유한다.

```markdown
## 대장

| ID | 테스트·명령 | 보호 스코프 | 크기 | 발행 작업 | 상태 | 마지막 성공 (일시 · SHA) | 비고 |
|---|---|---|---|---|---|---|---|
| TST-01 | `python -m pytest tests/test_x.py -q` | src/x.py, AC-03 | small | [20260101-sample](./work/20260101-sample/plan.md) | 유지 | 2026-01-02 10:00 · abc1234 | |

## 재정비 기록

| 일시 | 시점 | 작업 | 변경 요약 | 승인 |
|---|---|---|---|---|
| 2026-01-02 11:00 | 통합 | [20260101-sample](./work/20260101-sample/work-log.md#테스트-대장-변경) | 변경 없음 | 완료 보고 관문 |

## 변경 이력
```

- 행 단위는 실행 명령 하나로 도는 묶음(파일 또는 러너)이다. 묶음 안의 개별 테스트가 전이 대상이 되면 그 테스트만 새 행으로 분리하고 원래 행의 비고에 분리 사실을 적는다.
- `테스트·명령`은 실제 실행 형태(환경·작업 디렉터리·플래그 포함)로 쓴다. `마지막 성공`의 SHA는 그 명령으로 통과한 커밋이며 미커밋 변경이 있었으면 `+dirty`를 붙인다. `크기`는 small·medium·large.
- `상태`는 `유지 · 대체 · 병합 · 격리 · 폐기`만 쓴다. 전이된 행은 삭제하지 않고 상태 뒤 괄호에 분류·대상·일시를 적는다 — 예: `폐기(고아, 2026-02-01)`, `병합(→TST-04)`, `대체(→TST-07, DCR-003)`, `격리(환경, 후속 작업 ID)`.
- `## 재정비 기록`은 관문마다 1행이며 변경이 없어도 적는다. `## 변경 이력`은 [공통 변경 이력 절](#공통-변경-이력-절)을 따른다.
