# 문서 유형별 템플릿

새 문서를 만들 때 공통 머리말 뒤에 해당 유형의 절을 추가한다. 이 파일은 **표현 구조만** 정의한다. 요구사항·설계·ADR·DCR·승인의 의미, 발생 조건, 충분성과 상태 전이 권한은 [wf-design](../../wf-design/SKILL.md)이 소유하고, 구현 계획·작업 기록·검증·완료의 의미, 실행과 판정 권한은 [wf-implement](../../wf-implement/SKILL.md)가 소유한다. 아래 필수 절은 결정된 정보를 기록하는 공통 슬롯이며, 절이 존재하거나 채워졌다는 사실만으로 내용의 충분성·승인·완료를 선언하지 않는다. 기존 저장소에 더 구체적인 템플릿이 있으면 절 이름은 보존하되, 이 파일의 필수 구조와 공통 머리말을 유지한다.

## 공통 상태 규칙

| 문서 유형 | 일반적인 상태 흐름 |
|---|---|
| `requirements`, `design` | `draft → awaiting-approval → approved/rejected/on-hold → superseded` |
| `adr` | `proposed → approved/rejected/withdrawn → superseded` |
| `dcr` | `proposed → awaiting-approval → approved/rejected/on-hold → completed` |
| `approval` | `draft → completed` |
| `plan`, `work-log` | `draft → in-progress → blocked/completed` |
| `verification` | `draft → in-progress → completed` |
| `completion` | `draft → completed` 또는 `blocked` |
| `portfolio` | `draft → awaiting-approval → approved/rejected/on-hold → in-progress → completed` |

승인 관문의 응답별 전이는 다음과 같다. 어떤 응답이 있었는지와 그 효력은 [wf-design 사용자 승인 관문](../../wf-design/SKILL.md#8-사용자-승인-관문)이 결정한다.

| 사용자 응답 | 대상 상태 | 이후 |
|---|---|---|
| 승인 | `approved` | 기준선 번호를 발행하고 인계 |
| 수정 요청 | `draft` | 보완 후 `awaiting-approval`로 복귀 |
| 거부 | `rejected` | 기준선을 발행하지 않고 이유를 기록 |
| 보류 | `on-hold` | 재개 조건 해소 시 `awaiting-approval`로 복귀 |

상태 흐름은 표현에 사용하는 일반 경로다. 실제 전이 조건과 권한은 내용 소유자 스킬을 따른다. 실제 사건 없이 단계를 자동으로 진행하지 않는다. 승인 취소나 재개처럼 표에 없는 전이가 필요하면 이유와 권한을 변경 이력에 기록한다.

## 공통 변경 이력 절

`requirements`, `design`, `adr`, `dcr`는 문서 끝에 다음 절을 필수로 둔다. 상태, 기준선 또는 승인 결과가 바뀔 때마다 행을 추가한다.

```markdown
## 변경 이력

| 날짜 | 변경 | 근거 | 상태 또는 기준선 | 작성자·승인자 |
|---|---|---|---|---|
| YYYY-MM-DD | 변경 요약 | 관련 DCR·대화·검증 | draft → approved | 이름 또는 역할 |
```

`plan`, `work-log`, `verification`, `completion`, `approval`에서는 선택 사항이다. 이 유형들은 시간순 기록이나 결정 필드에 사건이 남으므로, 별도 이력이 같은 내용을 반복하면 두지 않는다. 필드 규칙은 [wf-doc 기존 문서 갱신](../../wf-doc/SKILL.md#3-기존-문서-갱신)을 따른다.

## 공통 문서 연결 절

모든 문서 유형은 공통 머리말의 `## 요약` 바로 뒤에 다음 절을 추가한다. 이 절은 문서가 짧아도 생략하거나 다른 절과 합치지 않는다. 유일한 예외는 [wf-doc 경량 경로 문서](../SKILL.md#28-경량-경로-문서)다.

```markdown
## 문서 연결

| 방향 | 관계 | 대상 문서 | 대상 항목 | 비고 |
|---|---|---|---|---|
| input | baseline | [REQ-작업-ID: 요구사항](./requirements.md) | FR-01, AC-01 | 승인된 입력 기준선 |
| output | refinement | [DESIGN-작업-ID: 설계](./design.md) | DES-01 | 이 문서를 구체화 |
```

링크 대상이 하나뿐이어도 표를 유지한다. 선행 문서가 없는 최초 요구사항 문서만 다음과 같이 기록할 수 있다.

```markdown
| 방향 | 관계 | 대상 문서 | 대상 항목 | 비고 |
|---|---|---|---|---|
| input | baseline | N/A | document | 루트 문서이며 선행 문서 없음 |
```

## 문서 유형별 필수 연결

이 표는 내용 소유자가 결정한 의미 관계를 어느 문서에서 링크로 표현할지 매핑한다. 요구사항·설계·ADR·DCR·승인의 관계는 [wf-design 문서 관계와 추적 범위](../../wf-design/SKILL.md#61-문서-관계와-추적-범위)를 따르며, 이 표가 새로운 관계를 만들거나 관계의 필요성을 독자적으로 결정하지 않는다. 대상 문서가 존재하는 시점부터 결정된 연결을 필수로 유지한다. 아직 생성되지 않은 후속 문서는 링크하지 않고, 생성할 때 양쪽 문서를 함께 갱신한다.

| 현재 문서 유형 | 반드시 연결할 문서 |
|---|---|
| `requirements` | 선행 요청·명세, 파생된 설계, 관련 승인 및 요구사항 변경 DCR |
| `design` | 요구사항 기준선, 관련 ADR/DCR, 승인 기록, 구현 계획 |
| `adr` | 결정이 적용되는 요구사항 또는 설계, 대체 전·후 ADR |
| `dcr` | 변경 대상 요구사항·설계·ADR, 승인 기록, 변경된 계획과 검증 결과 |
| `approval` | 승인 또는 거부 대상 문서와 기준선, 다음 단계 계획 또는 인계 문서 |
| `plan` | 승인된 요구사항·설계·ADR/DCR, 작업 기록, 검증 결과 |
| `work-log` | 구현 계획, 적용 기준선, 발생한 DCR, 검증 결과 |
| `verification` | 검증 대상 요구사항·인수 조건·설계·계획, 완료 보고 |
| `completion` | 승인된 기준선, 구현 계획·작업 기록, 검증 결과, 미완료 후속 문서 |
| `portfolio` | 포함된 각 작업의 계획 또는 요구사항, 포트폴리오 승인 기록 |

각 연결은 현재 문서와 대상 문서 양쪽에 기록한다. 외부·읽기 전용·불변 문서라 역방향 링크를 추가할 수 없는 경우에만 단방향 연결 사유와 대체 추적 위치를 `비고`에 기록한다.

## 요구사항 (`requirements`)

문서 ID 권장값: `REQ-<작업-ID>`

필수 절:

```markdown
## 문제와 목적

## 대상과 시나리오

## 범위

### 포함

### 제외

## 기능 요구사항

- FR-01:

## 비기능 요구사항

- NFR-01:

## 인수 조건

- AC-01:

## 제약과 의존성

## 가정과 미해결 질문

## 위험

## 추적성

## 승인 기록

## 변경 이력
```

요구사항·인수 조건에 필요한 의미, 구현 제약과 승인 조건은 [wf-design 요구사항 정의](../../wf-design/SKILL.md#42-요구사항-정의)와 [승인 관문](../../wf-design/SKILL.md#8-사용자-승인-관문)을 따른다. 이 템플릿은 결정된 내용을 배치하고 연결하는 형식만 정의한다.

## 설계 (`design`)

문서 ID 권장값: `DESIGN-<작업-ID>` (설계 **요소** 식별자 `DES-01`과 구분한다)

필수 절:

```markdown
## 설계 목표와 제약

## 시스템 경계와 구조

## 컴포넌트와 책임

- DES-01:

## 데이터와 인터페이스

## 정상·실패·복구 흐름

## 보안과 품질 속성

## 마이그레이션과 롤백

## 검증 전략

## 대안과 결정

## 가정과 미해결 질문

## 위험

## 추적성

## 승인 기록

## 변경 이력

## 인계
```

설계 영역의 필요성, ADR 분리 여부와 DCR 전환 여부는 [wf-design SW 설계](../../wf-design/SKILL.md#43-sw-설계)와 [승인된 설계 변경](../../wf-design/SKILL.md#5-승인된-설계-변경)을 따른다. 이 템플릿은 결정된 설계를 배치하고 연결하는 형식만 정의한다.

## ADR

문서 ID 권장값: `ADR-NNN`

```markdown
## 요약

- 결정:
- 핵심 이유:
- 주요 단점:

## 배경

## 영향을 받는 요구사항과 제약

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|

## 결정

## 이유

## 결과와 감수할 단점

## 후속 작업

## 대체 관계

- 대체 대상 ADR:
- 대체 ADR:

## 승인 기록

## 변경 이력
```

ADR의 생성 조건, 결정 범위, 승인과 대체 의미는 [wf-design 설계 결정 기록](../../wf-design/SKILL.md#44-설계-결정-기록)을 따른다. 이 템플릿은 결정된 ADR 내용을 표현하고 상호 링크하는 형식만 정의한다.

## DCR

문서 ID 권장값: `DCR-NNN`

```markdown
## 변경 사유와 증거

## 기존 기준선과 설계

## 제안 설계

## 변경 항목

| 대상 | 변경 전 | 변경 후 | 이유 |
|---|---|---|---|

## 영향 범위

- 요구사항과 인수 조건:
- 인터페이스와 데이터:
- 보안과 운영:
- 진행 중인 구현:
- 테스트와 문서:

## 고려한 대안

## 구현된 코드의 처리

- 유지:
- 수정:
- 되돌림:

## 마이그레이션과 롤백

## 검증 방법

## 남은 위험

## 승인 기록

## 변경 이력

## 인계
```

DCR 시작 조건, 변경 분류, 영향 분석, 구현 보류, 재승인과 새 기준선은 [wf-design DCR 절차](../../wf-design/references/design-change.md)를 따른다. 이 템플릿은 결정된 DCR 내용을 표현하고 관련 문서를 연결하는 형식만 정의한다.

## 승인 기록 (`approval`)

문서 ID 권장값: `APR-<작업-ID>-NNN`

기존 기준선 문서에 동일한 내용을 명확히 기록할 수 있으면 별도 파일을 만들지 않아도 된다.

```markdown
## 승인 대상

- 문서와 버전:
- 승인 범위:
- 제외 범위:

## 승인 전 미해결 항목

## 결정

- 결과: 승인 | 수정 요청 | 거부 | 보류
- 결정자:
- 결정 일시:
- 근거가 된 사용자 응답 또는 기록:

## 효력

- 유효한 기준선:
- 효력 시작 시점:
- 후속 상태 변경:

## 인계
```

승인 요청, 결정 권한, 승인 범위와 기준선 효력은 [wf-design 승인 관문](../../wf-design/SKILL.md#8-사용자-승인-관문)을 따른다. 이 템플릿은 실제 승인 결과를 영구 문서에 기록하는 형식만 정의한다.

## 구현 계획 (`plan`)

문서 ID 권장값: `PLAN-<작업-ID>`

```markdown
## 기준선

- 관련 요구사항:
- 관련 설계:
- 관련 ADR·DCR:

## 작업 정의

- 목표:
- 범위:
- 범위 밖:
- 가정:
- 위험:

## 작업 목록

### TASK-01: 작업명

- 상태: pending | in-progress | completed | blocked
- 상위: <부모 TASK-ID | 없음>
- 목표:
- 관련 요구사항과 설계:
- 변경 대상:
- 의존성:
- 위험:
- 검증 방법:
- 완료 조건:

## 검증 계획

## 마이그레이션과 롤백

## 인계
```

- 작업 분할, 완료 조건, 상태 전이와 설계 변경 반환은 [wf-implement 계획 수립](../../wf-implement/SKILL.md#32-계획-수립)을 따른다. 이 템플릿은 결정된 계획을 배치하는 형식만 정의한다.
- 작업 상태를 체크박스로 표시할 수 있지만 안정적인 `TASK-NN` 식별자를 함께 유지한다.
- `상위`는 분해 관계이며 `의존성`(순서 제약)과 구분한다. 이 필드에서 파생되는 트리 구조화·시각화 규칙은 [wf-tree](../../wf-tree/SKILL.md)가 소유하며, 트리를 사용하지 않는 계획에서는 생략할 수 있다.

## 작업 기록 (`work-log`)

문서 ID 권장값: `WORK-<작업-ID>`

```markdown
## 기준선과 현재 계획

## 현재 상태

- 진행 중인 작업:
- 마지막 완료 작업:
- 작업 트리 상태:
- 차단 요인:

## 수행 기록

### YYYY-MM-DD — TASK-01

- 수행 내용:
- 변경 파일:
- 발견 사항:
- 결정과 이유:
- 실행한 검증:
- 결과:

## 설계와 달라진 점

## 미완료 항목

## 재개 지점

- 다음 작업:
- 먼저 확인할 사항:
- 필요한 명령 또는 파일:
```

- 기록은 오래된 사건부터 시간순으로 추가한다.
- 큰 diff나 로그를 붙이지 말고 변경 파일과 증거 위치를 연결한다.
- 어떤 사건을 기록하고 설계 차이를 어떻게 처리할지는 [wf-implement 구현 절차](../../wf-implement/SKILL.md#33-구현)를 따른다.

## 검증 결과 (`verification`)

문서 ID 권장값: `VERIFY-<작업-ID>` (검증 **항목** 식별자 `VER-01`과 구분한다)

```markdown
## 검증 범위와 환경

- 대상 기준선 또는 구현:
- 실행 환경:
- 제외 항목:

## 결과 요약

- 성공:
- 실패:
- 미수행:

## 인수 조건별 결과

|---|---|---|---|---|
```

## 포트폴리오 (`portfolio`)

문서 ID 권장값: `PF-<슬러그>`

```markdown
## 목표와 범위

|---|---|---|---|

## 계획 트리

<!-- generated -->

## 승인 기록

```

- 포트폴리오의 생성 승인, 트리 구조·노드 유형과 갱신 규칙은 [wf-tree](../../wf-tree/SKILL.md)를 따른다. 이 템플릿은 결정된 내용을 배치하는 형식만 정의한다.
- `## 계획 트리` 절은 생성물이다. 손으로 수정하지 않고 wf-tree 렌더링 규칙으로 작업 목록에서 재생성한다.
- 작업 목록의 상태는 각 작업의 실제 상태를 기록할 뿐이며, 이 문서가 작업 상태를 전이시키지 않는다.
