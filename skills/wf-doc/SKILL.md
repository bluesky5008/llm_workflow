# Workflow 문서 공통 포맷

목적: 워크플로우 문서를 사람이 빠르게 판단할 수 있고 AI가 다음 세션에서 모호함 없이 작업을 재개할 수 있는 형태로 유지한다.

이 스킬은 문서의 **형식과 기록 방법**을 정의한다. 요구사항·설계·승인·구현·검증의 절차와 필수 내용은 각각 `wf-design`과 `wf-implement`를 따른다.

## 워크플로우 스킬과의 역할 경계

워크플로우 스킬을 **내용 소유자**, wf-doc을 **기록 형식 소유자**로 구분한다.

- 내용 소유자는 조사, 판단, 요구사항, 결정, 승인, 기준선, 완료 조건 및 상태 전이의 의미를 결정한다.
- wf-doc은 결정된 내용을 표현할 문서 유형, 머리말, 절 구조, 상태값 표기, 식별자 표현, 하이퍼링크, 표, 증거, 변경 이력 및 인계 형식을 결정한다.
- wf-doc은 비어 있는 템플릿 필드의 의미를 추측하거나 설계·승인 결정을 대신 내리지 않는다. 내용이 결정되지 않았으면 `TBD`와 해소 조건을 기록하고 내용 소유자의 절차로 돌아간다.
- wf-doc은 산출물의 필요 여부, 저장 위치, 승인 권한 또는 기준선 효력을 정하지 않는다. 해당 결정은 내용 소유자 스킬을 따른다.
- 내용 규칙과 형식 규칙이 충돌하면 의미·권한·상태 전이는 내용 소유자를, 표현·배치·링크는 wf-doc을 따른다.
- 겹치는 규칙을 양쪽에 복제하지 않는다. 소유자 스킬에 원문을 두고 다른 스킬은 해당 절을 하이퍼링크로 참조한다.

### wf-design과의 경계

> **정본:** 이 절이 wf-design ↔ wf-doc 경계의 정본이다. 상대 스킬에는 [요약](../wf-design/SKILL.md#wf-doc과의-역할-경계)만 두며, 경계를 바꿀 때는 이 절을 고치고 그 요약이 여전히 맞는지 확인한다.

| 중첩 영역 | wf-design 소유 | wf-doc 소유 |
|---|---|---|
| 적용과 산출물 | [워크플로우 적용 여부](../wf-design/SKILL.md#1-적용-시점), [필요한 산출물과 저장 구조](../wf-design/SKILL.md#6-산출물) | 선택된 산출물을 문서 유형과 템플릿에 매핑 |
| 요구사항·설계 | [요구사항, 인수 조건 및 설계의 의미와 충분성](../wf-design/SKILL.md#42-요구사항-정의) | 요구사항·설계 문서의 절 구조, 머리말과 링크 |
| ADR | [ADR 필요성, 대안, 결정, 결과 및 승인](../wf-design/SKILL.md#44-설계-결정-기록) | ADR Markdown 템플릿, 상태 표기, 대체 문서 링크 |
| DCR | [변경 분류, 영향 분석, 재승인과 새 기준선](../wf-design/references/design-change.md) | DCR Markdown 템플릿, 변경 이력과 상호 링크 |
| 승인·기준선·상태 | [누가 무엇을 언제 승인하며 어떤 기준선이 유효한지](../wf-design/SKILL.md#8-사용자-승인-관문) | 승인 결과 필드, 상태값 표기, 날짜와 변경 이력 형식 |
| 식별자 | 어떤 대상에 ID가 필요하고 언제 새 ID·기준선을 발행하는지 | 작업·문서·항목 ID와 기준선의 문자열 문법 및 표시 형식 |
| 추적성 | [어떤 요구사항·설계·ADR·DCR·승인·검증이 연결되어야 하는지](../wf-design/SKILL.md#61-문서-관계와-추적-범위) | 결정된 관계를 표현하는 식별자, 하이퍼링크·역방향 링크와 추적표 |
| 승인 요청과 기록 | 사용자에게 승인·재승인을 요청하고 응답의 의미·효력을 결정 | 영구 승인 기록의 템플릿과 승인 대상·근거 링크 형식 |
| 인계 | [Workflow 2로 넘길 내용과 인계 가능 여부](../wf-design/SKILL.md#7-완료-조건) | 인계 블록의 필드, 문서 링크와 재개 지점 형식 |
| 품질 판단 | 요구사항·설계의 정확성, 완전성, 실현 가능성 | 문서 구조의 일관성, 링크 유효성, 기계 판독성과 가독성 |

경계 적용 규칙:

1. 의미를 바꾸지 않는 서식 정규화·링크 수리·표현 개선에는 wf-doc만 사용할 수 있다. 요구사항이나 설계의 내용을 새로 결정하거나 기존 의미를 바꾸면 wf-design으로 전환한다.
2. wf-design 산출물을 문서화할 때는 wf-design 완료 조건과 wf-doc 자체 검토를 모두 통과한다.
3. 상태값은 wf-doc의 표기를 사용하되, 해당 상태로 바꿀 권한과 조건은 wf-design을 따른다.
4. ADR·DCR·승인·추적성·인계는 의미 규칙을 wf-design에서 읽고 표현 형식을 wf-doc에서 읽는다.
5. 식별자 발행과 기준선 증가는 wf-design에서 결정하고, 식별자 문자열과 문서 내 위치는 wf-doc에서 읽는다.
6. 대화형 승인 요청은 wf-design의 상호작용 절차를 따른다. 요청이나 응답을 파일로 보존하면 wf-doc의 `approval` 형식을 적용한다.

### wf-implement와의 경계

> **정본:** 이 절이 wf-implement ↔ wf-doc 경계의 정본이다. 상대 스킬에는 [요약](../wf-implement/SKILL.md#wf-doc과의-역할-경계)만 두며, 경계를 바꿀 때는 이 절을 고치고 그 요약이 여전히 맞는지 확인한다.

| 중첩 영역 | wf-implement 소유 | wf-doc 소유 |
|---|---|---|
| 적용과 산출물 | [계획·작업 기록·검증·완료 보고의 필요 여부, 저장 위치와 필수 내용](../wf-implement/SKILL.md#wf-doc과의-역할-경계) | 선택된 산출물을 `plan`, `work-log`, `verification`, `completion` 유형과 템플릿에 매핑 |
| 구현 계획 | [작업 분할, 순서, 의존성, 위험, 완료 조건과 상태 전이](../wf-implement/SKILL.md#32-계획-수립) | 계획 Markdown 구조, `TASK-NN` 표기와 문서 링크 |
| 작업 기록 | 실제 수행 내용, 변경 파일, 결정, 차단 요인, 갱신 시점과 재개에 필요한 사실 | 작업 로그의 필드, 시간순 표현, 증거 링크와 재개 지점 형식 |
| 검증 | [테스트·명령·환경 선택과 실행, 결과 판정과 실패 분류](../wf-implement/SKILL.md#34-검증) | 검증표, `VER-NN` 표기, 결과와 증거 링크 형식 |
| 완료 | [완료·부분 완료·차단 판단과 통합 상태](../wf-implement/SKILL.md#5-완료-조건) | 완료 보고서의 절 구조와 문서 상태 표기 |
| 상태 | 작업 상태 전이와 최종 구현 결과의 의미 | 문서 상태 및 작업·결과 상태값을 기록하는 위치와 표기 |
| 추적성과 인계 | 어떤 기준선·작업·검증이 연결되는지, 실제 완료·미완료·위험·재개 조건 | 식별자, 하이퍼링크·역방향 링크, 추적표와 인계 블록 형식 |
| 코드·API·운영 문서 | 구현과 일치하는 기술적 내용 | 워크플로우 기록의 공통 포맷만 소유하며 제품별 문서 템플릿을 대체하지 않음 |
| 품질 판단 | 구현 정확성, 검증 충분성, 통합과 완료 여부 | 문서 구조, 필수 필드, 식별자, 하이퍼링크와 기계 판독성 |

경계 적용 규칙:

1. 구현 계획·작업·검증·완료의 의미와 판정은 wf-implement에서 읽고, 그 문서의 골격은 [문서 유형별 템플릿](references/templates.md)에서 읽는다.
2. wf-doc은 테스트를 실행하거나 구현 상태를 추론해 성공·완료를 선언하지 않는다. 확인되지 않은 내용은 `TBD`와 확인 조건으로 남기고 wf-implement로 반환한다.
3. `TASK-NN`과 `VER-NN`은 안정적인 표현 식별자다. 어떤 작업과 검증 항목이 존재하며 무엇을 뜻하는지는 wf-implement가 결정한다.
4. 문서 상태, 작업 상태와 최종 구현 결과를 서로 복사해 자동 전이하지 않는다.
5. 구현 완료 보고를 전달하려면 [wf-implement 완료 조건](../wf-implement/SKILL.md#5-완료-조건)과 [wf-doc 자체 검토](#4-자체-검토)를 각각 통과해야 한다.
6. 문서 작성 중 기준선 의미 변경을 발견하면 wf-design으로, 새로운 구현 판단이 필요하면 wf-implement로 반환한다.

## 1. 기본 원칙

- 결론과 현재 상태를 먼저 쓰고 세부 근거를 뒤에 둔다.
- 사람에게 자연스러운 Markdown을 사용하되, 고정된 필드명·상태값·식별자를 유지한다.
- 확인한 사실, 해석, 가정, 결정, 미해결 질문을 섞어 쓰지 않는다.
- 요구사항에서 구현, 검증까지 같은 식별자와 검증 가능한 Markdown 하이퍼링크로 추적한다.
- 승인, 완료, 검증 성공을 추정하거나 대신 선언하지 않는다.
- 대화에만 존재하는 결정과 증거를 문서의 확정 정보로 취급하지 않는다.
- 기존 문서를 갱신할 때 사용자 작성 내용과 승인된 기록을 보존한다.
- 짧게 쓰되 판단, 재개 또는 검증에 필요한 근거는 생략하지 않는다.
- 문서 길이와 세부 수준을 작업의 복잡도와 위험에 비례시킨다. 빈 템플릿 절을 채우기 위해 내용을 반복하지 않는다.

## 2. 작성 절차

### 2.1 문서 유형 결정

내용 소유자가 필요하다고 결정한 산출물을 다음 유형 중 하나로 매핑하여 `문서 유형`에 기록한다. wf-doc이 산출물 필요 여부를 새로 결정하지 않는다.

| 유형 | 용도 |
|---|---|
| `requirements` | 문제, 범위, 요구사항, 인수 조건 |
| `design` | 구조, 계약, 동작, 품질 속성, 검증 전략 |
| `adr` | 장기간 영향을 주는 단일 설계 결정 |
| `dcr` | 승인된 기준선의 변경 요청과 재승인 |
| `approval` | 승인 범위와 결과를 독립적으로 기록해야 하는 관문 |
| `plan` | 구현 작업, 순서, 의존성, 완료 조건 |
| `work-log` | 진행 상태, 발견 사항, 변경 및 재개 지점 |
| `verification` | 인수 조건별 검증 방법, 결과, 증거 |
| `completion` | 통합 결과, 남은 위험, 후속 작업 |
| `status` | 여러 작업을 묶는 목표, 작업 분해와 계획 트리, 진행 현황 |

새 문서를 만들거나 문서 유형별 필수 절을 판단할 때 [references/templates.md](references/templates.md)를 읽고 해당 템플릿을 적용한다. 여러 유형을 한 파일에 합치면 `문서 유형`을 쉼표로 나열하고 각 유형의 필수 절을 유지한다.

### 2.2 근거 수집

작성 전에 다음을 확인한다.

- 작업 요청과 현재 작업 ID
- 승인된 요구사항·설계 기준선과 관련 ADR/DCR
- 저장소에서 확인한 사실과 실행 환경
- 현재 계획, 구현 상태, 검증 결과
- 사용자가 명시적으로 내린 결정과 승인
- 남은 질문, 위험, 차단 요인

값을 확인할 수 없으면 빈칸으로 두지 않는다. `TBD — 확인 책임자와 확인 조건`으로 기록한다. 적용되지 않는 항목은 `N/A — 적용되지 않는 이유`로 기록한다.

### 2.3 공통 머리말 작성

모든 문서는 다음 순서로 시작한다.

```markdown
# <문서-ID>: <문서 제목>

> 문서 유형: `<type>`
> 작업 ID: `<내용 소유자가 정한 작업 ID>`
> 상태: `<status>`
> 기준선: `<vN | draft | N/A — 이유>`
> 작성일: `<YYYY-MM-DD>`
> 최종 갱신: `<YYYY-MM-DD>`
> 관련 문서: [<문서-ID>: <제목>](<상대 경로>) 또는 N/A — 허용된 이유

## 요약

- 목적:
- 현재 결론 또는 상태:
- 다음 행동:
```

규칙:

- 날짜는 ISO 8601 형식으로 쓴다. 시간이 판단에 필요하면 시간대가 포함된 `YYYY-MM-DDTHH:mm:ss±HH:mm`을 사용한다.
- 작업 ID는 `YYYYMMDD-<작업-슬러그>` 형식을 권장한다. 예: `20260725-login-rate-limit`. 내용 소유자가 발행한 기존 작업 ID가 있으면 형식을 바꾸기 위해 새 ID를 만들지 않는다.
- 문서 ID와 항목 ID는 [추적 식별자](#추적-식별자)와 [문서 유형별 템플릿](references/templates.md)의 문자열 문법을 따른다. 어떤 대상에 ID가 필요하고 새 번호를 발행할지는 내용 소유자가 결정한다.
- 기준선은 `vN`으로 표시한다. 최초 발행, 증가와 효력은 wf-design이 결정하며 wf-doc이 임의로 값을 올리지 않는다.
- 저장소 안의 문서는 저장소 기준 상대 Markdown 링크를 사용해야 한다. 저장소 밖의 문서만 안정적인 URL을 사용할 수 있다.
- `관련 문서`에는 직접 영향을 주거나 받는 주요 문서를 하이퍼링크로 나열한다. 문서 ID, 파일명, 경로를 일반 텍스트나 코드 표기로만 적은 것은 연결로 인정하지 않는다.
- `관련 문서` 머리말은 `## 문서 연결`에 있는 주요 링크의 요약이어야 하며 두 위치의 링크와 관계가 서로 충돌해서는 안 된다.
- 불안정한 줄 번호보다 문서 ID와 절 제목을 참조한다. 안정적인 Markdown 앵커가 있으면 파일 링크에 앵커를 추가한다.
- `요약`은 본문을 읽지 않아도 목적, 현재 판단, 다음 행동을 알 수 있게 작성한다.
- 완료 상태의 문서는 `다음 행동`에 `없음` 또는 명시적인 후속 작업을 기록한다.

### 2.4 상태 기록

다음 상태값만 사용한다.

| 상태 | 의미 |
|---|---|
| `draft` | 작성 중이며 검토 기준이 아님 |
| `proposed` | 검토 또는 승인을 위해 제안됨 |
| `awaiting-approval` | 승인권자의 응답을 기다림 |
| `approved` | 명시적으로 승인되어 기준으로 사용 가능 |
| `in-progress` | 승인된 범위에서 작업 진행 중 |
| `on-hold` | 의사결정 또는 정보 확보를 위해 의도적으로 보류됨 |
| `blocked` | 재개 조건 없이는 진행할 수 없음 |
| `completed` | 해당 문서 유형의 작성·검토 조건을 충족하여 기록으로 전달 가능함 |
| `rejected` | 명시적으로 거부됨 |
| `withdrawn` | 제안자가 철회했거나 더 이상 검토하지 않음 |
| `superseded` | 후속 문서 또는 기준선으로 대체됨 |

- 문서 유형별 허용 상태는 템플릿의 상태 규칙을 따른다.
- 상태를 바꿀 때 근거가 되는 승인, 검증 또는 사건을 본문이나 변경 이력에 기록한다.
- 사용자 승인 전에는 `approved`로, 실행하지 않은 검증은 성공으로, 일부 완료는 `completed`로 표시하지 않는다.
- `on-hold` 또는 `blocked` 상태에는 원인, 영향, 재개 조건, 다음 책임자를 기록한다.

#### 문서 상태와 구현 상태 구분

- 공통 머리말의 `상태`는 **문서 상태**다. 문서가 `completed`여도 구현 작업이나 전체 구현 결과가 자동으로 완료된 것은 아니다.
- 계획 안의 작업 상태와 완료 보고의 구현 결과는 **내용 필드**다. 전이 조건과 완료·부분 완료·차단 판단은 [wf-implement](../wf-implement/SKILL.md)가 소유한다.
- wf-doc은 작업 상태와 구현 결과의 값, 위치와 표기를 템플릿으로 제공하지만 실제 상태를 추론하거나 전이시키지 않는다.
- 구현이 완료되었더라도 문서 링크나 필수 형식이 불완전하면 문서 전달은 완료되지 않는다. 이 경우 구현 결과를 바꾸지 않고 문서 상태와 미완료 사유만 기록한다.

### 2.5 본문 작성

- 각 절에는 하나의 목적만 둔다.
- 내용 소유자가 독립 추적 대상으로 결정한 요구사항과 결정은 한 항목에 하나씩 쓰고 발행된 안정적인 식별자를 표시한다.
- 반복 필드와 대응 관계는 표로, 이유와 맥락은 짧은 문단으로, 순서는 번호 목록으로 작성한다.
- 필수·금지·권장·허용을 구분해 `해야 한다`, `해서는 안 된다`, `권장한다`, `할 수 있다`로 표현한다.
- `적절히`, `충분히`, `가능하면`, `등`처럼 검증 기준이 불분명한 표현은 조건이나 예시로 구체화한다.
- 명령, 코드, 계약, 정확한 값은 코드 블록이나 인라인 코드로 구분한다.
- 큰 로그와 생성 결과를 그대로 붙이지 않는다. 핵심 결과를 요약하고 원본 파일, 명령 또는 아티팩트를 연결한다.
- 비밀 정보, 인증 정보, 개인정보를 문서나 증거에 복사하지 않는다. 필요한 경우 안전한 원본 위치와 접근 조건만 기록한다.

템플릿의 필수 절은 결정된 정보를 빠뜨리지 않고 기록하기 위한 **공통 정보 슬롯**이다. 필수 절의 존재만으로 해당 정보의 적용 여부·충분성·승인 가능성을 결정하지 않는다. 요구사항·설계·ADR·DCR·승인에서는 wf-design이 적용 여부와 충분성을 판단하고, 구현 문서에서는 wf-implement가 판단한다. 작은 문서에서는 의미를 잃지 않는 범위에서 인접한 절을 합칠 수 있다. 적용되지 않는 중요한 항목은 `N/A — 내용 소유자가 판단한 이유`로 남기고, 판단에 필요하지 않은 빈 절과 자리표시자는 제거한다.

정보의 성격을 한 절에서 함께 다뤄야 하면 다음 표지를 사용한다.

```markdown
- 사실: 저장소 또는 실행 결과에서 직접 확인한 내용
- 해석: 사실로부터 도출한 판단
- 가정: 아직 확인되지 않았지만 진행을 위해 둔 전제
- 결정: 승인되었거나 문서가 권한을 가진 범위에서 확정한 선택
- 질문: 답변 전까지 미해결인 내용
- 위험: 발생 가능성, 영향, 대응이 필요한 내용
```

### 2.6 문서 연결, 추적성과 증거

#### 하이퍼링크 강제 규칙

- 어떤 문서·항목 관계가 존재하고 필수인지는 내용 소유자가 결정한다. wf-doc은 새 의미 관계를 만들지 않고, 결정된 관계가 빠짐없이 클릭 가능한 링크로 표현되었는지 검사한다.
- 모든 워크플로우 문서에 `## 문서 연결` 절을 둔다. 다른 절과 합치거나 생략하지 않는다. 유일한 예외는 [경량 경로 문서](#28-경량-경로-문서)다.
- 다른 워크플로우 문서를 가리키는 문서 ID, 파일명, 기준선, ADR/DCR, 계획, 검증 및 인계 입력은 모두 Markdown 하이퍼링크로 작성한다.
- `관련 문서`, `문서 연결`, `추적성`, `승인 기록`, `대체 관계`, `기준선`, `검증 결과`, `인계`에서는 일반 텍스트 경로나 백틱으로 감싼 경로를 링크 대신 사용하지 않는다.
- 현재 문서가 최초 요구사항처럼 선행 워크플로우 문서가 없는 루트 문서인 경우에만 `N/A — 루트 문서이며 선행 문서 없음`을 허용한다. 연결 대상이 있는데 찾지 못한 경우에는 `N/A`로 숨기지 말고 `TBD`와 확인 책임자·조건을 기록한다.
- 아직 생성되지 않은 문서에는 깨진 가상 링크를 만들지 않는다. 해당 문서가 생성되는 변경에서 링크와 역방향 링크를 함께 추가한다.
- 하위 문서를 만들면 상위 문서에도 하위 문서로 향하는 역방향 링크를 같은 변경에서 추가한다. 예를 들어 설계가 요구사항을 링크하면 요구사항도 설계를 링크한다.
- 승인된 문서에 역방향 링크만 추가하는 것은 기준선 의미를 바꾸지 않는 문서 명확화로 처리할 수 있다. 링크가 새로운 관계나 기준선 변경을 의미하면 `wf-design`의 DCR 절차를 따른다.
- 대상 문서가 외부·읽기 전용·불변 기록이라 역방향 링크를 추가할 수 없으면 현재 문서의 `## 문서 연결`에 사유와 대체 추적 위치를 기록한다. 이 경우에만 단방향 연결을 허용한다.
- 같은 파일에 여러 문서 유형을 합쳤으면 파일 경로 대신 해당 절의 Markdown 앵커로 연결한다.
- 문서를 이동하거나 이름을 바꾸면 저장소에서 해당 경로와 문서 ID를 검색하여 들어오는 링크와 나가는 링크를 모두 갱신한다.

`## 문서 연결`은 공통 머리말과 요약 바로 뒤에 다음 형식으로 작성한다.

```markdown
## 문서 연결

| 방향 | 관계 | 대상 문서 | 대상 항목 | 비고 |
|---|---|---|---|---|
| input | baseline | [REQ-프로젝트: 요구사항](./requirements.md) | FR-01, AC-01 | 이 문서의 입력 기준선 |
| output | verification | [WORK-작업-ID: 작업 기록](./work/작업-ID/work-log.md#인수-조건별-결과) | VER-01 | 이 문서를 검증 (verification 유형 합침) |
```

- `방향`은 현재 문서를 기준으로 `input`, `output`, `bidirectional` 중 하나를 사용한다.
- `관계`는 `baseline`, `refinement`, `decision`, `change`, `approval`, `implementation`, `verification`, `result`, `replacement`, `handoff`, `related` 중 가장 구체적인 값을 사용한다.
- `대상 문서`는 반드시 `[문서-ID: 제목](경로)` 형태의 하이퍼링크로 작성한다.
- `대상 항목`에는 관련 FR/NFR/AC/DES/TASK/VER 식별자를 기록한다. 문서 전체가 대상이면 `document`로 기록한다.
- 문서 유형별 필수 연결 대상은 [references/templates.md의 문서 유형별 필수 연결](references/templates.md#문서-유형별-필수-연결)을 따른다.

#### 추적 식별자

식별자는 **항목 ID**와 **문서 ID** 두 층위로 나누며, 두 층위는 접두사를 공유하지 않는다.

항목 ID — 문서 안의 개별 항목을 가리킨다.

```text
FR-01     기능 요구사항
NFR-01    비기능 요구사항
AC-01     인수 조건
DES-01    설계 요소
ADR-001   설계 결정
DCR-001   설계 변경 요청
TASK-01   구현 작업
VER-01    검증 항목
RISK-01   위험
Q-01      미해결 질문
```

문서 ID — 파일 하나를 가리킨다. 항목 ID와 구분되도록 다른 접두사를 쓴다.

```text
REQ-<프로젝트-슬러그>      requirements (저장소 현행 문서)
DESIGN-<프로젝트-슬러그>   design (저장소 현행 문서)
PLAN-<프로젝트-슬러그>     plan (저장소 현행 문서)
WORK-<작업-ID>     work-log
VERIFY-<작업-ID>   verification
RESULT-<작업-ID>   completion
APR-<작업-ID>-NNN  approval
ST-<슬러그>        status (작업 상위 단위)
```

`adr`와 `dcr`은 문서 하나가 항목 하나에 대응하므로 `ADR-001`, `DCR-001`을 문서 ID로도 사용한다. 유형별 권장값과 예시는 [문서 유형별 템플릿](references/templates.md)을 따른다.

- 어떤 대상이 별도 식별자를 가져야 하고 언제 새 식별자나 기준선을 발행할지는 내용 소유자가 결정한다. wf-doc은 발행된 식별자의 문자열 문법, 표시 위치와 링크 형식만 소유한다.
- 문서 안에서 식별자는 유일해야 하며 의미가 바뀌어도 재사용하지 않는다.
- 문서 ID 접두사를 항목 ID로, 항목 ID 접두사를 문서 ID로 쓰지 않는다. `DES-01`은 항상 설계 요소이고 `DESIGN-<프로젝트-슬러그>`는 항상 설계 문서다.
- 삭제된 항목은 조용히 제거하지 말고 상태나 변경 이력으로 대체·취소 이유를 남긴다.
- 요구사항 → 설계 → 작업 → 검증의 연결은 `## 추적성`에 기록하며, 다른 파일에 있는 식별자는 해당 파일의 하이퍼링크로 만든다.
- 검증 증거에는 실행 방법, 실행 환경, 결과, 원본 위치를 포함한다.
- 실패와 미수행을 성공 결과와 분리하고 원인 또는 실행 조건을 기록한다.

권장 추적 표:

```markdown
## 추적성

| 요구사항 | 설계 | 작업 | 인수 조건 | 검증 | 결과 |
|---|---|---|---|---|---|
| [FR-01](./requirements.md) | [DES-01](./design.md) | [TASK-01](./plan.md) | [AC-01](./requirements.md) | [VER-01](./work/작업-ID/work-log.md) | 성공·실패·미수행 |
```

작업 규모에 맞게 열을 줄일 수 있지만, 존재하는 연결을 서술문 속에 숨기지 않는다.

### 2.7 인계와 재개 지점 작성

워크플로우, 세션 또는 담당자가 바뀌는 문서에는 다음 절을 둔다.

```markdown
## 인계

- 다음 단계 또는 워크플로우:
- 시작 조건:
- 입력 문서와 기준선:
- 완료된 항목:
- 미완료 항목:
- 차단 요인:
- 다음 행동:
```

`wf-design`에서 `wf-implement`로 인계할 때는 승인된 기준선, 승인 기록, 관련 ADR/DCR, 인수 조건, 남은 위험을 반드시 하이퍼링크로 연결한다. 승인되지 않은 초안을 구현 기준선으로 인계하지 않는다.

### 2.8 경량 경로 문서

내용 소유자가 [경량 경로](../wf-design/SKILL.md#적용-제외--경량-경로)로 판단한 작업에서 문서를 남기기로 하면, 단일 파일에 다음만 유지하고 나머지 절과 표는 생략한다. 경량 경로 여부는 내용 소유자가 판단하며 wf-doc이 스스로 결정하지 않는다.

- 공통 머리말 중 `문서 유형`, `작업 ID`, `상태`, `최종 갱신`. `기준선`은 `N/A — 경량 경로로 기준선 없음`으로 기록한다.
- `## 요약`의 목적, 현재 결론, 다음 행동
- 수행한 변경과 변경 파일
- 실행한 검증과 결과
- 남은 위험 또는 후속 작업. 없으면 `없음`으로 명시한다.

경량 경로 문서에는 다음을 적용한다.

- `## 문서 연결` 절과 `## 추적성` 표는 생략할 수 있다. 다만 참조하는 워크플로우 문서가 실제로 존재하면 그 링크는 [하이퍼링크 강제 규칙](#하이퍼링크-강제-규칙)대로 클릭 가능한 형태로 남긴다.
- 실패·미수행 검증과 남은 위험은 생략 대상이 아니다. 문서를 줄이기 위해 숨기지 않는다.
- 작업이 진행 중 경량 경로 조건을 벗어나면 그 시점에 정식 문서 유형과 필수 절로 승격하고, 승격 사실을 `## 요약`에 남긴다.

[자체 검토](#4-자체-검토)는 경량 경로 문서에도 적용하되, 생략이 허용된 절에 대한 항목은 통과한 것으로 본다.

## 3. 기존 문서 갱신

1. 현재 상태와 기준선, 관련 문서 링크의 유효성을 먼저 확인한다.
2. 사용자가 작성한 내용과 관련 없는 변경을 보존한다.
3. 승인된 기준선의 의미가 바뀌면 직접 덮어쓰지 않고 `wf-design`의 DCR 절차를 따른다.
4. 문서 관계가 추가·삭제되면 상대 문서의 역방향 링크를 같은 변경에서 갱신한다.
5. 구현 세부사항이나 진행 상태를 갱신하면 관련 계획·검증·추적 항목도 함께 갱신한다.
6. 상태, 기준선, 승인 결과가 바뀌면 `## 변경 이력`에 사건과 근거를 추가한다.
7. 내용이 실제로 바뀐 경우에만 `최종 갱신`을 변경한다.

`## 변경 이력`의 표 형식과 유형별 필수 여부는 [공통 변경 이력 절](references/templates.md#공통-변경-이력-절)을 따른다. `requirements`, `design`, `adr`, `dcr`에는 이 절을 필수로 둔다.

승인자의 이름을 알 수 없으면 임의로 만들지 말고 `사용자`처럼 확인 가능한 역할을 기록한다.

## 4. 자체 검토

문서를 전달하기 전에 확인한다.

- 문서 유형, 작업 ID, 상태, 기준선이 실제 상황과 일치하는가?
- 요약만 읽어도 목적, 현재 상태, 다음 행동을 알 수 있는가?
- 사실, 가정, 결정, 질문이 구분되는가?
- 다른 문서를 가리키는 모든 참조가 일반 텍스트가 아니라 Markdown 하이퍼링크인가?
- 루트 문서를 제외한 모든 문서가 하나 이상의 선행 또는 기준 문서와 연결되는가?
- 새 문서 관계의 역방향 링크가 상대 문서에 반영되었거나 허용된 예외 사유가 기록되었는가?
- 요구사항·설계·작업·검증의 연결이 하이퍼링크와 식별자로 추적되는가?
- 승인과 상태 변경에 근거가 있는가?
- 실패, 미수행 검증, 남은 위험과 차단 요인이 숨겨지지 않았는가?
- `TBD`에는 책임자와 해소 조건이 있고 `N/A`에는 이유가 있는가?
- 모든 로컬 링크의 대상 파일이 존재하고, 사용한 앵커가 실제 제목으로 해석되는가?
- 내용 없는 절, 중복 설명, 큰 원본 로그가 문서를 방해하지 않는가?
- 다음 세션의 AI가 대화 기록 없이 문서만으로 안전하게 재개할 수 있는가?

하이퍼링크 강제 규칙을 하나라도 충족하지 못하면 문서를 완료 상태로 표시하거나 전달하지 않는다. 먼저 링크를 고치거나 허용된 단방향·루트 문서 예외와 대체 추적 방법을 기록한다.

그 밖의 검토 결과에 문제가 있으면 문서를 고친 뒤 전달한다. 중요한 정보가 없어 채울 수 없으면 그 사실과 확보 방법을 미해결 항목으로 남긴다.
