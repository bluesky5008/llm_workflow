# Workflow 1 — 요구사항 정의 + SW 설계

목적: 사용자의 요청을 구현 가능한 요구사항과 승인 가능한 SW 설계로 구체화한다.

승인 후에는 wf-implement 스킬(Workflow 2)로 구현을 진행한다. 승인되지 않은 요구사항과 설계를 구현 기준으로 사용하지 않는다.

이 워크플로우의 문서를 만들거나 갱신할 때는 [wf-doc 공통 포맷](../wf-doc/SKILL.md)을 함께 적용한다. 이 스킬은 산출물의 필요성·저장 위치·필수 내용·상태 전이·승인 효력을 소유하고, wf-doc은 문서 유형·머리말·절 구조·식별자·하이퍼링크·증거·변경 이력·인계의 표현 형식을 소유한다. 요구사항·설계·ADR·DCR·승인 기록의 Markdown 골격은 이 스킬에서 다시 정의하지 않고 [wf-doc 문서 유형별 템플릿](../wf-doc/references/templates.md)을 따른다.

## wf-doc과의 역할 경계

이 스킬은 **요구사항과 설계의 의미 및 승인 절차**를 소유한다. 워크플로우 적용 여부와 필요한 산출물, 요구사항·인수 조건·설계·위험의 내용, ADR·DCR의 필요성, 승인과 기준선의 효력, Workflow 2로 인계할 시점을 결정한다.

[wf-doc](../wf-doc/SKILL.md)은 **결정된 내용을 기록하는 공통 문서 형식**을 소유한다. 머리말과 절 구조, 상태값 표기, 식별자 표현, 문서간 하이퍼링크, 추적표, 증거·변경 이력 및 인계 블록은 wf-doc을 따른다.

1. 무엇을 기록하고 어떤 상태로 전이할지는 이 스킬이, 그것을 어떤 필드·표·링크로 적을지는 wf-doc이 결정한다.
2. wf-doc 템플릿을 채웠다는 이유만으로 요구사항·설계가 완성되거나 승인된 것으로 판단하지 않는다.
3. 필요한 의미가 아직 결정되지 않았으면 wf-doc이 대신 만들지 않고 `TBD`로 표시한 뒤 이 워크플로우로 돌아온다.
4. 문서의 의미·승인 상태·기준선을 바꾸지 않는 서식 정규화·링크 수리·표현 개선은 wf-doc만으로 수행할 수 있다. 새로운 요구사항·설계 관계를 만들거나 기존 의미를 바꾸는 순간 이 워크플로우로 전환한다.

> **정본:** 중첩 기능별 소유권(식별자 발행, 추적성, 승인 기록, 인계 등)은 [wf-doc의 wf-design 경계표](../wf-doc/SKILL.md#wf-design과의-경계)가 정본이다. 판단이 필요하면 그 표를 읽고, 경계를 바꿔야 하면 그 표를 고친 뒤 이 요약이 여전히 맞는지 확인한다.

## wf-implement와의 역할 경계

이 스킬은 **무엇을 왜 어떤 계약과 구조로 만들지** 결정하고 승인된 기준선을 발행한다. [wf-implement](../wf-implement/SKILL.md)는 **승인된 기준선 안에서 어떤 작업과 코드로 구현하고 완료를 어떻게 증명할지** 소유한다.

1. 이 스킬은 문제·범위·요구사항·인수 조건·아키텍처·인터페이스·데이터·품질 속성과 중요한 대안을 결정하고, wf-implement는 이를 실행 계획·코드·테스트·통합으로 옮긴다.
2. 이 스킬은 검증해야 할 동작과 성공 기준을 정하고, wf-implement는 구체적인 테스트 방법을 선택해 실행하고 증거를 남긴다.
3. wf-implement는 승인된 설계를 번역하여 계획할 수 있지만 새로운 제품 결정이나 핵심 설계 결정을 계획 속에 추가할 수 없다.
4. wf-implement가 기준선과 충돌하는 사실을 발견하면 영향받는 구현을 보류하고 증거와 초안을 전달한다. 이 스킬이 변경을 분류하고 DCR·ADR·재승인 및 새 기준선을 소유한다.
5. 설계 승인은 구현 시작 기준을 제공하지만 push·병합·배포·삭제 같은 외부 또는 비가역 작업의 실행 권한을 대신하지 않는다.

설계 단계의 프로토타입은 가설과 실현 가능성을 검증하는 임시 산출물이며 승인된 제품 구현이 아니다. 제품 코드로 유지하려면 이 스킬에서 요구사항·설계 기준선에 반영하고 승인한 뒤 wf-implement에서 구현·검증한다.

> **정본:** 중첩 기능별 상세 소유권과 반환 조건은 [wf-implement의 wf-design 경계표](../wf-implement/SKILL.md#wf-design과의-역할-경계)가 정본이다. 경계를 바꿔야 하면 그 표를 고친 뒤 이 요약이 여전히 맞는지 확인한다.

## 1. 적용 시점

다음 상황에서 이 워크플로우를 사용한다.

- 새로운 기능이나 시스템을 개발할 때
- 기존 기능의 동작이나 공개 인터페이스를 변경할 때
- 요구사항 또는 기술적 접근 방법이 명확하지 않을 때
- 데이터 모델, 보안 정책, 아키텍처를 변경할 때
- 승인된 설계가 없거나 현재 저장소와 일치하지 않을 때

이 단계에서는 원칙적으로 제품 코드를 변경하지 않는다. 저장소 조사, 문서 작성, 읽기 전용 분석은 수행할 수 있다.

설계의 실현 가능성을 확인하기 위한 프로토타입이 필요하면 다음을 먼저 명시한다.

- 검증하려는 가설
- 프로토타입의 범위
- 제품 코드에 포함할지 폐기할지 여부
- 성공과 실패를 판단할 기준

프로토타입은 제품 구현 완료로 간주하지 않는다. 제품 코드로 전환하려면 [wf-implement와의 역할 경계](#wf-implement와의-역할-경계)에 따라 승인된 기준선으로 인계한다.

### 적용 제외 — 경량 경로

다음 조건을 모두 만족하는 작업은 Workflow 1의 산출물 작성을 생략하고 Workflow 2를 축약하여 적용할 수 있다.

- 제품 동작, 공개 인터페이스, 데이터 모델, 보안 정책에 영향을 주지 않는다.
- 변경이 국소적이고 쉽게 되돌릴 수 있다.
- 새로운 설계 결정이나 대안 비교가 필요 없다.

예: 오타·주석·로그 문구 수정, 원인이 명확한 단일 버그 수정, 기존 계약을 바꾸지 않는 테스트 보강.

경량 경로에서도 다음은 생략하지 않는다.

- 변경 범위 준수와 관련 없는 파일 보존
- 변경 위험에 맞는 검증 수행
- 결과와 남은 위험 보고

조건 충족 여부가 의심스러우면 정식 경로를 사용한다. 작업 도중 조건을 벗어나는 것이 확인되면 그 시점에 정식 경로로 전환한다.

## 2. 입력

- 사용자의 작업 요청
- 문제의 배경과 기대 결과
- 기존 저장소, 문서, 실행 환경
- 일정, 기술, 운영상의 제약
- 사용자가 이미 내린 결정

입력이 불완전해도 저장소와 실행 환경에서 확인 가능한 부분부터 조사한다. 결과를 크게 바꾸는 정보만 사용자에게 질문한다.

## 3. 기본 원칙

### 3.1 사실과 불확실성

- 확인한 사실, 해석, 가정을 구분한다.
- 직접 확인할 수 있는 내용은 사용자에게 묻기 전에 조사한다.
- 확인할 수 없는 내용은 추측하지 않고 가정 또는 미해결 질문으로 기록한다.
- 결과를 크게 바꾸지 않는 낮은 위험의 가정은 명시한 뒤 진행할 수 있다.
- 보안, 데이터, 비용, 공개 인터페이스 또는 호환성에 영향을 주는 가정은 사용자에게 확인한다.

### 3.2 범위

- 해결할 문제와 성공 기준을 먼저 정의한다.
- 범위와 범위 밖 항목을 함께 기록한다.
- 요청하지 않은 기능을 설계에 임의로 추가하지 않는다.
- 기존 시스템과 사용자 변경을 제약 조건으로 취급한다.

### 3.3 결정

- 중요한 결정은 선택 결과뿐 아니라 배경과 근거를 기록한다.
- 여러 대안이 의미 있게 경쟁한다면 장단점을 비교한다.
- 오랫동안 영향을 주거나 되돌리기 어려운 결정은 ADR로 분리한다.
- 제품의 목표, 범위 및 중대한 기술 결정은 사용자가 승인한다.

## 4. 진행 절차

### 4.1 현재 상태 조사

요구사항과 설계를 확정하기 전에 다음을 확인한다.

- 저장소 구조와 적용되는 개발 지침
- 현재 동작과 재현 방법
- 관련 모듈, 데이터, 인터페이스
- 기존 테스트와 문서
- 작업 중인 사용자 변경
- 기술적 제약과 잠재적 영향 범위

조사 결과에는 확인된 사실, 사실로부터 도출한 해석, 아직 확인하지 못한 가정, 사용자 결정이 필요한 질문을 구분하여 기록한다.

기존 코드에 승인된 요구사항·설계가 없거나 문서가 코드와 어긋나서 현행 상태 자체를 체계적으로 복원해야 하면 [references/reverse-engineering.md](references/reverse-engineering.md)를 읽고 그 절차(역공학)를 따른다. 역공학 결과는 증거 기반의 현행 상태 초안이며, 이 워크플로우의 검토와 승인 관문을 거쳐야 기준선이 된다.

### 4.2 요구사항 정의

다음 내용을 구체화한다.

- 해결할 문제와 목적
- 대상 사용자 또는 호출 주체
- 주요 사용 시나리오
- 기능 요구사항
- 비기능 요구사항
- 범위와 범위 밖 항목
- 제약 조건과 의존성
- 예외 상황과 실패 시 기대 동작
- 측정 가능한 인수 조건

독립적으로 추적하고 승인·검증해야 하는 요구사항과 인수 조건에는 안정적인 식별자를 부여한다. 어떤 항목을 분리해 식별할지는 이 스킬이 결정하고, 식별자의 문자열 문법은 [wf-doc 추적 식별자](../wf-doc/SKILL.md#추적-식별자)를 따른다.

좋은 인수 조건은 입력 또는 시작 상황, 수행할 행동이나 발생한 사건, 관찰 가능한 기대 결과를 포함한다. 가능한 한 자동 인수 테스트로 전환할 수 있는 형태로 작성한다. 전환할 인수 조건의 선정과 구체적인 테스트 방법은 [wf-implement 계획 수립](../wf-implement/SKILL.md#32-계획-수립)이 소유한다.

구현 방법을 요구사항으로 고정하지 않는다. 특정 기술이 반드시 필요하다면 그 이유와 제약을 함께 기록한다.

요구사항과 인수 조건에 어떤 의미를 담을지는 이 절을 따르고, 문서 절 배치·식별자 표현·하이퍼링크는 [wf-doc 요구사항 템플릿](../wf-doc/references/templates.md#요구사항-requirements)을 따른다.

### 4.3 SW 설계

요구사항을 만족하기 위해 다음 항목을 필요한 수준까지 설계한다.

- **시스템 구조:** 시스템 경계와 외부 연동, 아키텍처와 주요 컴포넌트, 컴포넌트별 책임, 컴포넌트 간 의존 관계
- **데이터와 인터페이스:** 데이터 모델과 상태, 저장 및 수명 주기, API·이벤트·메시지·파일 형식 등의 계약, 입력 검증과 오류 표현, 버전 및 하위 호환성
- **동작:** 정상 시나리오, 경계 및 예외 시나리오, 실패 감지와 복구, 재시도·중복 처리·타임아웃, 동시성 및 데이터 일관성
- **품질 속성:** 인증과 권한, 비밀 정보와 개인정보 보호, 성능과 자원 사용, 안정성과 가용성, 확장성과 유지보수성, 로그·지표·추적·알림
- **전환과 검증:** 기존 시스템과의 호환성, 데이터 또는 설정 마이그레이션, 롤백 방법, 테스트 가능성, 요구사항 및 인수 조건별 검증 전략

모든 항목을 기계적으로 작성할 필요는 없다. 작업에 영향을 주는 항목을 선택하되, 제외한 중요한 항목이 있다면 제외 이유를 기록한다.

이 절은 구조와 계약을 결정하지만 파일별 수정 순서나 작업 분해까지 소유하지 않는다. 승인된 설계를 작업·파일 단위로 변환하는 계획은 [wf-implement 계획 수립](../wf-implement/SKILL.md#32-계획-수립)이 소유한다.

### 4.4 설계 결정 기록

중요한 기술 결정에는 배경, 영향을 주는 요구사항과 제약, 고려한 대안, 선택한 안과 이유, 장점과 감수할 단점, 영향 범위를 기록한다.

ADR은 다음과 같은 결정에 사용한다.

- 핵심 기술이나 데이터 저장 방식 선택
- 주요 컴포넌트의 책임과 경계
- 외부 인터페이스 형식
- 인증, 권한, 개인정보 처리 방식
- 되돌리기 어렵거나 다른 작업에 장기간 영향을 주는 결정

ADR이 필요한지, 어떤 대안과 결정을 담고 언제 상태를 바꿀지는 이 스킬이 결정한다. Markdown 머리말, 상태값 표기, 문서 연결 및 절 배치는 [wf-doc ADR 템플릿](../wf-doc/references/templates.md#adr)을 따른다.

### 4.5 일관성 검토

사용자에게 승인을 요청하기 전에 자체 검토한다.

- 모든 핵심 요구사항이 하나 이상의 설계 요소에 연결되는가?
- 모든 인수 조건을 검증할 방법이 있는가?
- 설계가 범위 밖 기능을 불필요하게 포함하지 않는가?
- 컴포넌트의 책임과 인터페이스가 모호하지 않은가?
- 주요 실패와 복구 시나리오가 빠지지 않았는가?
- 보안 및 데이터 위험이 식별되었는가?
- 기존 동작과의 호환성 영향이 설명되었는가?
- 구현 작업으로 분해할 만큼 설계가 구체적인가?

## 5. 승인된 설계 변경

구현(Workflow 2) 중에 이미 승인된 설계나 요구사항을 변경해야 하는 상황이 되면 [references/design-change.md](references/design-change.md)를 읽고 그 절차(DCR)를 따른다. 변경은 사용자 재승인 전까지 제안 상태이며, 영향받는 구현은 재승인 전까지 확정하거나 통합하지 않는다.

## 6. 산출물

기본 산출물: 요구사항 명세, SW 설계 문서, 미해결 질문과 가정, 위험 목록, 필요한 ADR, 필요한 DCR 및 설계 변경 기록, 요구사항–설계–검증 추적 정보.

저장 위치는 `docs/work/<작업-ID>/`이며, 이 스킬이 소유하는 파일은 다음과 같다.

```text
docs/work/<작업-ID>/
├── requirements.md          # requirements
├── design.md                # design
├── design-change-log.md     # 설계 변경 기록
├── approvals/
│   └── APR-001-<관문명>.md  # approval (별도 파일이 필요한 경우)
├── changes/
│   └── DCR-001-<변경명>.md  # dcr
└── decisions/
    └── ADR-001-<결정명>.md  # adr
```

같은 디렉터리의 구현 산출물(`plan.md`, `work-log.md`, `verification.md`, `completion.md`)은 [wf-implement 작업 기록과 저장 위치](../wf-implement/SKILL.md#7-작업-기록과-저장-위치)가 소유한다. 이 스킬은 해당 파일을 만들거나 판정하지 않고 링크로만 참조한다.

식별자 생성과 기준선 규칙:

- **작업 ID:** 워크플로우를 시작할 때 안정적이고 고유한 작업 ID를 생성하거나 기존 ID를 재사용한다. 같은 작업의 의미가 유지되는 동안 ID를 바꾸지 않는다. 경량 경로로 이 워크플로우를 생략하는 작업의 작업 ID는 [wf-implement](../wf-implement/SKILL.md#7-작업-기록과-저장-위치)가 발행한다.
- **기준선 식별자:** 최초 승인 시 `v1`을 발행하고, 승인된 의미가 바뀌어 재승인될 때마다 1씩 올려 `v2`, `v3` 순으로 발행한다. 번호를 건너뛰거나 재사용하지 않으며, 거부·보류된 제안에는 새 번호를 발행하지 않는다. 요구사항 명세와 설계 문서에는 동일한 유효 기준선과 승인일을 기록한다.
- 작업 ID, 문서 ID, 항목 ID와 기준선의 문자열 문법 및 문서 내 표기는 [wf-doc 식별자 규칙](../wf-doc/SKILL.md#추적-식별자)을 따른다.

### 6.1 문서 관계와 추적 범위

이 스킬은 다음 관계의 존재와 의미를 결정한다.

| 기준 문서 | 의미상 연결해야 하는 대상 |
|---|---|
| 요구사항 | 선행 요청·명세, 이를 구체화한 설계, 승인 기록, 요구사항을 바꾸는 DCR |
| 설계 | 요구사항 기준선, 적용되는 ADR·DCR, 승인 기록, 인계된 구현 계획 |
| ADR | 결정이 적용되는 요구사항·설계, 대체 전·후 ADR |
| DCR | 변경 대상 요구사항·설계·ADR, 승인 기록, 변경 영향을 반영한 계획·검증 |
| 승인 기록 | 승인·수정 요청·거부·보류 대상 문서와 기준선, 후속 인계 또는 계획 |

대상 문서가 아직 존재하지 않으면 관계의 필요성만 보존하고 가상 링크를 만들지 않는다. 대상이 생성되면 같은 변경에서 양쪽 문서에 관계를 반영한다. 어떤 관계가 필요한지와 누락 여부는 이 스킬이 판단하고, 이를 문서간 하이퍼링크와 추적표로 표현하는 방법은 [wf-doc의 문서 연결·추적성 규칙](../wf-doc/SKILL.md#26-문서-연결-추적성과-증거)을 따른다.

작은 작업은 요구사항과 설계를 하나의 문서에 합칠 수 있다. 문서의 크기보다 필요한 결정과 근거가 빠지지 않는 것이 중요하다.

## 7. 완료 조건

다음 조건을 모두 만족하면 산출물이 사용자에게 승인을 요청할 수 있는 상태가 된다.

- 문제, 범위, 범위 밖 항목이 명확하다.
- 기능 및 비기능 요구사항이 정의되었다.
- 인수 조건이 관찰하고 검증할 수 있는 형태다.
- 핵심 요구사항과 설계의 연결을 설명할 수 있다.
- 주요 인터페이스, 데이터, 정상 및 실패 흐름이 정의되었다.
- 중요한 대안과 설계 결정의 근거가 기록되었다.
- 중대한 미해결 질문과 위험이 사용자에게 공개되었다.
- 구현 계획을 수립할 만큼 설계가 구체적이다.
- 기존 기준선의 변경인 경우 DCR, ADR 대체 관계, 변경 기록 및 새 기준선이 일관된다.

## 8. 사용자 승인 관문

사용자에게 대화형 승인 요청을 보낼 때는 목표, 범위, 핵심 요구사항, 설계 요약, 주요 결정, 가정, 남은 질문, 주요 위험과 승인 대상 산출물을 요약하고 이 요구사항과 설계를 구현 기준선으로 승인할지 명시적으로 묻는다. 이는 승인 상호작용의 필수 내용이지 영구 문서의 Markdown 포맷이 아니다.

요구사항·설계 문서와 영구 승인 기록의 절 구조는 wf-doc의 [요구사항](../wf-doc/references/templates.md#요구사항-requirements), [설계](../wf-doc/references/templates.md#설계-design), [승인 기록](../wf-doc/references/templates.md#승인-기록-approval) 템플릿을 따른다. 대화형 승인 요청을 파일로 보존할 때도 wf-doc의 `approval` 문서 유형을 적용한다.

사용자는 다음 중 하나로 응답한다. 각 응답에 대응하는 문서 상태는 [wf-doc 상태 기록](../wf-doc/SKILL.md#24-상태-기록)의 값을 사용한다.

- **승인:** 현재 요구사항과 설계를 기준선으로 확정하고 Workflow 2(wf-implement)로 이동한다. 문서 상태는 `approved`.
- **수정 요청:** 지정한 내용을 보완한 뒤 다시 검토한다. 문서 상태는 `draft`로 되돌리고, 보완이 끝나면 다시 `awaiting-approval`로 올린다.
- **거부:** 제안한 요구사항·설계를 기준선으로 삼지 않는다. 문서 상태는 `rejected`로 바꾸고 거부 이유와 근거가 된 사용자 응답을 기록한다. 문서를 삭제하지 않으며 기준선 번호를 발행하지 않는다. 같은 문제를 다시 다루려면 새 접근으로 이 워크플로우를 다시 수행한다.
- **보류:** 미해결 정보나 의사결정을 확보할 때까지 중단한다. 문서 상태는 `on-hold`로 바꾸고 원인, 영향, 재개 조건과 다음 책임자를 기록한다. 조건이 해소되면 `awaiting-approval`로 되돌린다.

승인 이외의 응답에서는 구현을 시작하지 않는다. 이미 진행 중인 구현이 있으면 [wf-implement](../wf-implement/SKILL.md#wf-design과의-역할-경계)의 보류 규칙을 적용한다.

### 승인 기록

승인은 대화에만 남기지 않고 문서에 기록한다. 승인을 받으면 다음을 수행한다.

1. 요구사항 명세와 설계 문서의 머리말에 기준선 식별자와 승인일을 기록한다. 최초 승인은 `v1`이다.
2. 관련 ADR의 상태를 `approved`로 변경한다.
3. 기존 기준선의 변경이면 설계 변경 기록에 승인 결과를 추가한다.

승인 여부, 승인 범위와 기준선 효력은 이 스킬이 결정한다. 영구 문서에 남기는 승인 기록의 구조와 상호 링크는 [wf-doc 승인 기록 템플릿](../wf-doc/references/templates.md#승인-기록-approval)을 따른다.

승인 기록이 완료되면 승인된 요구사항·설계 기준선, ADR, 인수 조건, 알려진 위험과 미해결 사항을 [wf-implement 시작 조건](../wf-implement/SKILL.md#1-시작-조건)에 맞춰 인계한다. wf-implement가 시작 조건을 확인하기 전에는 구현이 시작된 것으로 간주하지 않는다.
