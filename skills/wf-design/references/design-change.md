# 승인된 설계 변경 절차 (DCR)

이 절차는 이미 승인된 설계를 구현(Workflow 2) 중 발견한 사실이나 ADR 제안에 따라 변경할 때 사용한다. 변경이 요구사항이나 인수 조건까지 미치는 경우에도 별도 절차 없이 이 절차를 그대로 사용하며, 이때 요구사항 명세를 함께 갱신한다.

이 절차는 DCR의 시작 조건, 변경 분류, 영향 분석, 구현 보류 상태 확인, 재승인 및 새 기준선을 소유한다. DCR·ADR·변경 기록의 Markdown 구조, 상태값 표기, 추적성, 승인 기록과 인계 형식은 [wf-doc 공통 포맷](../../wf-doc/SKILL.md)과 [wf-design 경계표](../../wf-doc/SKILL.md#wf-design과의-경계)를 따른다.

[wf-implement](../../wf-implement/SKILL.md)는 차이 감지, 영향받는 구현의 즉시 보류, 증거와 현재 코드 상태 보존 및 초안 인계를 소유한다. 이 절차는 인계받은 내용을 기준으로 변경을 최종 분류하고 대안·영향, 재승인과 새 설계 기준선을 결정한다.

구현 중 발견된 설계 변경은 자동으로 승인된 결정이 아니다. Workflow 2에서 작성한 ADR은 사용자 승인 전까지 **제안 상태**이며, 이 절차를 완료해야 새로운 설계 기준선에 포함된다.

## 1. 변경 원칙

- 현재 설계 문서는 최신 승인 상태를 설명하는 기준 문서로 유지한다.
- 승인된 설계를 근거와 기록 없이 덮어쓰지 않는다.
- 변경 전 설계는 버전 관리 이력과 설계 변경 기록으로 추적할 수 있어야 한다.
- 승인된 ADR의 결정과 근거 본문은 과거 기록이므로 새 결론에 맞춰 고쳐 쓰지 않는다.
- 기존 ADR을 변경해야 하면 새 ADR을 만들고 두 ADR의 대체 관계를 기록한다.
- 변경의 영향을 받는 구현은 재승인 전까지 확정하거나 통합하지 않는다.
- 영향받지 않는 작업은 의존 관계가 없음을 확인한 경우에만 계속할 수 있다.

## 2. 변경 시작 조건

다음과 같은 상황이면 설계 변경을 시작한다.

- 설계대로 구현할 수 없다는 기술적 근거가 발견됨
- 승인 당시의 가정이 실제 코드나 실행 결과와 다름
- 더 안전하거나 단순한 대안이 구현 과정에서 확인됨
- 공개 인터페이스, 데이터 모델 또는 컴포넌트 책임을 바꿔야 함
- 새로운 보안, 개인정보, 성능 또는 운영 위험이 발견됨
- 기존 ADR을 뒤집거나 보완해야 함
- 이미 구현한 일부가 승인된 설계와 다름

단순한 코드 배치, 함수명, 내부 리팩터링처럼 설계의 의미와 계약을 바꾸지 않는 사항은 Workflow 2의 경미한 변경으로 처리할 수 있다.

## 3. 변경 절차

### A. 구현 보류 상태 확인

wf-implement가 영향받는 구현과 통합을 보류하고 다음 상태를 보존·기록했는지 확인한다.

- 완료된 구현
- 진행 중인 구현
- 실험 또는 임시 구현
- 아직 시작하지 않은 작업

이 절차에서는 제품 코드를 추가·수정·되돌리지 않는다. 보류 또는 상태 기록이 완료되지 않았으면 [wf-implement의 경계 규칙](../../wf-implement/SKILL.md#wf-design과의-역할-경계)에 따라 먼저 보류와 인계를 완료한다. 새 기준선 승인 후 구체적으로 유지·수정·되돌릴 파일과 작업은 wf-implement가 계획한다.

보안 사고나 데이터 손실을 막기 위한 긴급 조치는 wf-implement에서 먼저 수행할 수 있다. 이 경우 조치 내용과 사후 설계 변경이 필요한 이유를 인계받아 기록한다.

### B. 설계 변경 요청 작성

각 변경에는 `DCR`(Design Change Request) 식별자를 부여한다.

각 DCR에는 변경 사유와 증거, 발견 위치, 현재 기준선, 관련 요구사항·ADR, 기존 설계, 제안 설계, 변경 항목, 영향 범위, 구현된 코드의 처리, 마이그레이션·롤백 및 검증 방법을 포함한다.

이 절차가 DCR에 필요한 의미를 정의한다. 실제 문서의 머리말, 절 배치와 링크는 [wf-doc DCR 템플릿](../../wf-doc/references/templates.md#dcr)을 따른다.

`변경 항목`에는 최소한 기존 내용, 변경할 내용, 변경 이유를 기록한다. 코드, 테스트 또는 실행 결과에서 발견한 근거가 있다면 재현 방법과 함께 연결한다.

### C. 변경 분류

- **명확화:** 설계의 의미나 외부 동작을 바꾸지 않고 모호한 설명만 보완
- **설계 변경:** 구조, 책임, 인터페이스, 데이터, 품질 속성 또는 기존 ADR의 결정을 변경
- **요구사항 변경:** 제품 동작, 범위 또는 인수 조건까지 변경

명확화는 설계 변경 기록을 남기고 문서를 갱신할 수 있다. 설계 변경과 요구사항 변경은 사용자 재승인을 받아야 한다.

요구사항 변경도 동일한 DCR 양식과 설계 변경 기록을 사용한다. 이 경우 다음을 추가로 수행한다.

- DCR에 변경 전후의 요구사항과 인수 조건을 포함한다.
- 승인 시 요구사항 명세와 인수 조건을 먼저 갱신한 뒤 설계를 갱신한다.
- 요구사항 명세의 기준선 식별자도 설계 문서와 함께 올린다.

### D. 대안 및 영향 분석

다음 항목을 변경 전후로 비교한다.

- 관련 요구사항과 인수 조건
- 컴포넌트 책임과 의존 관계
- 공개 및 내부 인터페이스
- 데이터 모델과 기존 데이터
- 정상, 실패, 복구 흐름
- 보안, 성능, 안정성, 운영성
- 호환성, 마이그레이션, 롤백
- 테스트 및 관측 방법
- 완료되었거나 진행 중인 구현
- 다른 ADR과 후속 작업

의미 있는 대안이 둘 이상이면 장단점, 위험, 전환 비용을 비교한다. 증거가 부족한 핵심 가정은 제한된 프로토타입이나 테스트로 먼저 검증한다.

### E. ADR 제안 또는 대체

설계 변경이 중요한 기술 결정을 포함하면 ADR을 작성한다.

- 새로운 결정은 새 ADR을 `proposed` 상태로 작성한다.
- 기존 ADR을 변경하는 경우에도 새 ADR 번호를 사용한다.
- 새 ADR의 `대체 대상 ADR`에 이전 ADR을 기록한다.
- 사용자 승인 후 이전 ADR의 상태만 `superseded`로 바꾸고 `대체 ADR`에 새 ADR 링크를 추가한다.
- 이전 ADR의 배경, 대안, 결정, 이유, 결과 본문은 수정하지 않는다.
- 거부된 ADR은 삭제하지 않고 `rejected` 상태와 이유를 남긴다.

### F. 설계 문서 갱신

제안된 결정을 반영하여 설계 문서를 현재 상태 기준으로 갱신한다. 변경된 문장만 고치는 것으로 끝내지 않고 다이어그램, 예시, 계약, 실패 흐름 등 같은 결정을 표현하는 모든 부분의 일관성을 확인한다.

### G. 일관성 및 회귀 검토

- 변경 후에도 모든 요구사항과 인수 조건을 충족하는가?
- 변경과 관계없는 기존 요구사항이 손상되지 않는가?
- 새 ADR과 기존의 유효한 ADR이 충돌하지 않는가?
- 코드, 데이터, 외부 연동에 필요한 전환 방법이 있는가?
- 이미 구현한 부분의 유지, 수정, 되돌리기 판단이 명확한가?
- Workflow 2의 계획과 검증 항목을 어떻게 바꿀지 설명할 수 있는가?

## 4. 설계 변경 기록

설계 문서에는 최신 승인 상태를 반영하고, 별도의 변경 기록에는 DCR 링크, 날짜, 변경 요약, 관련 ADR 링크, 이전·새 기준선, 승인자 및 상태를 누적한다. 필드와 하이퍼링크 표현은 [wf-doc 변경 이력 규칙](../../wf-doc/SKILL.md#3-기존-문서-갱신)을 따른다.

설계 변경 기록은 최소한 무엇이·왜 바뀌었는지, 어떤 증거와 결정에 근거하는지, 누가 언제 승인했는지, 어느 기준선부터 유효한지, 어떤 후속 조치가 필요한지를 추적해야 한다.

버전 관리 시스템을 사용하더라도 커밋 차이만을 설계 변경 기록으로 대신하지 않는다. 코드 차이는 변경 내용을 보여주지만 설계 변경의 이유와 승인 상태까지 설명하지는 않기 때문이다.

## 5. 재승인과 새 기준선

사용자에게 대화형 재승인 요청을 보낼 때는 변경 요청, 변경 사유와 증거, 기존·제안 설계, 관련 ADR, 영향받는 요구사항과 인수 조건, 구현된 코드의 처리, 마이그레이션·롤백, 검증 계획과 남은 위험을 요약하고 이 변경을 새 설계 기준선으로 승인할지 명시적으로 묻는다. 이는 재승인 상호작용의 필수 내용이지 영구 문서의 Markdown 포맷이 아니다.

DCR과 영구 승인 기록의 절 구조는 wf-doc의 [DCR](../../wf-doc/references/templates.md#dcr)과 [승인 기록](../../wf-doc/references/templates.md#승인-기록-approval) 템플릿을 따른다. 대화형 재승인 요청을 파일로 보존할 때도 wf-doc의 `approval` 문서 유형을 적용한다.

사용자는 **승인 / 수정 요청 / 거부 / 보류** 중 하나로 응답한다. 거부되면 기존 설계를 유지하고 ADR 및 DCR에 거부 이유를 기록한다.

승인 시 다음을 함께 수행한다.

1. DCR 상태를 `approved`로 변경한다.
2. 새 ADR 상태를 `approved`로 변경한다.
3. 대체된 ADR 상태와 상호 링크를 갱신한다.
4. 설계 문서의 버전 또는 기준선 식별자를 올린다.
5. 설계 변경 기록에 승인 결과를 추가한다.
6. 요구사항–설계–ADR–검증 추적 정보를 갱신한다.

관련 문서와 기록은 가능한 경우 동일한 커밋에서 변경하여 하나의 설계 기준선으로 식별할 수 있게 한다.

## 6. Workflow 2로 반환

새 기준선이 승인되면 Workflow 2에 다음 정보를 전달한다: 새 기준선과 변경된 문서, 승인된 DCR 및 ADR, 유지할·수정할·되돌릴 구현, 추가하거나 변경할 테스트, 마이그레이션 및 롤백 작업, 재개할 계획 항목과 순서.

무엇을 인계할지는 이 절차가 결정하고, 문서 링크와 인계 블록 형식은 [wf-doc 인계 규칙](../../wf-doc/SKILL.md#27-인계와-재개-지점-작성)을 따른다.

[wf-implement](../../wf-implement/SKILL.md#32-계획-수립)는 기존 계획을 그대로 재개하지 않는다. 변경 영향을 반영하여 계획과 완료 조건을 갱신한 뒤 구현을 재개한다.

설계 변경은 다음 조건을 모두 만족하면 `completed`로 기록한다.

- 새 기준선이 사용자에게 승인되었다.
- 관련 설계 문서와 ADR 상태가 일관되게 갱신되었다.
- Workflow 2의 계획과 검증 항목에 변경이 반영되었다.
- 구현 결과가 새 설계에 일치하는지 검증되었다.
- 필요한 마이그레이션과 통합이 완료되었다.
