# 질문 단계 — 모호성 점검과 질문 발행

[wf-design §2 입력](../SKILL.md#2-입력)과 [§4.1 현재 상태 조사](../SKILL.md#41-현재-상태-조사)가 소유하는 질문 규칙의 본체다. 설계 초안 전에 무엇을 점검하고, 언제 무엇을 묻고, 답을 어디에 적는지 정한다. 결정과 대안은 [REQ-DESIGN-design-questions](../../../docs/work/20261026-design-questions/req-design.md) FR-01~07과 [ADR-020](../../../docs/work/20261026-design-questions/ADR-020-설계-질문과-적대-검토.md)이 정본이다.

## 1. 시점과 적용 범위

정식 경로에서 §4.1 조사를 마친 뒤, 요구사항·설계 초안을 쓰기 전에 수행한다. [경량 경로](lightweight-path.md)에는 적용하지 않는다. 직접 확인할 수 있는 것은 묻기 전에 조사한다(§3.1).

## 2. 모호성 점검

다음 7항목마다 "해석이 둘 이상이고, 어느 쪽을 고르느냐가 결과를 바꾸는가"를 판정한다. 점검은 질문이 0건이어도 의무다.

| 항목 | 판정 질문의 예 |
|---|---|
| 범위 | 포함·제외 경계가 요청에서 갈리는가 |
| 인수 조건 | 관찰할 기대 결과가 둘 이상으로 읽히는가 |
| 실패 시 기대 동작 | 오류·중단·부분 성공에서 무엇을 해야 하는지 정해졌는가 |
| 보안 | 권한·비밀·공격면이 선택에 따라 달라지는가 |
| 데이터 | 형식·보존·이전이 선택에 따라 달라지는가 |
| 공개 인터페이스 | 호출자가 보는 계약이 선택에 따라 달라지는가 |
| 호환성 | 기존 사용자·환경이 선택에 따라 깨지는가 |

판정 결과는 질문 절에 한 문단으로 남긴다 — 항목별로 질문 ID 또는 `해당 없음(이유)`.

## 3. 질문 발행

점검에 걸린 항목만 질문으로 올린다. 결과를 바꾸지 않는 차이는 가정으로 적고 진행한다 — 과잉 질문은 해결률을 떨어뜨리고 비용을 늘린다.

- **필드:** 질문, 선택지(가능하면 2지선다), 권장안, 근거. 권장안은 답이 없을 때의 기본 가정이다.
- **표:** [wf-doc 요구사항 템플릿](../../wf-doc/references/templates.md#요구사항-requirements)의 질문 표 골격(6열)을 쓴다. 식별자는 기존 항목 ID `Q-NN`이며 새 계열이나 별도 등록부를 만들지 않는다.
- **순서와 수:** 결과에 미치는 영향이 큰 순으로 정렬한다. 수 상한은 두지 않는다.

## 4. 질문 없음

질문이 0건이면 질문 절에 `질문 없음 — <점검 항목과 이유>` 한 줄을 남긴다. 이유 없는 "질문 없음"은 점검을 하지 않은 것과 같다.

## 5. 묻는 시점

기본은 설계 초안 전이다. 답을 반영한 뒤 초안을 쓴다.

예외: 선택지마다 바뀌는 FR·NFR·DES·AC 행을 근거 칸에 `영향:`으로 열거할 수 있고, 어느 선택지도 구조(컴포넌트·계약)를 바꾸지 않으면, 권장안으로 초안을 쓰고 승인 관문에서 함께 물을 수 있다. 구조를 바꾸는 질문은 초안 전에 묻는다.

## 6. 답 반영

사용자 답은 질문 표 `답` 칸에 인용과 일자로 적는다. 승인 관문에서 받은 답은 승인 기록과 같은 응답 인용 규칙([approval-request §4](approval-request.md#4-승인-기록의-응답-인용))을 따른다. 답이 권장안과 다르면 영향 행을 고친 뒤 승인을 기록한다 — 구조가 바뀌면 승인 요청을 다시 한다.

## 7. 구현 중 질문

구현 중 인수 조건·설계가 둘 이상으로 해석되면 추측해 구현하지 않고 멈춘다. 절차는 [design-change §2](design-change.md#2-변경-시작-조건)를 따른다.
