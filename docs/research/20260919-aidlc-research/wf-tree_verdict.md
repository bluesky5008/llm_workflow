# wf-tree 존치 판단 — 계획 수립·시각화 논문 근거

> 질문: "개발 플로우의 플랜을 수립하고 시각화하는 것(wf-tree)은 근거 있는 행위인가, 제외해야 하는가?"
> 방법: wf-tree를 기능 5개로 분해하고, 각 기능에 대해 2025–2026 실증 논문의 찬성·반대 근거와 저장소에서 측정한 비용을 대조. 작성 2026-08-27.

---

## 0. 결론 먼저

**wf-tree는 "전부 존치"도 "전부 제외"도 근거에 맞지 않는다.** 기능별로 갈린다.

| wf-tree 기능 | 근거 판정 | 권고 |
|---|---|---|
| ① 계획 구조화 — 작업 분해, `상위:`, `depends:` DAG | **찬성 근거 강함** (4편 실증 + 1편 서베이) | 존치. 오히려 의존 복원을 강제하는 절차를 보강 |
| ② 진행 상태 추적 — pending/in-progress/completed, 롤업 | **찬성 근거 강함** (3편 실증) | 존치 |
| ③ 사람용 시각화 — ASCII/Mermaid 렌더링 | **"보이는 계획"은 찬성 근거 있음. 그러나 "트리 다이어그램 > 체크리스트"를 보인 논문은 없음** | 온디맨드로 전환. 매 갱신 자동 재생성은 제외 |
| ④ 에이전트용 시각화 — 트리를 컨텍스트에 넣는 것 | **근거 없음 + 비용 근거 있음** | 제외 (같은 정보의 3중 표현) |
| ⑤ 분기 템플릿 — implement 노드마다 test·review 자동 제안 | **혼재** — 비가역 게이트는 찬성, 일반 절차 자동 추가는 반대 근거 | 필수 게이트(approve·release·migrate)만 남기고 나머지 제외 |

한 줄로: **계획 모델은 남기고 렌더링 층을 뺀다.** 시각화 관심 자체는 정당하나, 그 가치는 "에이전트가 매번 그리는 산출물"이 아니라 "사람이 필요할 때 목록에서 뽑아 보는 뷰"에 있다는 것이 근거의 방향이다.

---

## 1. 근거 요약 — 논문별

### 1.1 계획 구조화(분해·DAG)는 도움이 되는가

| 논문 | 설정 | 결과 | wf-tree ①에 대한 함의 |
|---|---|---|---|
| **Beyond Entangled Planning / Task-Decoupled Planning** (Li 외, 2026.1, [2601.07577](https://arxiv.org/html/2601.07577v1)) | Supervisor가 과제를 **의존 추적이 있는 서브골 DAG**로 분해, 실행기는 활성 서브태스크로 컨텍스트 한정 | TravelPlanner·ScienceWorld·HotpotQA에서 베이스라인 상회, **토큰 최대 82% 절감**. 재계획을 활성 노드에 국한해 오류 전파 차단 | wf-tree의 "부모-자식=분해, depends=순서" 분리와 같은 모델. 찬성 |
| **LoopsBench** (Microsoft 외, 2026.7, [2608.00267](https://arxiv.org/html/2608.00267v1)) | 112 태스크·5,300 유닛 의존 DAG, 장기 개발 | 병목은 "loop state discipline". 기록된 계획의 **의존 간선 F1 0.71**(최고)·0.27–0.39(오픈소스) — 계획이 실제 선행 DAG의 일부만 복원 | 계획에 의존을 적는 것 자체가 부족한 게 아니라 **복원 정확도**가 병목. wf-tree의 `depends:`는 표현 장치일 뿐 복원을 강제하지 않음 → 보강 대상 |
| **Evaluating Plan Compliance** (Liu 외, 2026.4, [2604.12147](https://arxiv.org/html/2604.12147v1)) | SWE-agent 16,991 궤적, 4 모델, 계획 변형 8종 | 표준 계획(navigate→reproduce→patch→validate)은 **성공률을 높임**. 그러나 **"초기 단계에 태스크 특화 단계를 덧붙이면 성능 저하"**. 계획 준수율은 성공과 상관 | 계획은 찬성. 단 계획을 두껍게 하는 것은 반대 → ⑤ 분기 템플릿에 경고 |
| **Do Agents Need to Plan Step-by-Step?** (Megagon, 2026.5, [2605.08477](https://arxiv.org/html/2605.08477v1)) | 전체 계획 선행(FH) vs 단계별(SH) | 정확도 동등, FH가 **입력 토큰 2–3배 절감**(도구 많으면 4.7배). "eager step-wise monitoring is often unnecessary" | 선행 계획(wf-implement §3.2) 찬성. 매 단계 재계획·재렌더는 불필요 → ③④에 반대 방향 |
| **Learning When to Plan** (Paglieri 외, ICLR-계열, [2509.03581](https://arxiv.org/abs/2509.03581)) | 항상 계획 vs 안 함 vs 동적 | "항상 계획은 비용이 크고 **장기 과제에서 성능을 깎는다**", 안 하면 능력 제한. 동적 계획이 최선이고 **사람이 쓴 계획으로 유도하면 단독보다 높음** | 계획 존재 찬성, 매 행동마다 계획 갱신 반대. 사용자 승인 계획이 에이전트를 유도한다는 점은 wf-design→plan 구조 지지 |
| **The Horizon Gap** 서베이 (2026.7, 1,547편, [2608.06663](https://arxiv.org/html/2608.06663)) | — | DAG·계층 분해는 오류 전파 방지에 유효. 단 **"더 정교한 분해는 그 자체로 지침과 실행 필요 사이의 불일치를 만들 수 있다"**. 단일 우세 방식 없음 | 분해 깊이에 상한이 필요. wf-tree "깊이 제한 없음"과 긴장 |

**판정: ①은 찬성 근거가 강하다.** 반대 근거는 "계획 자체"가 아니라 "계획의 과잉(깊이·장식·재계획 빈도)"에 대한 것이다.

### 1.2 진행 상태 추적은 도움이 되는가

| 논문 | 결과 | 함의 |
|---|---|---|
| **Push Your Agent / PushBench** (Cai 외, 2026.5, [2605.23574](https://arxiv.org/html/2605.23574v1)) | 명시적 상태 추적 없는 표준 컨트롤러: 중간 목표 **성공 ~30%, 중복 제출 55–88%**. 상태 추적(StateQGP): **69–78%, 중복 0**. 검증 게이트만으로는 회복 안 됨. Claude Code·Codex CLI도 100개 규모에서 3/9로 하락 | 진행 상태를 외부 산출물로 두는 것이 모델 개선 없이 신뢰성을 바꿈. wf-tree ②·wf-implement §3.2 상태 전이 직접 지지 |
| **Subgoal-driven Framework** (DeepMind, 2026.3, [2603.19685](https://arxiv.org/html/2603.19685v1)) | 실패의 **~45%가 중간에 멈춤**. 서브골 생성이 **진행 지표로 AUROC 0.84** | 완료/미완료 서브골 목록은 "어디까지 왔나"의 신뢰할 수 있는 신호 |
| **SKILL.md Smells** (2607.01456) | "No Progress Tracking"이 **냄새**(71%가 보유) — 다단계 워크플로우에 진행 추적 없음을 결함으로 분류 | 베스트프랙티스 문헌 29종이 진행 추적을 요구 |
| LoopsBench | "Context-budget renewal does not remove regression pressure" — 워커 복귀 시 완료 의무의 명시적 추적 필요 | 세션 인계 시 상태 목록이 필수 |

**판정: ②는 찬성 근거가 강하다.** 단, 근거가 지지하는 형태는 전부 **목록(체크리스트·상태 필드)** 이지 트리 다이어그램이 아니다.

### 1.3 사람용 시각화 — "보이는 계획"이 감독을 돕는가

| 논문 | 설정 | 결과 | 함의 |
|---|---|---|---|
| **Cocoa** (Feng 외, CHI 2026, [2412.10999](https://arxiv.org/html/2412.10999v4)) | 편집 가능한 단계별 계획(상태: 미실행/진행/완료/입력필요)을 문서 안에 표시 vs 같은 에이전트의 채팅 UI. 연구자 16명 within-subjects | **조종성 4 vs 3 (p=.005)**, 사용 용이성 동일. 능동적 공동 실행 시간 15.2% vs 3.1%, **출력 검사 시간 33.6% vs 54.1%**. "채팅 기록을 뒤지는 대신 계획으로 돌아가서 다시 시킨다" | 보이는 계획+상태는 사람의 개입 지점을 만들고 검토 부담을 줄임. 형태는 **체크리스트 형태의 목록** |
| **Plover** (2026.7, [2607.15193](https://arxiv.org/html/2607.15193v1)) | 계획을 "persistent, inspectable, revisable artifact"로 외재화한 GUI 에이전트. 형성 연구 6명 | 자율 실패 26건 중 **23건(88%) 복구**, 평균 개입 2.04회. 사용자는 "불투명한 계획과 조용한 적응"에 어려움 | 계획 외재화 찬성. n=6 형성 연구라 근거 강도는 낮음 |
| **Human oversight of agentic systems in practice** (Microsoft, 2026.6, [2606.05391](https://arxiv.org/html/2606.05391v1)) | 숙련 개발자 17명 인터뷰 | 감독 활동 4종 중 **공동 계획(co-planning)** 이 사후 검토 부담을 줄이는 핵심. **실시간 모니터링은 거의 하지 않음** — 실행 시간 같은 간접 단서로만 드리프트 감지. 휴리스틱: "계획을 실제 실행의 충실한 대리물로 취급" | 시각화 가치는 **계획 시점과 재개 시점**에 집중, 실행 중 지속 관찰용은 아님. 또 "계획=실행"이라는 가정은 위험 휴리스틱으로 분류됨 → 트리 상태가 실제 코드 상태와 어긋날 때의 위험 |
| **Position: Humans are Missing from AI Coding Agent Research** (CMU/Stanford/Princeton, 2026.7, [2608.12355](https://arxiv.org/html/2608.12355)) | 입장 논문 | 실제 병목은 자율 완수가 아니라 협업. "계획이 확정된 뒤 수락/거부 이분법만 강요" 하는 시스템이 문제 → 의미 있는 결정 지점에서의 조종성 필요 | 계획 가시성 찬성. 단 wf-tree보다 wf-design 승인 관문·DCR이 이 요구에 더 직접 대응 |
| **Agent Plans in OSS** (ESEM 2026, [2608.04661](https://arxiv.org/html/2608.04661v1)) | 36,710 리포 중 `.claude/plans`·`.cursor/plans` 85개 파일 | 계획 파일 중앙값 178줄. **78/85가 커밋 1회 후 미수정**, 이슈·PR에서 참조 거의 없음. **계획이 결과(머지·리버트)에 미치는 영향은 미검증** — "가장 시급한 열린 질문" | 현장에서 계획 산출물은 만들어지지만 **살아있는 문서로 유지되지 않음**. 성과 효과는 아직 아무도 측정 못함 |

**판정: "보이는 계획+상태"는 사람 쪽에서 찬성 근거가 있다(Cocoa가 가장 강함). 그러나 다음 두 가지는 어느 논문도 보이지 않았다.** (a) 트리/다이어그램이 평면 체크리스트보다 낫다는 것, (b) 계획 시각화가 최종 코드 품질을 높인다는 것. Cocoa의 계획은 상태가 붙은 단계 목록이고, 감독 인터뷰는 실시간 관찰이 드물다고 했다. 즉 근거가 지지하는 것은 **"승인 시점과 재개 시점에 읽을 수 있는 상태 있는 목록"** 까지다.

### 1.4 에이전트용 시각화 — 트리를 컨텍스트에 두면 에이전트가 나아지는가

- 직접 실험한 논문은 **찾지 못했다.** "Does the Way You Plan Matter?" ([2605.29927](https://arxiv.org/html/2605.29927v1))는 계획 표현 4종(순차 서브골·체크리스트·의사코드·서술)을 비교했는데 **모델마다 최적 표현이 다르고 단일 우세 없음** — 그래프/다이어그램 형식은 비교 대상에 없었다. MermaidSeqBench([2511.14967](https://arxiv.org/html/2511.14967v1))는 생성 방향만 다룬다.
- 반대 방향 근거는 있다. 1차 보고서의 세 논문(TDAD·AGENTS.md·Skills Harmful)이 보인 것은 "규칙·장식 텍스트는 컨텍스트를 밀어내고 비용을 올린다"였고, Skills Harmful의 효율 저하 분류 중 Heavy Implementation Pipeline(16.5%)은 "산출물 하나에 여러 변환 단계를 의무화"하는 패턴이다. wf-tree는 **같은 항목 목록을 ASCII와 Mermaid로 두 번 더 그리고 상태 갱신마다 재생성**하므로 이 패턴에 해당한다.

**판정: ④는 찬성 근거 없음, 반대 근거 있음.**

### 1.5 분기 템플릿 — 노드 유형별 자식 자동 제안

- 찬성: AI-DLC 2026의 backpressure·비가역 작업 게이트, 감독 인터뷰의 "a priori control". `release`·`migrate`·`approve` 같은 **비가역 관문을 빠뜨리지 않게 하는 것**은 근거 있음.
- 반대: Plan Compliance는 "태스크 특화 단계를 계획에 덧붙이면 성능 저하", Skills Harmful은 "템플릿·체크리스트가 필수 작업으로 둔갑(과잉 절차 62.6%)". wf-tree §4는 `implement` 노드마다 `test(선행)`+`review`를 제안하는데, 이는 wf-implement §3.3·§3.5가 이미 규정한 것의 **중복 표현**이라 정보를 더하지 않고 노드 수만 늘린다.

**판정: ⑤는 필수 게이트만 존치.**

## 3. 종합 판정과 권고

**존치할 것 (근거 강함)**
- 계획 목록의 `상위:`(분해)·`depends:`(순서) 필드와 상태 전이. 이것은 wf-tree가 아니라 wf-doc plan 템플릿에 이미 있는 **단일 원천**이며, TDP·LoopsBench·PushBench가 지지하는 실체다.
- 세션 재개 시 "활성 경로만 보기"라는 목적. 감독 인터뷰·LoopsBench가 재개 지점의 상태 가시성을 요구한다.

**제외하거나 온디맨드로 바꿀 것 (근거 없음 + 비용 있음)**
- 상태 갱신마다 ASCII·Mermaid 자동 재생성(§7 갱신 시점). FH 계획 논문·Learning When to Plan이 "매 단계 갱신"을 비용으로 봄.
- Mermaid 매체. ASCII와 정보가 같고, 에이전트 쪽 효과 근거가 없다. 사람이 그림을 원할 때만 생성.
- 완료 사이클 트리 스냅숏 의무(8–9KB/사이클). 계획 목록이 정본이면 스냅숏은 git 이력에서 재구성 가능하므로 wf-implement §7 불변식("git으로 재구성 가능한 내용은 간결하게")과도 충돌한다.
- `implement`→`test`+`review` 자동 제안. 필수 게이트 3종(approve·release·migrate 검증)만 유지.

**보강할 것 (근거가 지목한 실제 병목)**
- 의존 복원 절차: 파일 겹침·심볼 참조로 `depends:` 후보를 검출하는 자기 검토(LoopsBench 근거 패턴). 이것이 "트리를 그리는 것"보다 계획 품질에 직접 닿는다.
- 분해 깊이 상한(Horizon Gap의 과분해 경고). 예: 작업 내부 2단계.

**시각화 관심을 살리는 방식**
- 렌더링을 스킬 규칙이 아니라 **스크립트**로 옮긴다(`skills/wf-tree/scripts/render.py`: plan.md 목록 → ASCII/Mermaid). Smells의 Missing Utility Script 권고와 wf-tree 자신의 단일 소스 원칙에 부합하고, 에이전트가 손으로 재렌더하는 토큰·드리프트를 없앤다. 사람은 원할 때 실행해서 본다.
- 결과적으로 wf-tree SKILL.md는 "필드 규칙 + 게이트 3종 + 스크립트 호출"로 줄어 wf-doc plan 템플릿의 부록 수준이 된다.

**이 판단의 한계**
- 트리 vs 체크리스트를 사람 대상으로 직접 비교한 실험은 없다. Cocoa는 목록형이었고, 트리가 더 나쁘다는 증거도 없다. 따라서 "렌더링 제외"는 **효과 근거 부재 + 비용 근거 존재**에 의한 판단이지, 해롭다는 증거에 의한 판단이 아니다.
- 계획 산출물이 최종 코드 품질에 미치는 영향은 ESEM 2026 논문이 말하듯 아직 아무도 측정하지 않았다. 사용자 저장소에서 "트리 유/무" A/B(재개 정확도·의존 누락 건수)를 돌리면 그 자체가 현재 문헌에 없는 데이터가 된다.
