# 1. Reversa 심화 — 역공학 절차 대조

## 1.1 6역할 파이프라인과 산출물

scout(인벤토리) → archaeologist(모듈 분석) → detective(비즈니스 규칙·gap) → architect(아키텍처·영향 매트릭스) → writer(requirements/design/tasks.md·추적성) → reviewer(신뢰도 보고·질문·잔여 gap). 인계는 파일 기반(`_reversa_sdd/` 산출물 + `.reversa/` 실행 상태). 각 역할의 프롬프트 내부 구조는 본문에서 확인 못함.

## 1.2 Claim-증거 모델과 신뢰도 지수 (재확인 완료)

- Claim은 정형 객체가 아니라 문서 내 서술적 단언이며, 원칙은 "모든 관련 claim은 파일·모듈·라우트·스키마·쿼리 등 레거시 증거로 추적 가능해야 한다". 행 범위 명시 여부·인라인 태그 문법은 확인 못함.
- 3단 분류: confirmed(직접 증거) / inferred(패턴·이름·흐름 — "확실성으로 서술 금지") / gap(인간 검증 필요).
- 지수: **confirmed 1.0 + inferred 0.5 (gap 0)**, ATM 사례 (490+24×0.5)/517 ≈ 97.1%. **모듈별로 계산**(menu·conta·extrato·util·kbdread). 결정적 단서: "이 지수는 파이프라인이 부여한 분류의 요약일 뿐, claim에 대한 외부 감사가 없었으므로 **사실적 정확도로 해석해서는 안 된다**."

**사용자 절차와의 필드 단위 대조.** EV→OBS→RR→RD의 3단 분리(증거→관찰→해석)는 Reversa의 증거→claim 2단보다 사실·해석 오염을 잘 막는다. 5단 신뢰도는 Reversa 3단에 없는 **conflicting을 독립 범주로** 갖고, inferred를 strongly-inferred/tentative로 쪼개며, **반증 조건 기록 의무**는 Reversa에 대응물이 없다.

## 1.3 Gherkin 패리티와 ATM 사례의 실상 (재확인 완료)

- 53개 시나리오(로그인·잔액·출금·입금·이체·내역·통화 포맷·키 마스킹)는 Migration 단계 산출. **시나리오 전문 인용·도출 경로·claim 역링크는 본문에 없음.**
- 패리티 = 레거시(COBOL)와 신규(Go)의 교차 실행 검증인데, **연구 종료 시점에 "in progress"** — 즉 53개 시나리오는 실행된 검증이 아니라 실행 예정인 계약이다. 사용자 어휘로는 "실행하지 못한 검증".
- gap 처리: 심각·중간 5건은 문서화된 인간 결정으로 해소, 3건 잔존, 2건 범위 제거. tasks.md 11개 중 9 완료 / 1 진행(패리티) / 1 미착수(컷오버).
- 한계(저자 명시): 통제 비교 없음(단일 에이전트·통상 문서화 대비), claim 정확도 외부 검증 없음, 교육용 단일 사례, 재구성 미완 상태의 보고.

## 1.4 S14 보강안 — 가져올 3가지, 지킬 6가지

**가져올 것 (reverse-engineering.md 편집 초안):**

1. **시나리오 초안 인계** — §8 확장:
> 인계할 때 외부에서 관찰할 수 있는 동작은 가능한 범위에서 전제·행위·기대 결과(Given/When/Then) 형식의 시나리오 초안으로 표현한다. 각 시나리오 초안에는 근거가 되는 `RR`·`EV` 식별자와 신뢰도를 명시하고, `confirmed`가 아닌 시나리오는 특성화 후보이지 확정 대상이 아님을 표시한다. 시나리오 초안은 실행 가능한 테스트가 아니라 특성화 대상 선정 자료이며, 테스트로의 전환·실행·성공 판정은 wf-implement가 소유한다.

   (wf-implement §3.3에는 "시나리오 초안이 있으면 이를 우선 사용한다" 한 줄 추가. Reversa의 교훈 — 미실행 패리티가 지표와 함께 보고됨 — 을 반영해, 미실행 시나리오를 검증 완료로 기록하지 않는 §2.5 원칙 적용을 명시.)

2. **문서 단위 신뢰도 집계(보조 지표)** — §5 보조 절:
> 인계 문서에는 문서 단위 신뢰도 요약을 기록할 수 있다. `RR`·`RD` 항목을 신뢰도별로 집계하고, 필요하면 가중 합산 비율을 병기한다: `confirmed` 1.0, `strongly-inferred` 0.75, `tentative` 0.5, `conflicting` 0, `unknown` 0. 이 비율은 검토 우선순위 배정용 보조 지표이며, 항목별 신뢰도 범주·반증 조건을 대체하지 않고, 사실적 정확도의 측정값으로 해석하지 않는다.

   (Reversa 3단과의 차이: conflicting을 0으로 **별도 계상**해 충돌 증거가 지수를 끌어내리게 함. "외부 감사 없음" 경고문을 규칙 본문에 그대로 옮김.)

3. **추적표에 spec-impact 열** — 단계 15 확장:

| 항목 ID | 근거 사슬 | 신뢰도 | 영향 코드 | 영향 산출물·시나리오 |
|---|---|---|---|---|
| RR-03 | EV-05 → OBS-04 | strongly-inferred | `src/account.cob` | 시나리오 초안 S-07, GAP-02 |

   (이 항목이 승인에서 기각·수정되면 무효화되는 해석·시나리오·후속 항목을 적는 역방향 열. 논문은 매트릭스 이름만 제공 — 형식은 자체 설계이며 wf-doc 식별자 규칙을 따름.)

**지킬 것(이관 금지):** 5단→3단 축소 금지, 반증 조건 폐기 금지, OBS 층 제거 금지, RR/RD→FR/DES 승인 관문 우회 금지, 항목 단위 숫자 점수 도입 금지, 미실행 검증의 성공 기록 금지 원칙 유지.

# 2. Security Debt 정밀 분석

## 2.1 방법 (재확인 완료)

AIDev의 5개 에이전트(Copilot·Codex·Claude Code·Cursor·Devin) PR 4,022건 / 파일 변경 16,112건. **범위가 좁다**: 고위험 경로(CI 정의·컨테이너·IaC·설정·셸·노트북)의 **추가된 줄만** — 락파일·vendor 제외. 판정은 오픈 모델 2종(Qwen3.6-35B·Gemma-4-26B, temp 0.1)의 합집합, 골드 376건 대비 **정밀도 0.908 / 재현율 0.775 / F1 0.836**(κ 0.789). 분류는 CWE가 아닌 자체 6범주(OWASP·CIS 기반).

## 2.3 권고의 구체성과 한계

권고는 방향 수준("인간-AI 협업 지점의 context-aware 가드레일", "라이브 자격증명의 최초 주입 예방") — pre-commit·PR 봇·핀 강제 같은 구체 메커니즘 **없음**. 한계: 재현율 0.775(보고치는 하한), 심각도 기준표 부재(모델 재량), 오픈소스 한정, 시크릿 분석은 74건 소표본.

## 2.4 S16 설계 — 보안 게이트

**(a) §3.4 배치 (S3 검증 깊이 표와 결합).**
- **시크릿 스캔 = 1단계(정적 분석)에 상시 편입, 전 열 필수** — critical의 99.6%인데 리뷰가 81.1% 놓침 → "위험 비례" 대상이 아니라 상수 비용 상시 검사. 경량 경로 열에서도 필수.
- **공급망 핀 검사 = 5단계(보안 비기능), 경로 트리거 조건부** — diff가 `.github/workflows/**`·`Dockerfile*`·`*.tf`·셸을 건드릴 때만(smell의 87.6%가 이 두 파일군이므로 경로 트리거로 대부분 커버). §3.5 보안 블록에 "CI·컨테이너 변경 시 action SHA 핀·이미지 태그 고정 확인" 항목 추가.

**(b) Stop 게이트(quality-gates.md) 구체 명령 (Windows, 묶음 B 훅과 결합):**

```text
```gates
secrets = gitleaks git --staged --no-banner --redact --exit-code 2
actions-pin = powershell -c "exit [int]([bool](Get-ChildItem .github\workflows -Filter *.yml -Recurse -EA SilentlyContinue | Select-String 'uses:\s*[^\s@]+@(?![0-9a-f]{40})'))"
docker-tag = powershell -c "exit [int]([bool](Get-ChildItem -Recurse -Filter Dockerfile* -EA SilentlyContinue | Select-String ':latest'))"
```
```

운용 규칙: 도구 미설치는 경고 후 통과(fail-open 유지). **gitleaks 탐지만 block**, 오탐 72.8% 문제는 `.gitleaks.toml` allowlist(테스트 픽스처·플레이스홀더 패턴)로 흡수하고 `--redact`로 게이트 출력의 재유출 방지. 핀 미고정은 리마인더로 시작 → 오탐률 실측 후 block 승격. 심각도는 모델 재량이 아니라 규칙 고정(시크릿=critical, 핀 미고정=major).

**(c) 67.6% 인간 유입의 함의 — 3계층 배치.** 에이전트 세션의 Stop 게이트는 유출 경로의 ~1/3만 막는다. 같은 `.gitleaks.toml`을 **① Claude Stop 훅 ② 저장소 pre-commit 훅(인간·에이전트 공용) ③ CI/서버측 push protection**의 3계층이 공유해야 하며, 단일 설정 파일 공유가 규칙 드리프트를 막는 핵심이다.

**(d) 팀 메모리(묶음 C) 결합.** 메모리 항목 저장 전 동일 gitleaks 규칙으로 입력 위생(작업 기록 발췌의 재유출 방지 — SAP 보안 게이트와 동일 지점), 게이트가 잡은 smell을 6범주 라벨로 메모리에 적재해 반복 패턴을 계획 단계 선행 확인 사항으로 환류.

**(e) 측정.** 도입 전: 최근 병합 PR ≥50건에 소급 실행해 기저율(38.9%·82.3%·27.2% 곡선과 비교). 도입 후 4주+: block 발생률과 오탐률(allowlist 추가 건수), 병합 시점 잔존 smell율, 인간 vs 에이전트 커밋 탐지 분리 집계(67.6% 재현 여부 = 3계층 투자의 직접 근거). 재현율 0.775이므로 자체 수치도 하한임을 명시.
