## 0. 이번 독해로 바뀐 판정 — 1차 보고서 정정 3건

1. **Lengthy Skill Body 아님.** 실측 어절 수: wf-implement 3,309 / wf-doc 3,195 / wf-design 2,332 / wf-tree 2,077 — 논문 임계 5,000단어 미만. **다이어트의 논문 측 근거는 LSB(길이)가 아니라 UD(위임되지 않은 세부)다.** 판정 축은 "길이"가 아니라 "위임 가능한 저수준 세부의 존재"이며, 그래서 짧은 wf-tree도 UD에 해당하고, 긴 경계표는 판단 규칙이므로 UD 근거가 아니다.
2. **Rationalization Loophole 아님 확정.** "생략하지 않는다", "판단이 애매하면 정식 경로/중대한 변경", "실패한 검증을 제외하여 전체 성공으로 보고하지 않는다" 류 가드가 스킬당 11–23회 존재. 94% 기저율과 반대편. **이 가드 문장들은 다이어트 시 references로 옮기면 안 되는 본문 잔류 대상이다.**
3. **Series of Commands 완화.** §3.4 6단계는 고정 순서지만 "위험에 비례"·예외·대체 경로가 명시되어 적응 여지가 있음 — 경계선상. (S3 검증 깊이 표가 들어가면 완전 해소.)

또한 냄새 검출기의 성능은 가중 F1 0.78·정밀도 0.79·재현율 0.78(53파일 2인 라벨링 검증)이므로, **개별 파일 판정은 오탐·미탐을 전제**해야 한다. 논문 표본은 영어 스킬만이라(비영어 9,830개 제외) 한국어 스킬은 표본 밖이고, 5,000단어 임계가 한국어 어절과 등가인지는 다루지 않는다.

## 1. Codified Context — 계층 배치의 원리

### 1.1 시스템

단독 개발자가 AI 에이전트만으로 108,256 LOC C# 분산 시뮬레이션을 70일·283 세션에 개발한 관찰 연구. 지식 인프라 총량 = 코드베이스의 **24.2%**(54파일 ~26,200줄): 헌법 0.6% + 에이전트 명세 8.6% + 명세 문서 15.0%.

### 1.2 Tier 1 헌법(~660줄)의 내용과 배제 기준

내용 목록(원문): "code quality standards, naming conventions, build commands, architectural pattern summaries **with references to detailed specifications in Tier 3**, checklists for common operations, **known failure modes**, and orchestration protocols."

배제 기준은 단 하나 — **간결성**: "헌법은 과도한 컨텍스트 소비 없이 모든 세션에 전부 들어가야 한다. 상세한 서브시스템 문서는 Tier 3에 두고 링크로 참조한다." 역할 분리: 헌법은 "항상 따라야 하는 규칙이 무엇인가?", Tier 3는 "서브시스템 X가 세부적으로 어떻게 동작하는가?"에 답한다.

### 1.3 강제 트리거 — 이 논문의 가장 중요한 이전 가능 항목

콜드 계층은 저절로 읽히지 않는다. 헌법이 **명령한다**: "the constitution requires the orchestrator to consult the trigger table before changes, and requires use of suggest_agent(task_description) when exploring unfamiliar code." 결과: MCP 검색 1,478회, 283 세션 중 218 세션이 지식 베이스 접근. 트리거 표는 파일 패턴/신호 → 에이전트 라우팅("Network, sync" → network-protocol-designer).

### 1.4 그 외 이전 가능한 관찰

- Tier 2 명세(19개, 115–1,233줄)의 **절반 이상이 행동 지시가 아니라 도메인 지식**. 에이전트 신설은 사전 설계가 아니라 실패 관찰 기반("특정 도메인 디버깅이 해결 없이 긴 세션을 소모하면 전문 에이전트를 만드는 편이 빨랐다").
- **지식 공백 감지**: 드롭 시스템 문서 검색이 0건 → "null 결과 자체가 정보였다" → 명세를 먼저 만들고 리팩토링 진행.
- 한계: 관찰 연구·통제 비교 없음·단일 개발자·특수 도메인. "개발 속도나 코드 품질 개선을 통계적 엄밀성으로 정량화할 수 없다."

### 1.5 환경 차이 주의 4가지

1. **강제 로드 부재가 최대 위험.** 논문은 MCP 도구 + 헌법 명령으로 콜드 접근을 보장한다. 사용자 환경에서 references/는 모델이 하이퍼링크를 따라가기로 *선택*해야 읽힌다. → 이관 시 본문에 논문식 강제 문구("X를 할 때는 references/Y를 읽는다")가 없으면 **이관은 사실상 삭제다.**
2. 논문의 24.2%는 프로젝트 고유 사실의 축적 결과. 사용자 스킬은 범용 절차 규칙이라 내릴 것은 주로 표현 형식(템플릿·렌더링·체크리스트)이다. 비율을 목표치로 오독하지 말 것.
3. 논문 Tier 2는 별도 컨텍스트의 서브에이전트라 915줄 명세도 메인 세션을 오염시키지 않는다. 사용자의 스킬 4개는 같은 세션에 동시 로드되므로 **간결성 제약이 논문보다 엄격**해야 한다.
4. 처방이 아니라 "일관성 열화를 늦춘 한 사례"의 설계 원리 이전이다. 이관 후 references가 실제로 읽히는지 관찰하며 조정한다(§6 실험).

## 2. Smells 심화 — 판정 기준의 정밀화

### 2.1 판정 방법

26개 냄새 = MLR 29개 소스의 모범 관행 26개를 역전. 정적 5종(본문 5,000단어, name 64자, description 1,024자, 백슬래시 경로, description 내 XML)은 룰 기반; 의미적 21종은 Qwen3.6-27B(4-bit)에 정의+양성/음성 예시를 주고 판정. 검증 F1 0.78. 238개 중 무결 파일 1개, 평균 10.5개.

### 2.2 다이어트 직결 냄새 6종의 정밀 기준과 재판정

| 냄새 | 정밀 기준 | 사용자 스킬 재판정 |
|---|---|---|
| UD (46%) | 저수준 구현 세부를 참조 문서·스크립트로 위임하지 않음. **정량 임계 없음 — 위임 가능성이 축** | wf-doc: templates.md로 위임했으나 머리말 코드블록·문서 연결 표·식별자 문법이 본문 잔존. wf-implement §7 세칙, wf-tree §7 세칙 해당. **경계표는 판단 규칙이라 UD 아님** |
| RL (94%) | 필수 단계 건너뛰기를 막는 지침 부재 | **비해당 확정** (가드 11–23회/스킬). 가드는 본문 잔류 |
| BG (81%) | 권장 gotcha 헤더로 치명 경고를 부각하지 못함 | **4/4 해당** — 경고가 산문에 산재, 전용 경고 절 없음. `> **정본:**` 콜아웃뿐 |
| MUS (66%) | 스크립트가 더 잘할 작업에 스크립트 부재 | wf-tree 렌더 재생성·분할, wf-doc 링크·앵커 검사 해당. scripts/ 0개 |
| SOC (62%) | 순서 고정으로 적응 차단 | 경계선상 — 예외·비례 단서 있음 |
| LSB (~0%) | 5,000단어 초과 | **비해당** (최대 3,309어절) |

### 2.3 종단 분석이 주는 규칙

142개 스킬·1,199 커밋 추적: **"한번 들어온 냄새는 이후 개발에서 거의 제거되지 않는다."** 제거 사례의 패턴은 본문에 없음(지속성만 보고). 도출:
- 유일하게 검증된 개입 지점은 **도입 시점 차단**(커밋 전 린트).
- 다이어트는 일회성 이벤트다. 이후 "본문에 한 줄만 추가" 커밋이 UD를 재도입한다 → "절차 세부·표기 세칙·템플릿은 references/에만 추가한다"를 저장소 규칙으로 명문화.
- 본문 어절 상한(제안: 2,000어절 경고)으로 성장 추세를 감시.

### 2.4 컴포넌트 지도에서 나온 부수 발견

13개 컴포넌트 중 기존 가이드(29개 소스)가 커버하지 않는 6종은 Introduction·Evaluation·Tools·MCP Integration·Agent Architecture·Other. 사용자 스킬은 그중 **Introduction(적용 시점·경량 경로)과 Evaluation(자체 검토)을 이미 갖췄다** — 가이드 부재 속에서 확보한 강점이므로 본문 유지 가치가 있다. 빈약한 것: wf-implement의 Usecase(예시 0개 — 1차 보고서의 ME 판정과 일치), Tools(단계별 허용/금지 도구 목록).

### 3.3 강제 트리거 문장 초안 (이관의 성패를 가르는 부분)

논문의 "requires the orchestrator to consult the trigger table before changes"를 본떠, 조건+명령 형태로 본문에 남긴다. 기존 문체 유지:

- (wf-implement §3.5 자리) "구현을 마치고 자체 리뷰를 시작할 때는 [references/review-checklist.md]를 읽고 전 항목을 확인한다. 이 문서를 읽지 않은 자체 리뷰는 수행하지 않은 것으로 간주한다."
- (wf-implement §3.4 자리) "검증 단계와 깊이는 [references/verification-depth.md]의 표를 따른다. 표를 참조하지 않고 단계를 생략하면 생략 이유를 기록해도 유효하지 않다."
- (wf-tree) "계획 트리를 생성·재생성할 때는 `scripts/render.py`를 실행한다. 손으로 트리를 그리거나 고치지 않는다."
- (wf-doc) "새 문서를 만들거나 머리말·식별자·인계 블록을 채울 때는 [references/templates.md]의 해당 절을 읽고 그 골격을 사용한다."

트리거 문장은 "읽지 않으면 그 행위는 수행되지 않은 것"이라는 기존 §2.5("실행하지 못한 검증은 성공으로 간주하지 않는다") 어법과 결이 같아 스킬 전체와 충돌하지 않는다.

## 4. S5 설계안 — 경고 절(Gotcha) 초안

BG 해소: 각 스킬 상단(경계 절 다음)에 `## 주의 — 자주 틀리는 것` 절을 신설하고, 산재한 경고를 모은다. 중복 3곳은 정본 1곳+링크로.

**wf-implement:**
> ## 주의 — 자주 틀리는 것
> - **설계 승인은 실행 승인이 아니다.** push·병합·배포·삭제는 별도 사용자 승인이 필요하다(§2.3). 이 문장이 정본이며 다른 곳의 언급은 이 절을 가리킨다.
> - 실행하지 못한 검증을 성공으로 보고하지 않는다(§2.5).
> - 완료 판단과 문서 상태(`completed`)는 다른 것이다 — 문서 머리말을 바꿨다고 작업이 완료되지 않는다.
> - 회귀 의무 목록의 테스트를 수정·제외하여 통과시키지 않는다(S2 신설 규정).

**wf-tree:**
> ## 주의
> - `depends:` 점선의 화살표 머리는 **대기자** 쪽이다 — UML 의존성 화살표와 방향이 반대다.
> - 부모-자식은 분해이지 순서가 아니다. 순서는 `depends:`만 표현한다.
> - 롤업 집계는 표시 전용이다. 문서의 상태 필드를 자동으로 바꾸지 않는다.

**wf-doc:**
> ## 주의
> - 하이퍼링크 규칙을 하나라도 충족하지 못한 문서는 완료로 표시하지 않는다.
> - 템플릿을 채웠다는 사실이 승인·완료를 만들지 않는다. 의미는 내용 소유자 스킬이 결정한다.
> - TBD를 지우기 위해 내용을 지어내지 않는다. 확인 책임자와 해소 조건을 남긴다.

## 5. 커밋 전 스킬 린트 체크리스트 (S13 선행 구현, ★=스크립트 자동화 가능)

1. ★ name ≤64자, description ≤1,024자 (경고 임계 900자 — 현재 wf-tree 913자 초과 주의)
2. ★ description에 XML 태그 없음, 경로에 백슬래시 없음
3. ★ 본문 어절 ≤5,000(논문 기준) + 저장소 상한 2,000어절 경고(성장 감시)
4. ★ 상대 링크·앵커 유효성(대상 파일 존재, 한글 앵커 해석)
5. ★ references/ 무결성: 본문이 링크한 파일 존재, 어디서도 링크되지 않는 references 파일 경고
6. ★ N줄 초과 코드블록·표가 본문에 있으면 "references 이관 검토" 경고(UD 근사)
7. ★ 가드 문구 패턴 ≥1회(RL 근사), `## 주의` 절 존재(BG 근사)
8. 수동/LLM: UD(남은 본문이 판단 규칙인지 세부인지), MUS, SOC(순서 지시에 적응 조건이 붙어 있는지)
9. 프로세스: SKILL.md diff에 절차 세부 +30줄 초과 시 references 이동 검토를 리뷰 항목으로

## 6. 이행 순서와 실험 설계

**이행 순서.** S1–S3 편집(이전 보고서)과 같은 사이클에서:
1. `references/`·`scripts/` 파일 생성(내용 이동, 의미 불변 — wf-doc 단독 서식 작업으로 처리 가능)
2. 본문에서 이동분 삭제 + 강제 트리거 문장 삽입 + `## 주의` 절 신설
3. 린트 스크립트(`skills/scripts/lint.py`) 추가, 이후 커밋마다 실행
4. 이 작업 자체를 정식 경로(요구·설계 승인 → TASK 분해)로 돌려 첫 관측 표본으로 삼음

**실험 — "이관이 삭제가 되지 않았는가"가 핵심 질문.**
- 지표 ① **참조 준수율**: 자체 리뷰·검증·템플릿 작성 시점에 해당 references 파일을 실제로 읽었는가(세션 로그에서 Read 호출 확인). 논문의 218/283(77%) 세션 접근률이 참조 기준.
- 지표 ② 규칙 준수율 유지: 재현 테스트 선행 작성률, 인계 절 갱신률, 머리말 형식 오류율 — 다이어트 전후 5–10 사이클 비교, **하락하지 않아야 함**(비열등성).
- 지표 ③ 세션당 규칙 텍스트 토큰: 스킬 본문 합계(다이어트 전 ~42k자 → 후 예상 ~25k자) + 실제 로드된 references 크기.
- 지표 ④ 린트 경고 수 추세(종단 분석의 "재발 감시").
- 혼동: S1–S3 편집과 동시 적용이라 효과 분리가 안 됨 → 목적을 "성능 향상 입증"이 아니라 "품질 비열등 + 토큰 감소"로 한정하면 동시 적용이 문제되지 않는다.
- 실패 시 롤백 기준: 참조 준수율이 낮아(예: 절반 미만) 규칙 준수율이 떨어지면, 해당 references는 본문으로 되돌리고 트리거 문장을 강화하는 쪽부터 시도.
