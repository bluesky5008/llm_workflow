## 0. 결론

1. **plan 단계에서 계획하는 쪽이 증거상 확실히 낫다.** 사전에 쓰기 범위를 선언하고 겹치지 않게 묶음을 나눈 뒤 생산자→소비자 순으로 병합하면 통합 성공 9/9·충돌 0이었고, 조정 없이 병렬로 돌리면 1/9·충돌 13건이었다(NP-Bench). 의존 그래프로 공유 "허브" 파일을 분리하는 계획은 직렬 대비 통과율 +11~14%p, 1.8~2.1배 빠르고 비용 28~35% 감소였다(Co-Coder).
2. **구현 단계의 즉흥 병렬화는 조건부로만 된다.** 범위를 런타임에 추론하는 문제는 미해결(NP-Bench 한계)이고, 구조 없이 파일 단위로 나누면 비용 +60%(Co-Coder), Claude Code Agent Teams는 가장 빠르지만 두 벤치마크에서 품질이 직렬보다 낮았다. 동적 분기(AgentSpawn)는 완료율을 올리지만 토큰 +54%이고 단일 저자·미재현이다. 따라서 런타임에는 **읽기 전용 작업(조사·리뷰·테스트 작성 맥락 분리)은 자유롭게, 구현 TASK는 plan 데이터로 검사가 통과할 때만** 병렬화한다.
3. **llm_workflow는 이미 절반을 갖고 있다.** §3.2의 "수정 파일 겹침·심볼 참조 → `depends:` 후보 검출"과 wf-tree의 `depends:` 렌더링은 NP-Bench 계획기의 입력(범위·의존)과 같은 것이다. 빠진 것은 (a) TASK별 쓰기 범위의 명시, (b) 병렬 묶음 산출, (c) 병렬 실행 시의 기록·검증 규약이다.
4. **병렬화의 실제 비용은 검증과 기록에 있다.** 각 worktree의 검증은 서로 다른 SHA에 귀속되므로(3튜플 규칙) 병합 후 다시 검증해야 하고, `work-log.md`·`test-register.md`·`status.md`는 단일 파일이라 여러 에이전트가 쓰면 충돌한다. 규약 없이 병렬화하면 이 저장소의 강점(증거·재개 가능성)이 먼저 깨진다.

## 2. 현행 llm_workflow와의 대조

| 현행 | 병렬화 관점 | 판정 |
|---|---|---|
| §3.2 계획: "수정 파일이 겹치거나 심볼을 참조하는 작업 쌍은 `depends:` 후보로 검출" | NP-Bench 계획기의 의존 간선 입력과 같음 | ✅ 기반 있음 |
| §3.2 "수정하거나 추가할 주요 파일"(계획 단위) | TASK별 **쓰기 범위**로는 명시되지 않음 — 묶음 산출의 전제 | ⚠️ 공백 |

| verification-depth §1: TASK `completed` 전이마다 `유지` 행 전량 | 병렬 TASK마다 전량이면 비용이 묶음 크기만큼 늘어남 | ⚠️ 묶음 단위로 재배치 필요 |

## 3. 적용 방안 — 후보 P-01~P-08

### plan 단계

| ID | 항목 | 내용 | 근거 |
|---|---|---|---|
| **P-01** | TASK 쓰기 범위 필드 | plan 템플릿의 TASK 항목에 `범위:`(수정·추가할 파일·glob)를 둔다. 기존 §3.2의 겹침 검출이 이 값을 입력으로 쓴다 | NP-Bench는 선언된 범위가 보장의 전제 |
| **P-02** | 허브·계약 우선 배치 | 공유 헬퍼·스키마·공개 인터페이스를 바꾸는 TASK는 **단독 묶음의 선두**에 두고, 소비자 TASK는 그 뒤 묶음으로. 저장소 관통 문서(`requirements.md`·`design.md`·대장)를 바꾸는 TASK도 단독 | Co-Coder 허브 분리, NP-Bench 계약 순서, 공유 헬퍼 간섭 97% |
| **P-03** | 병렬 묶음 산출 | `depends:`가 없고 `범위:`가 서로 겹치지 않는 TASK를 묶음 `W1, W2, …`로 나눈다(탐욕적 색칠 + 위상 정렬). `render.py`에 계산 뷰를 추가하면 손으로 판단하지 않아도 된다(B층 스크립트). 묶음은 **허용**이지 의무가 아니다 — 직렬 실행은 언제나 유효 | NP-Bench 계획기, ADR-010 "기계적으로 재현 가능한 것은 scripts" |
| **P-04** | 병렬화 여부 판단 기준 | 묶음 폭이 2 이상이고 TASK가 각각 수십 분 이상일 때만 병렬. 작은 TASK·촘촘한 의존·문서 위주 작업은 직렬 | Agent Teams 문서 "너무 작으면 조정 비용이 이득보다 큼", Co-Coder |

### 구현 단계

| ID | 항목 | 내용 | 근거 |
|---|---|---|---|
| **P-05** | 실행 규약 | 메인 세션(리드)이 묶음의 TASK마다 **worktree 격리 서브에이전트**를 띄운다. 서브에이전트는 자기 TASK의 TDD·관련 행 실행까지만 하고 **문서(work-log·대장·status·plan)는 쓰지 않는다** — 결과(변경 요약·Red/Green 증거·SHA)를 리드에 반환. 리드만 기록한다 | 단일 파일 충돌 회피, 상시 재개 불변식 보존. Agent Teams는 worktree 격리가 없고 재개 시 팀원 복원이 안 돼 비권장 |
| **P-06** | 묶음 단위 통합·검증 | 묶음이 끝나면 리드가 위상 순서로 **하나씩** 병합하고(각 병합 뒤 관련 행), 마지막 병합 HEAD에서 `유지` 행 전량 1회 + 대장 등록. 실패한 TASK만 재시도(전면 재실행 금지) | 3튜플 규칙, RSTD 선택적 재시도 −51.7% |
| **P-07** | 범위 위반·정보 전달 | 서브에이전트 종료 시 `git diff --name-only`가 `범위:` 안인지 리드가 확인하고, 벗어나면 그 TASK를 직렬로 되돌린다. 다음 묶음 TASK가 앞 묶음의 변경 파일과 인접하면 앞 변경의 요약을 프롬프트에 넣는다 | NP-Bench 범위 미강제 한계 보완, 요약 전달 82% 회복 |
| **P-08** | 런타임 즉흥 병렬의 범위 | plan에 묶음이 없어도 언제든 병렬화해도 되는 것: 읽기 전용 조사, 리뷰 관점 분리, 테스트 작성 맥락 분리(R-10). 구현 TASK는 런타임에 P-01·P-03 검사(범위 비겹침·`depends:` 없음)를 통과할 때만 — 검사 없이 판단하지 않는다 | 런타임 범위 추론 미해결, 파일 단위 단순 병렬 비용 +60% |

**세션 인계와의 관계.** 인계 판단 경계를 "계획 항목"에서 "묶음"으로 넓힌다(진행 중 서브에이전트가 있으면 인계하지 않고 묶음 종료까지 기다리거나 묶음을 포기하고 직렬로 재개).

## 4. 순서와 측정

- **선후:** P-01(범위 필드)은 비용이 작고 직렬 실행에도 이득(다인 사용의 파일 선점 S36, 회귀 가드의 범위 판단과 공유)이 있어 먼저 할 수 있다. P-03~P-07은 테스트 사이클 1·2 이후 — 대장 등록·검증 규칙이 바뀌는 중이라 그 위에 얹는다.
- **측정(코드 저장소에서만 의미 있음):** 같은 plan을 직렬/묶음 병렬로 각각 실행해 벽시계 시간, 토큰, 병합 충돌 수, 병합 후 재검증 실패 수, 범위 위반 수를 비교. 이 저장소는 문서·싱글턴 파일 위주라 묶음 폭이 거의 1이 되어 이득이 작을 것으로 예상.
- **다인 사용과의 관계:** P-01·P-02·P-07은 사람 간 병렬 작업의 충돌 감소 방안(S35·S36)과 같은 장치다. 한 번 설계해 두 용도에 쓴다.
