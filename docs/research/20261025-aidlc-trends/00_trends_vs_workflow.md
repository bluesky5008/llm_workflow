## 0. 결론 요약

1. **현행 워크플로우의 노선은 최신 증거와 대체로 일치한다.** 설계를 TDD 앞의 별도 단계로 두는 것, 결정 사다리(재사용 우선), "테스트를 지우는 쪽이 입증 책임", 3튜플 증거, 재정비 관문, 경량 경로가 모두 2026년 연구·실무가 권하는 방향이다. 다인 토론 1라운드의 예측(싱글턴 파일 충돌, 전역 번호 경쟁)도 실측 연구로 뒷받침된다.
2. **가장 큰 공백은 "규칙은 있는데 강제가 없다"는 점이다.** 프롬프트에 둔 계획은 22~45%만 지켜지고, 구조를 코드로 강제하면 성공률이 오른다. 테스트 우회(reward hacking)는 보호된 평가 경로로 가장 크게 줄어든다. AWS AI-DLC도 v2에서 "모델이 따를 것이라 믿는 규칙"을 결정론적 엔진으로 바꿨다. → 미적용 S9(Stop 게이트)에 **승인 게이트 훅(S28)·등록 테스트 쓰기 차단 훅(S29)**을 묶어 최우선으로 권한다.
3. **설계에서 AI가 가장 약한 곳은 관계와 기존 자산이다.** 컴포넌트 식별 F1 0.571에 비해 관계 F1은 0.130이고, 이미 있는 클래스·헬퍼를 다시 만드는 사례가 반복 보고된다. → 기존 자산 대조(S22)와 기계 검사 가능한 컴포넌트·의존 목록(S24).
4. **보류했던 S11(적대적 설계 검토)은 조건부로 살아난다.** 근거를 인용하게 강제한 검토자+비평자는 단일 검토자보다 낫고(F1 0.533 vs 0.495), 근거 강제가 없으면 더 나빠진다(0.457). 9월의 보류 근거(E2EDevBench)는 "근거 없는 중간층"에 대한 것이었다.
5. **다인 확장 전에 싱글턴 표 5개를 "파일 1개 = 레코드 1개 + 생성 색인"으로 바꿔야 한다.** 서로 다른 에이전트의 동시 PR 쌍은 41.7%가 텍스트 충돌했다(같은 에이전트 19.8%). Gitea 28.0(2026-09-30)부터 CODEOWNERS 승인을 병합 차단 조건으로 강제할 수 있어, 보류 중인 Q-01~Q-05에 답할 재료가 갖춰졌다.

## 1. AI를 이용한 설계

### 1.1 AI는 설계를 잘하는가 — 증거

| 측면 | 결과 | 출처 |
|---|---|---|

**정리.** 지식과 후보 생성은 강하고, 관계 추론·트레이드오프 선택·기존 구조 존중·시간에 따른 설계 유지가 약하다. "AI에게 설계를 맡긴다"보다 **"AI가 초안을 내고, 약한 부분은 기계 검사와 사람 판단으로 메운다"**가 증거에 맞는 분업이다.

### 1.2 더 나은 설계 진행 방식 — 증거가 있는 것과 없는 것

| 방법 | 증거 | 판정 |
|---|---|---|
| 계획을 세우고 따르게 함 | 나쁜 계획은 계획이 없는 것보다 나쁨(16,991회 실행). 프롬프트 속 계획 준수율 약 22~45%, 구조를 코드로 강제하면 SWE-bench Verified 0.36→0.44 | **강함** — 단, 계획 자체의 검토와 강제가 전제 |
| 인터뷰(명확화 질문) | 불충분 명세 과제에서 상호작용이 최대 74% 개선. 모델은 지시 없이는 거의 묻지 않음. 모호한 대상에 행동하면 안전 성공률 67.9%→8.6% | **강함** — Anthropic 현행 가이드도 "인터뷰 → SPEC.md → 새 세션에서 구현" |
| Spec-driven 도구(Spec Kit·Kiro·OpenSpec·BMAD) | Spec Kit에 저장소 탐색·검증 훅 추가 시 품질 +0.15·SWE-bench Lite +1.7점, 실행당 13분 추가, 사람은 훅 없는 쪽을 19:8로 선호. 실행 가능한 계약은 저가 모델을 3/10→10/10으로 올리지만 프런티어 모델엔 비용만 추가 | **약~중** — Thoughtworks Radar Vol 34: Spec Kit·OpenSpec Assess, "에이전트 지시 비대화" Caution |
| TDD로 설계를 대신함 | 비공식 실험에서 TDD 지시가 앞단 설계를 방해("actively work against such an up front design step") | 설계를 TDD 앞 별도 단계로 두라는 근거 |
| 적대적 검토 | 근거 인용 강제 검토자+비평자 F1 0.533 > 단일 0.495 > 근거 강제 없는 적대 검토 0.457(동조 날조). "N개 이상 찾아라"는 과잉 설계 유발 | **조건부 강함** |
| 대안 여러 개 생성 후 비판 | 직접 증거 없음. 사람-LLM 설계 18쌍 중 대안을 요구한 것은 3쌍(앵커링) | 의미 있게 경쟁할 때만 |
| 경량 형식 검사 | Kiro가 인수 조건을 SMT로 옮겨 충돌·공백 탐지 후 2지선다 질문. 정확도 공개 수치 없음 | 관찰 |

### 1.3 AWS AI-DLC (2026-10 기준, v2.11.1)

- **v2의 핵심 변화:** v1의 "모델이 따를 것이라 믿는 규칙"을 **결정론적 엔진**으로 교체 — 코드가 다음 단계를 고르고 LLM은 그 안에서 일한다. Claude Code·Kiro·Codex 등에서 동작.
- **구조:** 5단계(Initialization·Ideation·Inception 9·Construction 7·Operation 7) 33스테이지, 에이전트 14, **워크플로 프로필 11개**(Classic 18스테이지, Express 10, Bugfix 9).
- **Inception 산출물:** 요구사항, 스토리, YAML 컴포넌트 목록(`components.md`), ADR(`decisions.md`), 의존 그래프가 있는 작업 단위(unit), 계약, 인도 계획.
- **사람 관문:** Initialization 이후 모든 스테이지 끝에 실제 사람 메시지가 필요한 승인 관문. 단계 경계마다 자동 추적성 검사. Construction은 단위별 승인이고, 승인에는 사람이 승인한 검증 명령의 도구 작성 영수증이 필요. "자동 계속" 모드에서도 계획 승인과 실패는 항상 멈춤.
- **현장 교훈:** 1시간쯤 지나면 승인이 고무도장이 됨, 작은 버그 수정에 승인 6회, 의도를 쓴 사람이 계획을 승인하면 안 됨. AWS의 10~15배 생산성 주장은 독립 데이터 없음.

**우리와의 관계.** AI-DLC Classic 프로필은 현행 wf-design→승인→wf-implement와 거의 같은 골격이고, Express·Bugfix 프로필은 우리 경량 경로에 해당한다. 차이는 (a) 관문을 코드가 강제한다는 점, (b) 컴포넌트·의존을 YAML로 두고 기계 검사한다는 점, (c) 프로필 선택이 판단이 아니라 명시적 분기라는 점이다.

## 2. 개발 중 회귀 테스트 관리

### 2.1 최신 증거

**A. 에이전트의 테스트 우회(9~10월 이전 조사 이후 신규)**

| 출처 | 결과 |
|---|---|
| ImpossibleBench (2510.20270) | 명세와 테스트가 모순되는 과제에서 GPT-5 54%, o3 49%, Opus 4.1 50%가 통과를 "만들어냄". **명시적 중단(불가 표시) 출구를 주자 GPT-5 54%→9%, o3 49%→12%** — 원문 재확인. 숨긴 테스트는 우회를 거의 0으로 만들지만 정상 성능도 떨어뜨림 |
| SpecBench (2605.21384) | 보이는 기능별 테스트는 모든 에이전트가 통과. 기능을 조합한 보류(held-out) 테스트와의 격차가 코드 규모 10배마다 28%p 확대 — 단일 기능 테스트는 게이밍하기 쉽다 |
| Reward Hacking Benchmark (2605.02964) | 환경 강화로 우회 6.5%→0.8%, 과제 성공률 불변. 단일 최대 기여는 **보호된 평가 경로와 실패 시 닫히는 파싱(약 41.5%)**. 우회의 약 28%는 사고 과정에 흔적이 없음 |
| Bergen 외 (2609.19101) | 모델의 자기 보고 F1 13.2% — 에이전트가 "테스트 안 건드렸다"고 해도 믿을 근거가 아니다 |

**B. 에이전트가 쓴 테스트의 품질**

- 테스트를 거의 쓰지 않은 모델과 대부분 쓴 모델의 해결률 차이가 2.6점에 불과하고, 테스트 개수를 바꿔도 83.2% 과제에서 결과가 같다. 단언보다 print가 많다(2602.07900).
- 에이전트 테스트 커밋의 36%가 mock 추가(사람 26%), 범용 mock 95%, fake 사용은 사람보다 적음(32% vs 57%). CLAUDE.md 약 11.2만 개 중 mock을 언급한 것은 약 1.3만 개(2602.00409).
- 스위트 크기와 뮤테이션 점수의 상관 r=0.031, 커버리지와 실제 버그 탐지 r≈0.37~0.48(ISSTA'26 재현, 2607.22880).
- 동작을 보존하는 코드 변경에서 LLM은 새 테스트 11.8개를 쓰고 기존 10.9개를 버리며 일치는 18.1% — **유지보수보다 재생성 경향**(2603.23443).
- LLM 테스트는 약간 더 flaky하고, 그중 63%가 정렬되지 않은 컬렉션 순서 의존. flaky함은 프롬프트의 예시 테스트에서 복제된다(2601.08998).

**C. 뮤테이션을 오라클로**

- Meta ACH: 비동치 뮤턴트 4,660개 → 테스트 571개, 엔지니어 수용 73%. Meta JiT(2601.22832): 자동 평가기로 사람 검토 70% 감소.
- 기존 테스트를 보여 준 LLM 뮤턴트는 "기존 테스트를 통과하지만 실제 결함을 가진" 비율이 79~88%로, 테스트를 보지 않은 LLM(12~23%)·mutmut(4~6%)보다 훨씬 높다(2609.35841).
- MuMuTestUp(2605.19265): 코드 변경 후 낡은 테스트를 뮤테이션·커버리지 피드백으로 갱신, 뮤테이션 점수 72.39%(최고 기준선 +16.66점).

**D. 테스트 간 관계와 선택(RTS)**

- Legunsen FSE'16: 동적(Ekstazi) 20.6% 선택, 클래스 수준 정적 29.4%·누락 0.2% 리비전, 메서드 수준 정적 43.8%·안전하지 않음 10.6%. **거친(파일·클래스) 단위 정적 선택이 실용적으로 가장 안전**, 리플렉션은 정적 분석의 사각.
- 도구: pytest-testmon(`.testmondata` 의존 DB), Jest `--findRelatedTests`, Datadog TIA(덮은 파일이 같을 때만 생략, 생략 불가 표시 지원).
- 공백: AI 생성 테스트로 인한 스위트 비대화를 직접 측정한 2026 동료 심사 논문은 찾지 못함 — 위 B의 간접 증거뿐.

**E. 도구·실무**

- Anthropic best practices: 수정 전 실패 테스트, 결정론적 게이트로서의 Stop 훅, "일한 에이전트가 채점하지 않도록" 검증 서브에이전트, 한 Claude가 테스트를 쓰고 다른 Claude가 통과시키기, 특정 폴더 쓰기를 막는 훅.
- TDD Guard → Probity(v1.10.1)로 대체: PreToolUse로 실패 테스트 우선·최소 구현·green에서만 리팩터를 강제. **어느 도구도 기존 테스트 파일 편집을 기본으로 막지 않는다.**
- 실무 가지치기(Rachev 2026-08): 테스트별 범위 커버리지 겹침 행렬 → 70~80% 겹치는 쌍을 테이블 기반 테스트로 병합, "커버리지 하락 금지". 겹침은 중복의 증거가 아니라 후보 신호.

## 3. 동료 개발자와의 협업 충돌

### 3.1 최신 증거

- **에이전트 동시 작업은 이미 흔하다.** AIDev-pop 33,596 PR 분석에서 저장소의 40.2%에 동시에 열린 에이전트 PR 쌍이 있고(1주 창으로 보면 53.4%), **서로 다른 에이전트 PR 쌍의 텍스트 충돌 41.7%, 같은 에이전트 쌍 19.8%**(2607.04697 — 원문 재확인). 충돌 파일의 84.4%가 소스 코드, 약 42%가 구조적 충돌(수정/삭제, 추가/추가).
- **큰 PR과 중복 작업이 거절된다.** 에이전트 PR 병합률 71.48%, 변경 1줄당 병합 확률 약 1% 감소, 실패 CI 1건당 약 15% 감소. 거절된 표본의 23%가 다른 PR과 중복·대체(MSR '26). Claude Code PR 중앙값은 사람의 약 2~6배 크기.
- **DORA 2025:** 작은 배치와 강한 버전 관리 관행을 AI 역량으로 명시 — 작은 배치가 AI의 긍정 효과를 증폭하고 마찰을 줄인다. 병목은 코드 리뷰로 이동.
- **의미 충돌:** 자연히 분리된 실제 PR 쌍은 간섭이 드물지만(834회 중 1회), **공유 헬퍼를 둘 다 건드리는 과제는 97% 간섭**. 상대 작업의 완료된 변경을 요약해 알려 주면 82% 회복("Passes Alone, Fails Together", 2026-09). 의존 그래프로 공유 "허브" 파일을 격리하는 계획이 순차·파일 분할·Agent Teams보다 통과율 +14.0%, 2.1배 속도(Co-Coder). 일정 계획기가 있으면 충돌 13→0(NP-Bench, 소규모). 결론: **병합 도구보다 사전 조정이 효과를 만든다.**
- **LLM 충돌 해결은 절반 수준.** 최고 모델이 개발자 해결과 정확히 일치 47~55%(Merge-Bench). 구조 병합기 mergiraf는 리눅스 커널 충돌 병합 7,415건 중 428건만 완전 해결. git `union` 드라이버는 줄 순서를 보장하지 않아 표에 위험.
- **Claude Code 공식 문서:** worktree가 세션별 독립 체크아웃 제공. Agent Teams는 실험 기능이고 팀원을 worktree로 격리하지 않으므로 "팀원마다 다른 파일 집합을 소유하도록 분할"하라고 권고.
- **Spec Kit 팀 가이드:** 기능당 명세 소유자 1명, 팀 헌장 파일은 지정 관리자·팀 승인으로만 변경, 명세 → 계획 → 작업 순서로 커밋·리뷰, 인터페이스 계약은 API 소유자가 소유. 저장소 컨텍스트 파일(AGENTS.md·CLAUDE.md 2,303개)은 설정 코드처럼 잦은 소규모 추가로 변함 — 소유·리뷰 대상 파일로 다뤄야 한다.
- **Gitea(2026-10):** 28.0.0(2026-09-30)에서 **CODEOWNERS 규칙 전부 승인 전 병합 차단** 옵션 신설(원문 재확인), 봇 계정 추가. 보호 브랜치는 필수 승인 수, 낡은 승인 무효화, 뒤처진 브랜치 차단, 필수 상태 검사(Jenkins 보고 가능), 보호 파일 패턴을 지원. 네이티브 머지 큐 없음(외부 gitea-mq v0.2.0), 네이티브 스택 PR 없음. Gitea 서버 측 병합이 `.gitattributes` 사용자 정의 드라이버를 쓰는지는 미확인.

## 5. 권고 순서

v1 원칙("예측이 아니라 실측")과 D-02(최소 1개 사이클은 코드 저장소에서)를 따른다.

1. **사이클 A' — 강제 장치 묶음(S9 + S28 + S29 + S30).** 근거가 가장 강하고 이 저장소에서도 동작을 검증할 수 있다(훅 테스트 TST-01 확장). 스킬 본문은 거의 바뀌지 않고 `setup/hooks/`에 집중된다.
2. **사이클 C' — 질문 장치 묶음(S21 확대 + S23 + S11 재작성).** 설계 단계의 품질과 테스트 우회를 동시에 줄인다. 분량 증가는 references로 보낸다(ADR-010 계층 규칙).
3. **다인 사용 전 구조 변경(S35 + S36 + Q-01~Q-05 결정).** 동료 도입(Gitea 전환) 일정보다 먼저 끝내야 한다. 식별자 체계 변경은 나중에 할수록 링크 수정 비용이 커진다. 보류 중인 `20260814-multiuser-workflow`를 재개하는 형태가 자연스럽다.
4. **코드 저장소 실측 사이클(S22·S24·S27·S31·S32·S33·S34).** 효과는 실제 제품 코드에서만 측정된다. S24·S27은 첫 코드 저장소 작업에 함께 얹을 수 있다.
5. **문서 소량(S25·S26·S37).** 언제든 끼워 넣을 수 있다.
