레거시 저장소에서는 **편입 → 측정 → 배치 정리 → 상시 운영** 순서로 간다. 편입은 삭제·수정 없이 대장에 올려 가드 보호를 받게 하는 단계이고, 측정은 모듈별 기준값(실행 시간, flaky 이력, 테스트별 커버리지 겹침, 표본 뮤테이션, 냄새 점검 R-07)을 잡는 단계다. 배치 정리는 모듈 단위로 고아 폐기·중복 병합·냄새 리팩터·flaky 해소·느린 테스트 분리를 하며, 이후에는 통합 관문의 점진 재정비가 이어받는다.

## 0. 원칙

- **규칙 → 강제 순서.** 현행 규칙(주의 ④ "`유지` 행 테스트를 수정·제외해 통과시키지 않는다", 입증 책임, 4조건)은 이미 최신 증거와 맞다. 1차 사이클은 새 규칙을 늘리지 않고 **있는 규칙을 기계로 강제**한다.
- **전량 실행 시점은 늘리지 않는다.** [verification-depth §1](../../../skills/wf-implement/references/verification-depth.md#1-시점별-실행-집합)의 "전량 실행은 `completed` 전이·통합·재개 세 시점 밖에 두지 않는다"를 유지한다. 새 게이트는 테스트를 다시 돌리지 않고 **기록과 diff를 검사**한다.
- **스킬 본문은 하네스 무관.** 훅은 `setup/hooks/` 어댑터에 두고, 스킬에는 의무만 적는다(README 원칙).
- **이 저장소에서 검증 가능한 것부터.** 사이클 1은 TST-01(훅)·TST-02(린트) 확장으로 검증할 수 있다. 효과(우회 감소)는 코드 저장소에서만 측정된다(D-02).

### 레거시 테스트 정비 — 기존 코드 저장소에 적용할 때 (2026-10-25 추가)

사이클 1·2 완료 후 기존 코드 저장소에 워크플로우를 적용하면서 이미 있던 테스트를 정비·최적화하려면 아래 네 공백을 메워야 한다. 현행 재정비 관문은 **대장에 등록된 행 중 이번 변경이 닿은 범위**만 다루고, 폐기·병합의 "유일 검증 아님" 조건은 **인수 조건과의 연결**을 전제하기 때문이다. 레거시 테스트는 대장에 없고 인수 조건과도 연결되어 있지 않다.

|---|---|---|---|---|
| **R-13** | 대장 편입(onboarding) 절차 | `verification-depth.md` 새 절, wf-implement §3.1 | 워크플로우를 적용하는 첫 작업에서 기존 스위트를 **삭제·수정 없이** 대장에 올린다. 같은 SHA 2회 실행 → 둘 다 통과 `유지`, 결과 불일치 `격리`, 둘 다 실패 `격리(기존 실패)`와 실패 증거. 행은 처음엔 파일·디렉터리 단위로 거칠게, `보호 스코프`는 커버리지로 채우거나 `미확정`. 편입 즉시 R-02·R-03 보호를 받는다 | 편입 전에는 가드가 레거시 테스트를 보호하지 못해, 새 워크플로우로 코딩하는 동안 에이전트가 레거시 테스트를 자유롭게 고칠 수 있다 — **편입이 정비보다 먼저** |
| **R-14** | 전수 재정비 작업 유형 | wf-implement §3.6, `verification-depth.md` §3 | 통합에 딸린 관문과 별개로, 대장 일부 또는 전부를 범위로 하는 **독립 재정비 작업**을 정식 경로로 둔다. req-design에 대상 범위·성공 기준(뮤테이션 kill 보존, 실행 시간 등)을 적고 승인받는다. 배치(모듈) 단위 TASK, **제품 코드 동결**(테스트와 제품 코드를 같은 작업에서 바꾸지 않음) | 테스트 정리는 제품 동작을 바꾸지 않지만 판단과 사용자 승인(4조건)이 많아 경량 경로에 맞지 않는다 |
| **R-15** | `리팩터` 전이와 레거시용 유일성 판정 | `verification-depth.md` §2·§3 | (a) 테스트 수정을 위한 전이 규칙: 냄새 제거·mock→fake 교체 등은 같은 제품 코드 SHA에서 수정 전·후 모두 통과 + 뮤테이션 kill 집합이 줄지 않음을 증거로 허용. (b) 인수 조건이 없는 행의 "유일 검증 아님"은 **다른 테스트가 죽이지 못하는 뮤턴트를 이 테스트만 죽이는가**로 판정하거나, [역공학](../../../skills/wf-design/references/reverse-engineering.md) 10단계(테스트 분석)의 RR 항목에 연결해 판정 | 현행 상태값은 폐기·병합·대체·격리만 있어 "고쳐서 유지"를 표현할 수 없다. 4조건의 유일성은 AC 연결을 전제 |
| **R-16** | 대량 승인 계층화 | `verification-depth.md` §3, 작업 기록 `### 테스트 대장 변경` | 근거가 기계적인 분류(`고아`: 파일·심볼 부재)는 목록 일괄 승인, 판단이 필요한 분류(`중복`·`동어반복`·`자명`·`리팩터`)는 배치별로 개별 행 승인. 가드(R-02)는 승인된 req-design의 대상 TST 범위 안에서는 배치당 1회 확인으로 묶는 방식 검토(D-6) | 레거시 스위트는 후보가 수십~수백 건이라 건별 확인은 승인 피로로 고무도장이 된다 |

**선후 관계.** R-13은 사이클 1(R-01·R-02)의 직후, 기존 저장소 적용 첫날에 수행한다. R-14~R-16은 사이클 2(R-06·R-08)를 전제한다. R-11(커버리지로 보호 스코프 갱신)은 R-13의 `보호 스코프` 채우기에 필요하므로 사이클 3에서 이 묶음으로 당긴다.

**레거시 정비 작업의 성공 기준 후보(R-14 req-design 입력).** 모듈 배치마다 (1) 대장 행의 뮤테이션 kill 집합 합이 정비 전 이상, (2) `유지` 행 전량 통과, (3) 제품 코드 diff 0, (4) 폐기·병합·리팩터 행마다 분류·증거·승인 기록, (5) 실행 시간·격리 행 수의 전후 값 기록(목표치는 저장소별로 req-design에서 정함).

## 3. 사이클 1 완료 판정 초안(인수 조건 후보)

- `유지` 행 테스트 파일을 Edit/Write하려 하면 사용자 확인 요청이 뜨고, 새 테스트 파일은 확인 없이 쓰인다.
- 셸로 `유지` 테스트 파일을 바꾸고 대장 변경 기록 없이 종료하려 하면 Stop이 1회 막힌다.
- 대장이 없는 저장소에서 두 훅은 아무 동작도 하지 않는다.
- `completed` TASK 수행 기록에 `Red` 필드가 없으면 린트가 오류를 낸다.
- TST-01·TST-02가 확장된 건수로 같은 SHA 2회 통과한다.
