# Human–AI Development Workflow — llm_workflow 개발 브리핑

- AI에게 코딩을 맡길 때의 개발 워크플로우: 스킬 4종, 문서 모델, 세션 핸드오프 자동화
- 내부 동료 개발자 공유용 · 정보 공유 목적
- 2026-08-09 · github.com/bluesky5008/llm_workflow

> 노트: 이 자료는 llm_workflow 저장소의 전체 개발 내용을 공유하기 위한 것입니다. 설득이나 의사결정용이 아니라 "우리가 무엇을 왜 이렇게 만들었는지"의 정보 공유가 목적입니다. 자료 자체도 이 워크플로우(wf-design 승인 관문 → wf-implement TDD 구현)를 통과해 만들어졌습니다.

## AI 코딩 위임의 실패 모드

- 요구사항이 불명확한 채 구현부터 시작 — 방향이 어긋난 결과물
- 요청하지 않은 추상화·기능이 붙는 과잉 구현
- "완료했습니다"와 실제 동작의 괴리 — 검증 없는 완료 선언
- 세션이 끊기면 맥락 소실 — 대화에만 있던 결정·계획·검증 결과 유실
- 해법: 규칙 나열이 아니라 워크플로우 + 문서 모델 + 하네스 자동화의 3중 구조

> 노트: 네 가지 실패 모드는 LLM의 구조적 특성에서 나옵니다. 특히 마지막 항목 — 모델은 자기 컨텍스트 사용량을 신뢰성 있게 알지 못하고, 자동 컴팩션(손실 요약)은 예고 없이 옵니다. 그래서 "잘 부탁한다"는 지시만으로는 해결되지 않고 구조가 필요합니다.

## 해법 개요 — 2-워크플로우와 승인 관문

```
작업 요청
  → [WF1] 요구사항 정의 + SW 설계   (wf-design)
  → ★ 사용자 승인 관문 — 기준선 vN 발행
  → [WF2] 계획 + 구현 + 검증·리뷰 + 통합   (wf-implement)
  → 완료 (증거 포함 보고)
```

- WF1이 "무엇을 왜 어떤 구조로", WF2가 "어떻게 만들고 완료를 어떻게 증명할지"를 소유
- 승인되지 않은 요구사항·설계는 구현 기준으로 사용하지 않음
- 작은 작업은 경량 경로로 WF1 생략 가능 (뒤 슬라이드)

> 노트: 사람 조직의 설계 리뷰 게이트를 AI 협업에 이식한 구조입니다. 핵심은 승인 관문이 대화가 아니라 문서(기준선 vN + 승인 기록)로 영구화된다는 점입니다.

## 스킬 아키텍처 — 4종과 소유권 경계

- 실행 기준(정본)은 스킬 문서 4개 — 다른 문서와 다르면 스킬을 따름
  - wf-design: 요구사항·설계·ADR/DCR·승인·기준선
  - wf-implement: 계획·구현·검증·리뷰·통합·완료 판단
  - wf-doc: 문서 형식 계층 (별도 단계 아님) — 머리말·상태·식별자·링크
  - wf-tree: 선택 계층 — 계획 트리·포트폴리오 시각화
- 내용 소유자 vs 형식 소유자 분리: "무엇을 기록할지"와 "어떻게 적을지"를 다른 스킬이 소유
- 겹치는 규칙은 복제하지 않음 — 한쪽에 정본, 다른 쪽엔 요약 + 링크 (경계표마다 정본 위치 명시)
- 진입점: 스킬 자동 로드가 없는 에이전트용 루트 SKILL.md 라우터

> 노트: 정본 원칙 덕에 규칙을 고칠 때 한 곳만 수정하면 됩니다. 각 스킬에 상대 스킬과의 경계표가 있고, 어느 쪽이 정본인지 문서에 박혀 있어 규칙 충돌 시 판정 기준이 명확합니다.

## wf-design — 요구사항 정의 + SW 설계

- 조사 먼저: 확인 가능한 사실은 사용자에게 묻기 전에 저장소·실행 환경에서 조사
- 사실 / 해석 / 가정 / 질문을 구분해 기록 — 추측을 사실로 승격하지 않음
- 산출물: 기능·비기능 요구사항(FR·NFR), 측정 가능한 인수 조건(AC), 설계 요소(DES), 위험
- ADR: 장기 영향·비가역 결정은 대안 비교와 함께 별도 기록
- DCR: 구현 중 승인된 기준선을 바꿔야 할 때 — 재승인 전까지 제안 상태, 영향 구현은 보류
- 역공학 절차: 승인된 문서가 없는 기존 코드의 현행 상태를 증거 기반으로 복원

> 노트: 구현 방법을 요구사항으로 고정하지 않는 것이 원칙입니다. 인수 조건은 "입력·행동·관찰 가능한 결과"를 갖춰 가능한 한 자동 테스트로 전환할 수 있는 형태로 작성합니다.

## 승인 관문과 기준선

- 대화형 승인 요청: 목표·범위·핵심 요구사항·설계 요약·주요 결정·가정·위험을 요약하고 명시적으로 질문
- 응답 4종과 상태 전이: 승인(approved) / 수정 요청(draft로) / 거부(rejected) / 보류(on-hold)
- 승인 시 기준선 vN 발행 — 재승인마다 v2, v3… 번호는 건너뛰거나 재사용하지 않음
- 승인은 대화에만 남기지 않고 문서의 승인 기록 절에 영구화
- 결정 등록부(docs/decisions.md): ADR·DCR의 저장소 전역 일련번호와 한눈 조망
- 설계 승인 ≠ 실행 승인: push·배포·삭제 등 외부·비가역 작업은 별도 명시 승인

> 노트: "누가 언제 무엇을 승인했는가"가 문서로 남아, 다음 세션의 AI가 대화 기록 없이도 유효한 기준선을 판단할 수 있습니다.

## wf-implement — 계획 + 구현 + 검증·리뷰 + 통합

- 시작 조건: 승인된 기준선. 없으면 정식 구현을 시작하지 않음
- 계획: TASK 분해(각각 명확한 결과·완료 조건), 의존성, 작업별 선행 테스트 명시
- 구현 중 기준선 충돌 감지 → 영향 구현 보류, 증거·초안과 함께 wf-design으로 반환(DCR)
- 완료의 증거: "코드 작성됨" ≠ 완료 — 인수 조건과 검증 결과로만 판단
- 실행하지 못한 검증을 성공으로 간주하지 않음. 실패·미수행은 보고에서 숨기지 않음
- 자체 리뷰(요구사항·정확성·보안·품질 4관점) → 통합 → 최종 보고

> 노트: 검증은 위험에 비례해 정적 분석 → 단위 → 통합 → 시나리오 → 비기능 → 실행 확인 순서로 수행합니다. 테스트 실패는 "이번 변경 탓 / 기존 실패 / 환경 탓 / 원인 불명"으로 분류해 기록합니다.

## 최소 구현 원칙 — 결정 사다리와 TDD

```
1 만들 필요가 있는가? (YAGNI)     4 플랫폼 네이티브 기능이 해결하는가?
2 저장소에 이미 있는가?            5 설치된 의존성이 해결하는가?
3 표준 라이브러리가 해결하는가?     6 한 줄로 가능한가?
                                  7 그래도 필요하면 동작하는 최소 코드
```

- 코드 작성 전 사다리를 위에서부터 검토, 성립하는 첫 단계에서 멈춤
- 최소화 금지 영역: 신뢰 경계 입력 검증, 데이터 손실 방지 오류 처리, 보안·접근성
- TDD: 테스트가 필요한 로직은 실패하는 테스트 먼저 (Red → Green → Refactor)
- 버그 수정은 재현 테스트 먼저 — 경량 경로에서도 생략하지 않음

> 노트: "해법에는 게으르되, 조사에는 게으르지 않는다" — 사다리는 문제를 이해한 뒤 적용하는 것이지 이해를 대신하지 않습니다. ponytail 스킬 full 모드가 기준이며, 충돌 시 wf-implement 규정이 우선합니다.

## wf-doc — 문서 공통 포맷

- 목적: 사람이 빠르게 판단하고, AI가 다음 세션에서 모호함 없이 재개하는 문서
- 공통 머리말: 문서 유형 · 작업 ID · 상태 · 기준선 · 날짜 · 관련 문서 + 요약(목적/결론/다음 행동)
- 상태 어휘 11종 고정: draft, awaiting-approval, approved, in-progress, completed, superseded …
- 식별자 2층: 항목 ID(FR-01, DES-01, TASK-01, VER-01…) / 문서 ID(REQ-, DESIGN-, WORK-…)
- 하이퍼링크 강제: 문서 관계는 클릭 가능한 링크 + 역방향 링크, 추적표로 FR→DES→TASK→AC→VER 연결
- 문서가 승인·완료를 대신 선언하지 않음 — 템플릿을 채웠다고 승인된 것이 아님

> 노트: 원칙 한 줄 — "대화에만 존재하는 결정과 증거를 문서의 확정 정보로 취급하지 않는다". 세션이 끝나면 대화는 사라진 것으로 간주하고, 문서만 남습니다.

## 문서 모델 — 저장소 관통 문서 + 작업 일지

```
docs/
├── requirements.md    # 현행 요구사항 — 작업마다 새로 만들지 않고 기준선 누적
├── design.md          # 현행 설계
├── plan.md            # 현행 구현 계획 (완료 사이클은 축약 이관)
├── decisions.md       # ADR·DCR 전역 등록부
└── work/<작업-ID>/    # 작업별 일지: work-log, ADR, DCR
```

- 현행 문서는 저장소를 관통하며 기준선(v1→v2…)을 누적 — "지금 유효한 것"이 항상 한곳에
- 작업 폴더에는 해당 작업의 기록과 결정만 — 이력의 정본
- 검증·완료 보고는 work-log에 유형을 합쳐 기록 (파일 수 최소화)

> 노트: 처음엔 작업별 산출물 구조였다가 "저장소 관통 + 작업 일지" 모델로 재편했습니다(커밋 d5292ad). 현행 상태와 이력을 분리한 것이 핵심입니다.

## wf-tree — 계획 트리와 포트폴리오

- 헌장: "제안하되 결정하지 않는다" — 계획의 새 원천이 아니라 구조화·시각화 계층
- 두 계층: 포트폴리오(노드 = 작업 1개) / 작업 내부(노드 = action item)
- 분기 템플릿: design 노드엔 리뷰+승인, implement 노드엔 테스트(선행)+리뷰를 자동 제안
- 필수 게이트는 생략 제안 금지: release·migrate 검증·포트폴리오 승인
- 단일 소스: 목록이 정본, 트리·다이어그램은 재생성물(generated 표시) — 다르면 목록이 맞음
- 렌더링: ASCII + Mermaid, 상태별 색상, depends 점선 (완료 노드는 기준선이 바뀌어도 안 되돌림)

> 노트: 목적은 누락 방지입니다 — 승인 관문, 자체 리뷰, 롤백 준비처럼 잊기 쉬운 항목을 노드 유형별 템플릿이 구조적으로 상기시킵니다. 항목의 의미·완료 판정은 여전히 wf-design·wf-implement 소유입니다.

## 경량 경로 — 모든 작업이 정식 경로는 아니다

- 조건(모두 충족 시 WF1 생략 가능):
  - 동작·공개 인터페이스·데이터 모델·보안에 무영향
  - 국소적이고 되돌리기 쉬움
  - 새 설계 결정·대안 비교 불요
- 예: 오타·주석 수정, 원인 명확한 단일 버그, 계약을 안 바꾸는 테스트 보강
- 생략할 수 없는 것: 변경 범위 준수, 위험 비례 검증, 결과·위험 보고, 버그 재현 테스트
- 판단이 애매하면 정식 경로. 진행 중 조건을 벗어나면 그 시점에 전환

> 노트: 기록 의무도 조건부입니다 — 경량 작업이 "현재 세션 안에 끝나지 않을 것으로 보이면" 그때부터 재개 가능한 기록을 시작합니다. 짧은 작업은 절단 확률과 손실이 모두 작아 상시 기록의 비용이 이득을 넘기 때문입니다.

## 세션 핸드오프 — 문제와 3층 설계

- 문제: 세션 절단과 자동 컴팩션(손실 요약)으로 대화 속 결정·계획·검증 결과가 유실
- A층 — 스킬 불변식 (적용 완료): 계획 항목마다 작업 기록 갱신 → 언제 끊겨도 문서만으로 재개, 표준 재개 프롬프트
- B층 — 저장소 스크립트 (미착수 후보): 재개 가능성 린트 등
- C층 — 하네스 훅 (적용 완료): Claude Code 훅으로 재개 진입·절단 신호·컴팩션 안전망을 기계화
- 설계 원칙: 스킬 본문은 하네스 중립 — 훅·자동 요약 같은 하네스 기능을 전제하지 않고 의무·상태 어휘로만 규정. 하네스 의존 자동화는 setup/ 어댑터에

> 노트: 전제 — 모델은 자기 컨텍스트 사용량을 신뢰성 있게 알지 못합니다. A층만으로도 워크플로우는 성립하고(훅이 죽어도 안전), C층은 사람·모델의 자발성에 의존하던 세 지점을 기계로 보강한 것입니다.

## C층 — Claude Code 훅 3종과 ADR-001

```
훅 이벤트 → setup/hooks/*.ps1 → docs/work/ 가드(무관 저장소 무동작)
          → additionalContext 주입 (스킬 절차를 가리키는 포인터만)
```

- 세션 시작(재개): 미완료 작업 기록 목록 + "재개 절차를 먼저 적용하라" 주입
- 툴 사용 후(임계값): transcript 성장량이 기본 1500KB 초과 시 "다음 계획 항목 경계에서 세션 인계" 주입
- 컴팩션 직후(재정렬): "요약은 손실 압축 — 작업 기록을 정본으로 재확인하라" 주입
- ADR-001: 컨텍스트 신호 = transcript 파일 크기 성장 프록시 — 훅이 접근 가능한 유일한 문서화된 신호 (대안: statusline 브리지, 모델 자기 판단, 마일스톤 카운트 비교 기각)
- 컴팩션 직전 개입은 불가(조사로 확인) → 사전 임계값 + 사후 재정렬의 2단 안전망

> 노트: 모든 훅은 fail-open — 오류 시 조용히 통과하고 세션을 막지 않으며, A층 수동 경로가 남습니다. 임계값은 환경 변수(CLAUDE_WF_THRESHOLD_KB)로 조정 가능합니다. 주입 텍스트는 새 규범을 만들지 않고 스킬이 이미 규정한 절차를 가리키기만 합니다.

## C층 — 구현과 검증

- TDD: 테스트 하니스 먼저 작성, 구현 부재로 13개 케이스 실패(Red) 확인 → 구현 → 21/21 성공(Green)
- 설치 멱등: settings.json 병합 — 기존 설정·사용자 훅 보존, 재실행 안전, 경로 이동 시 갱신
- 실설치·실저장소 스모크 성공. 설치 직후 진행 중 세션에서 훅 실행 실증(상태 파일 확인, VER-08)
- 임계값 실측 보정: 매우 긴 세션의 transcript 1758KB 실측 → 기본값 1500KB 유지 결정
- 발견: PowerShell 5.1 함정 2건(stderr 리다이렉트 중단, 단일 결과 .Count) — 하니스에서 해결
- 남은 관찰 2건 공개: 재개·재정렬 주입의 실세션 가시성 — 미완료 작업이 있는 다음 세션에서 자연 확인

> 노트: 한글 인코딩 문제는 메시지를 별도 md 파일로 분리하고 훅 스크립트를 완전 ASCII로 유지해 원천 회피했습니다. "남은 관찰"을 완료로 보고하지 않고 검증 표에 미수행으로 공개한 것 자체가 이 워크플로우의 보고 원칙입니다.

## 설치와 어댑터 — 하네스 중립의 실현

- setup_claude.ps1 (Windows, 재실행 안전):
  - skills를 junction으로 연결 — git pull만으로 스킬 최신화
  - 워크플로우 규칙을 CLAUDE.md에 설치, 훅 3종을 settings.json에 병합 등록
- setup_codex.ps1: 진입 규칙을 AGENTS.md에 설치 + 수동 호출용 custom prompts
  - Codex는 스킬 자동 로드가 없어 "짧은 상시 규칙 + 세션 중 저장소 SKILL.md 읽기" 방식
- macOS/Linux: symlink 수동 설치
- 같은 스킬 정본을 하네스별 어댑터가 각자의 방식으로 연결 — 스킬 본문은 무수정

> 노트: Codex 설치는 저장소 절대 경로를 규칙에 박으므로 저장소를 옮기면 재실행이 필요합니다. 훅 제거는 settings.json에서 이 저장소 경로가 포함된 항목을 삭제하면 됩니다.
