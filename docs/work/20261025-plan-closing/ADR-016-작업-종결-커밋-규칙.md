## 요약

- 목적: 마지막 커밋·push 시점에 모든 문서가 완료 상태가 되도록 종결 순서를 정한다.
- 현재 결론 또는 상태: A 채택(승인 2026-10-25) — 구현 커밋 → clean 재실행 → 문서 전용 종결 커밋 → 1회 push. 문서에 push 결과를 쓰지 않는다.
- 다음 행동: 없음 — 적용은 [WORK-20261025-plan-closing](./work-log.md).

## 배경

종결 문서는 "어느 커밋에서 `유지` 테스트가 통과했는지"(대장 `마지막 성공` SHA)와 통합 상태를 기록한다. 커밋은 자기 SHA를 담을 수 없고 push 결과는 push 뒤에야 안다. 그래서 regression-guard는 구현 커밋 → 종결 커밋 → push 뒤에도 문서 갱신(plan 트리)이 남았고, 작업 기록의 "푸시"는 사전 서술이었다.

## 영향을 받는 요구사항과 제약

- 사용자 요구: 마지막 커밋·push 시점에 모든 문서 완료, 이후 문서 변경 없음.
- 대장 `마지막 성공`은 SHA이며 `regression_guard.py`(Python)·`wf-test-guard.ps1`(PS)이 판독한다(DES-08 공유 견본).
- push는 사용자 승인 범위(wf-implement §2.3).

## 고려한 대안

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 구현 커밋 → 그 SHA에서 `유지` 재실행 → 종결 갱신 일괄 → 문서 전용 종결 커밋 → 두 커밋 1회 push. push 결과는 문서에 쓰지 않음 | 대장 SHA 기계 검증 유지, 새 장치 없음. 종결 커밋이 문서만 바꾸므로 구현 커밋의 3튜플이 유효 | 커밋 2개 |
| B | 단일 커밋. 대장 셀에 `work:<작업-ID>`를 적고 판정기가 `git log -1 -- docs/work/<ID>/work-log.md`로 종결 커밋을 해석 | 커밋 1개 | 대장 형식과 판독기 2개(Python·PS) 동시 변경, 셀에서 SHA를 바로 읽을 수 없음 |
| C | 단일 커밋 + 미리 정한 태그명을 셀에 적고 `git push --atomic`으로 커밋·태그 함께 push | 커밋 1개 | 작업마다 태그 누적, B와 같은 판독기 변경 |
| (현행) | 종결 순서 규칙 없음 | — | push 뒤 문서 변경·사전 서술 발생 |

## 결정

A를 채택한다. 종결 갱신은 한 번의 문서 전용 종결 커밋에 모으고, 그 전에 `git diff --name-only <구현 SHA>`가 `docs/` 밖을 포함하지 않음을 확인한다. 문서의 통합 상태는 구현 커밋 SHA와 "종결 커밋과 함께 push 대상(승인 일시)"만 적고, push 뒤 그 작업의 문서는 고치지 않는다. 구현 커밋이 승인되지 않으면 종결하지 않는다.

## 이유

- 사용자 요구(마지막 커밋 = 완료)를 충족하는 가장 작은 변경이다. B·C는 회귀 보호의 핵심인 대장 형식과 두 판독기를 함께 바꿔야 한다.
- 종결 커밋이 문서만 바꾸면 테스트 집합과 명령이 같고 테스트 대상 파일이 그대로라 구현 커밋 SHA의 통과 기록을 종결 상태의 근거로 인용할 수 있다.
- push 결과의 정본은 원격 ref다. 문서에 쓰면 사후 수정이 필요해진다.

## 결과와 감수할 단점

- 작업마다 커밋 2개(구현·종결)가 생긴다.
- 커밋 승인 전에는 작업이 `awaiting-approval`로 남는다.
- 종결 커밋에 코드가 섞이는 실수는 사람이 확인 명령으로 막는다(기계 검사는 후속).
