# ADR-005: 작업 기록의 수명주기 — 상태 전이 시 축약과 제자리 동결

## 요약

- 결정: 작업 기록의 아카이빙은 파일 이동이 아니라 **상태 전이 시점의 축약과 제자리 동결**이다. TASK가 `completed`로 바뀔 때 그 TASK의 수행 기록 항목을 한 번 확정해 쓰고, 작업이 `completed`로 바뀔 때 인계 절을 축약하고 포트폴리오 행을 제거한다. 완료된 작업 폴더는 `docs/work/<작업-ID>/`에 그대로 남고 이동·소급 편집하지 않는다.
- 핵심 이유: 재개에 필요한 정보는 열린 작업에만 있고, 완료 작업의 이력은 git이 정본이다. 이동은 들어오는 링크 수리를 매번 요구하고 훅 동작에는 이점이 없다.
- 주요 단점: 완료 폴더가 `docs/work/`에 누적된다. 조망은 `docs/work/` 목록과 `git log`로 대체한다.

## 배경

현행 규정에는 아카이빙 개념이 없다. [wf-implement §7](../../../skills/wf-implement/SKILL.md#7-작업-기록과-저장-위치)은 "계획 항목 하나를 완료할 때마다" 작업 기록을 갱신하라고만 하고, 완료된 작업 기록은 영구히 그대로 남는다. 사용자는 "작업기록, 인계절 등의 작업중 쌓이는 로그들의 적절한 아카이빙 타이밍"(요구 4)을 요청했다.

실측(2026-10-09): 작업 기록 8편 중 가장 최근 것이 234행·26KB로 최대이며, 인계·재개 지점·현재 상태·완료 보고 인계처럼 열린 작업의 재개를 위한 절이 완료 후에도 그대로 남아 있다. 훅은 머리말의 상태만 읽고, 완료 작업 폴더로 들어오는 링크는 40여 곳이다.

## 영향을 받는 요구사항과 제약

- [FR-04](./req-design.md#기능-요구사항) — 아카이빙 시점. [FR-08](./req-design.md#기능-요구사항) — 자기 적용.
- [NFR-01](./req-design.md#비기능-요구사항) — 완료 문서 보존. 소급 편집·이동 금지와 정합.
- [wf-design DCR 절차 §1](../../../skills/wf-design/references/design-change.md) "완료는 당시 기준선에 대한 사건 기록" — 완료 기록을 되돌리거나 고쳐 쓰지 않는다는 원칙과 같은 방향.
- 훅(`setup/hooks/wf-common.ps1`)은 `docs/work/*/work-log.md` 머리말 상태로 열린 작업을 고른다. 위치 이동은 훅에 영향이 없지만, 이동한 폴더는 훅의 탐색 범위에서 빠진다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. 달력 기준(완료 후 N일·월) `docs/work/archive/`로 이동 | `docs/work/`가 작게 유지 | 시점이 작업 상태와 무관해 자동화 없이는 잊힌다. 이동마다 들어오는 링크 수리. 완료 문서 불변 원칙과 충돌 | 링크 40여 곳 + 매번 반복 |
| B. 완료 즉시 `docs/work/archive/`로 이동 | 열린 작업만 `docs/work/`에 남아 조망이 쉽다 | 링크 수리 비용은 A와 같다. `requirements.md`·`design.md`·`decisions.md`의 추적 링크가 모두 바뀐다. 훅 이점 없음 | 링크 40여 곳 + 매 완료 시 |
| C. 상태 전이 시 축약 + 제자리 동결 (채택) | 재개용 절은 열려 있는 동안만 존재. 링크 불변. 훅·등록부·추적표 무영향. 완료 문서 불변 원칙과 정합 | 완료 폴더 누적. 완료 로그 안의 수행 기록은 그대로 남는다(git이 정본이지만 파일도 남음) | wf-implement §7 소절 1개, 인계 축약 규칙 1문단 |
| D. git 태그·브랜치만 사용, 문서는 손대지 않음 | 규칙 변경 없음 | 사용자가 지적한 "쌓이는 로그"가 그대로 남는다. 요구 4 미충족 | 없음 |

## 결정

대안 C를 채택한다. 트리거와 행동은 다음과 같다.

| 트리거(상태 전이) | 행동 | 소유 |
|---|---|---|
| TASK `in-progress → completed` | 그 TASK의 수행 기록 항목을 한 번 확정해 쓴다(결정과 이유·발견·검증·결과). 이후 수정하지 않는다. 진행 중 메모는 항목이 아니라 인계 절의 다음 행동에만 둔다 | wf-implement §3.2·§7 |
| 작업 `in-progress → completed`(완료 보고 종결) | 인계 절을 축약(다음 단계 `없음`, 완료된 항목, 미완료 `없음`, 다음 행동 `없음`; 재개 프롬프트·미커밋 변경·시작 조건 제거). 기준선과 현재 계획의 진행 서술 삭제. `docs/status.md` 행 제거 | wf-implement §7, wf-doc §2.7 |
| 완료 이후 | 폴더·파일을 이동하지 않고 편집하지 않는다(역방향 링크 행 추가만 허용). 이력은 git이 정본 | wf-implement §7 |

`on-hold`·`blocked` 전이는 기존 규정(원인·영향·재개 조건·다음 책임자 기록)을 유지하며 축약 대상이 아니다.

## 이유

- 재개에 필요한 정보(다음 행동, 미커밋 변경, 재개 프롬프트)는 작업이 열려 있는 동안만 의미가 있다. 완료 시점에 지우는 것이 가장 자연스러운 "아카이빙 타이밍"이며, 사용자가 받아들인 방향(2026-10-09 세션)과 같다.
- 수행 기록 항목을 완료 시 한 번 쓰면 진행 중 누적되는 중간 서술이 사라진다. 세션이 중간에 끊겨도 인계 절이 재개 지점을 보장하므로 정보 손실이 없다.
- 이동은 비용만 있고 이점이 없다. 훅은 상태로 판정하고, 추적 링크는 경로에 의존한다.

## 결과와 감수할 단점

- `docs/work/`에 완료 폴더가 누적된다 → `docs/status.md`가 열린 작업만 보여 주고, README가 `docs/work/` 목록과 git을 조망 수단으로 안내한다(사이클 1 DES-07).
- 완료 로그의 수행 기록은 축약되지 않는다 → 처음부터 짧게 쓰도록 필드·상한·린트(FR-01·02·06)가 막는다. 사후 축약보다 작성 시 제한이 조사의 결론(도입 시점 차단)과 맞다.
- 인계 절 축약으로 완료 로그에서 재개 프롬프트가 사라진다 → 완료 작업은 재개 대상이 아니며, 후속은 완료 보고의 후속 작업 절이 가리킨다.
