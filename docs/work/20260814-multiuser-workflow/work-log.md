## 토론 기록

### 2026-08-14 — 제1라운드: 다인 사용 예측과 장단점

사용자 질문: 지금까지 1인 사용자가 설계·구현·검증을 실행하는 것을 가정했는데, 2명 이상의 개발자가 이 워크플로우를 적용하면 실제로 어떻게 사용하게 되고 어떤 장단점이 발생할 것인가.

분석 방법: 네 스킬의 규정을 통독하고 각 규정이 다인·동시 작업에서 어떻게 작동할지 추적(아래는 규정 인용에 근거한 **예측·해석**이며 실측 사실이 아님). 전제 시나리오: 개발자 2~5명, 각자 자기 Claude 세션, 공유 저장소에서 git 브랜치 + PR 흐름.

#### 예측되는 실제 사용 모습

1. **작업 폴더는 자연스럽게 병렬화된다.** `docs/work/<작업-ID>/`가 작업별로 분리되어 있어 개발자 간 work-log 충돌이 없다. 이 부분은 설계 변경 없이 확장된다.
2. **승인 관문은 "자기 승인"으로 변질된다.** [wf-design §8](../../../skills/wf-design/SKILL.md#8-사용자-승인-관문)의 승인권자는 "사용자" 단수인데, 각 세션에서 "사용자"는 그 개발자 본인이다. 초기에는 각자 자기 설계를 자기가 승인해 관문이 개인 체크포인트로 작동하고, 기준선 충돌 사건을 겪은 뒤 팀은 관문을 비동기 리뷰("설계 승인 = 문서 PR을 지정 승인권자가 approve")로 재해석할 것이다. wf-doc의 상태 어휘(`awaiting-approval`, `on-hold`의 "다음 책임자")는 이미 비동기 승인을 표현할 수 있어, 바뀌는 것은 상호작용 방식이다.
3. **충돌은 싱글턴 5파일에 집중된다.** `requirements.md`·`design.md`·`plan.md`·`decisions.md`·`status.md`는 [저장소 관통 현행 문서](../../../skills/wf-design/SKILL.md#6-산출물)라 모든 작업이 갱신한다. 최악은 `plan.md` — [wf-tree 갱신 시점 규칙](../../../skills/wf-tree/SKILL.md#갱신-시점)이 진행 상태 갱신마다 트리 재생성을 요구해 mermaid·ASCII 블록이 브랜치마다 갈라지고 git이 자동 병합하지 못한다. 완화 요인: [단일 소스 원칙](../../../skills/wf-tree/SKILL.md#단일-소스-원칙)(목록이 정본, 트리는 파생물) 덕에 "목록만 병합하고 트리는 병합 후 재생성"이라는 해법이 명확하다.
4. **전역 번호 발행이 가장 날카롭게 부러진다.** [결정 등록부의 전역 일련번호](../../../skills/wf-design/SKILL.md#62-결정-등록부)는 "등록부의 마지막 번호 다음"을 발행하는데, 두 브랜치가 동시에 ADR-007을 발행하면 병합 시 충돌한다. 번호가 파일명(`ADR-007-*.md`)과 모든 하이퍼링크에 박혀 있고 wf-doc이 식별자 재사용을 금지하므로 재번호 부여 자체가 규정 위반이 되어 복구가 어렵다. [기준선 vN](../../../skills/wf-design/SKILL.md#6-산출물)도 같은 구조 — 동시 재승인이 v3을 두 개 만드는데, 기준선 번호는 선형 역사를 전제하고 git의 진실은 브랜치 모양이다.

#### 장점 — 다인용에서 오히려 커지는 가치

- **문서가 곧 공유 상태 → 인수인계 비용 급감.** "대화에만 존재하는 결정은 사라진 것" 원칙과 [상시 재개 가능 불변식](../../../skills/wf-implement/SKILL.md#7-작업-기록과-저장-위치)은 세션 간 연속성 장치인데, 다인 상황에서는 **사람 간 연속성**이 된다. 재개 절차가 사람을 특정하지 않으므로 B의 AI가 재개 프롬프트 하나로 A의 작업을 이어받을 수 있어 버스 팩터가 구조적으로 낮아진다.
- **DCR이 "관료제"에서 "핵심 기능"으로 승격.** 1인에게 다소 무거운 DCR 절차(보류→초안→재승인→새 기준선)가 다인에서는 정확히 필요한 것 — B가 A의 기준선과 충돌을 발견했을 때 조용히 공유 계약을 고치는 대신 [정해진 반환 흐름](../../../skills/wf-implement/SKILL.md#wf-design과의-역할-경계)을 따른다. 사실상 경량 변경관리위원회가 내장된 셈.
- **추적성 강제 → 리뷰 품질 상승.** PR 리뷰어가 요구사항→설계→TASK→검증 증거의 링크 사슬을 받아 리뷰가 "코드 고고학"이 아니라 "증거가 주장을 뒷받침하는가" 검사가 된다.
- **완료의 증거 문화.** "실행하지 못한 검증은 성공이 아니다" + 검증 증거의 실행 환경 필수 기록이 다인 고전 문제 "내 환경에서는 됐는데"를 차단한다.
- **포트폴리오 계층이 진짜 청중을 만난다.** `docs/status.md`의 작업 트리·`depends:`·롤업은 1인에게 사치스럽지만 팀에게는 그대로 스탠드업 대시보드다. 모든 팀원의 AI가 같은 포맷으로 산출물을 내므로 남의 작업을 읽는 비용이 균일하게 낮다 — 워크플로우가 사람 간 계약이자 **AI 세션 간 프로토콜**로 작동한다.

#### 단점 — 마찰 3축

| 축 | 문제 | 관련 규정 |
|---|---|---|
| 동시성 | 싱글턴 5파일 병합 충돌, 트리 재생성 churn | [산출물 구조](../../../skills/wf-design/SKILL.md#6-산출물), [트리 갱신 시점](../../../skills/wf-tree/SKILL.md#갱신-시점) |
| 식별자 | ADR/DCR 전역 번호·기준선 vN·TASK-NN 발행 경쟁, 재번호 불가 | [전역 번호](../../../skills/wf-design/SKILL.md#62-결정-등록부), [기준선 규칙](../../../skills/wf-design/SKILL.md#6-산출물) |
| 거버넌스 | "사용자" 단수 전제, 역할·승인권 미정의, 기준선 발효 시점 부재 | [승인 관문](../../../skills/wf-design/SKILL.md#8-사용자-승인-관문) |

상세:

- **기준선의 브랜치 문제.** A 브랜치에서 DCR 승인으로 design.md가 v3이 되어도 main 병합 전까지 B는 v2로 계획한다. [wf-implement §3.1 재확인](../../../skills/wf-implement/SKILL.md#31-현재-상태-재확인)이 rebase 시점에 일부를 잡지만, "어느 브랜치의 기준선이 유효한가", "승인 시점과 발효 시점의 구분"에 대한 어휘가 없다. 같은 설계 절을 건드리는 동시 DCR 2건의 순서를 강제하는 장치도 없다.
- **같은-변경(same-change) 의무의 침식.** 역방향 링크·등록부·트리를 "같은 변경에서" 갱신하라는 규정은 저장소 스냅숏 하나를 전제한다. 각 세션은 자기 스냅숏에서 자체 검토를 통과하지만, 병합 후 main은 아무 세션도 검사하지 않은 조합 상태가 된다(끊어진 역링크의 사각지대). 충돌 고통이 누적되면 갱신을 몰아서 하게 되어 "손실은 마지막 갱신 이후 분량" 보증이 약해진다. **규칙이 깨진다기보다 규칙 준수 비용이 동시성으로 증폭되어 자연 침식되는 것**이 예측되는 실패 양상.
- **작업 소유권 신호 부재.** 진행 중 work-log의 존재가 약한 점유 신호일 뿐, "다른 사람의 in-progress 작업을 건드리지 말라"는 규정이 없다. 두 세션의 AI가 동시에 design.md를 고치는 것을 막는 것은 현재로선 git 충돌뿐이다.

#### 팀이 자생적으로 만들 관례 (수렴 예측)

1. **발효 규칙:** 기준선 번호·전역 번호는 main 병합 시점에 확정, 브랜치에서는 `ADR-draft-<슬러그>` 임시 표기 — 승인(사람의 결정)과 발효(main의 사실)의 분리.
2. **관문 재매핑:** 설계 승인 = 문서 PR approve, APR 기록에 실명 기입("승인자를 모르면 `사용자`" 규칙은 다인용에서 폐기됨).
3. **plan.md 분할:** 작업별 계획은 작업 폴더로 내리고 plan.md는 색인화, 트리 재생성은 main 병합 후 1회(CI 훅 후보).
4. **담당자 필드:** work-log·포트폴리오에 담당자 추가 — wf-doc에서 유일하게 사람-역할이 등장하는 `on-hold`의 "다음 책임자"를 상시 필드로 승격하는 자연스러운 확장.

#### 종합

- 세션 간 **순차** 인계용 장치(문서 정본주의, 재개 불변식, 증거 강제)는 다인 개발의 요구와 일치 — 순차 협업(인수인계·리뷰·재개)은 현행대로 탁월하다. 부족한 것은 **병렬성**: 싱글턴 파일 배치·선형 일련번호·단수 승인자라는 1인용 가정 3개가 동시 작업에서 전부 경쟁 조건이 된다.
- 대칭 관찰: 1인용에서 부담스럽던 것(DCR·경계 규정)이 다인용의 핵심 가치가 되고, 1인용에서 빛나던 것(매 갱신 재생성되는 계획 트리)이 다인용 최대 충돌 유발원이 된다.
- 세 가정 모두 철학이 아닌 기계적 선택이라 수정 가능: 네임스페이스(전역 번호→작업 스코프), 발효 규칙(병합=발효), 역할 모델(승인권자 지정)이면 골격을 바꾸지 않고 다인용이 된다.
