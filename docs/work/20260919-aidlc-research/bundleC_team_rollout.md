## 0. 이번 묶음의 결론 한 줄

**팀 확장은 리뷰 인원을 늘리는 문제가 아니라, 1인 감독(업계 현실 78.9%)을 전제로 그 1인이 남기는 외재화된 증거·메모리를 팀 자산으로 승격하는 파이프라인 문제다.** 그리고 가장 시급한 실행 항목은 뜻밖에 단순하다 — 현재 전역 설치(~/.claude) 모델 때문에 **팀원들이 작업할 제품 리포는 논문 기준 L1(미설정)**이며, 이는 도입 후 품질 저하가 2배로 나타난 바로 그 상태다.

# 1. A Few Pages of Markdown — RAMP 성숙도와 품질 비용

## 1.1 RAMP 4단계 (재확인 완료)

| 레벨 | 이름 | 판별 산출물 |
|---|---|---|
| L1 | Unconfigured | AI 관련 커밋 파일 없음 |
| L2 | Grounded Prompting | context 산출물 ≥1: rules(CLAUDE.md·.cursorrules·copilot-instructions.md 등), configuration, architecture 문서, code-style |
| L3 | Agent-Augmented | capability 산출물 ≥1: 명명된 agents, commands(슬래시 명령), **skills(200–600줄 도메인 가이드)**, MCP 설정 |
| L4 | Orchestration | coordination 산출물: flows(단계·의존성 있는 실행 계획), session-logs(타임스탬프·수정 파일·커밋 SHA·결과) |

누적 위계는 Guttman scalogram CR=0.997로 확인. 분류기는 12개 도구·43개 패턴 탐색 + 임베딩 의미 분류, 리포 수준 인간 일치 97.1%. **git 훅·CI·PR 템플릿은 산출물 목록에 없음.**

기업 리포 441개 분포: **L1 66.7% / L2 24.7% / L3 8.6% / L4 0%.** rules 파일은 L2의 98.2%가 보유 — 사실상의 진입 산출물.

## 1.2 결과 (OSS 509개, staggered DiD, Borusyak 추정량, 재확인 완료)

| 지표 | L1 (미설정, 236개) | L2+ (설정, 273개) | 비율 |
|---|---|---|---|
| 인지 복잡도 | **+52.7%*** | +26.7%** | 2.0× |
| 정적 분석 경고 | +24.1%** | +14.0%* | 1.7× |
| 중복 라인 밀도 | +15.4%* | +14.2%** | 1.1× |
| 월별 커밋(속도) | +37.6%*** | +27.5%*** | — |
| 추가 LOC(속도) | +48.1%* | +68.7%*** | — |

**속도 이득은 성숙도와 무관하게 오고, 갈리는 것은 품질이다.** 이벤트 스터디에서 도입 전 평행 추세 확인 — 괴리는 도입 후 발생. 단 L2/L3/L4 개별 효과와 산출물 유형별 분해는 표본 제약으로 없음(L2+ 병합).

## 1.3 정적 성숙도 — "몇 페이지의 마크다운"이 제목인 이유

- 산출물의 **73.8%가 한 번 커밋 후 수정 없음**(set-and-forget). 도입자의 83.1%는 단발 진입, 레벨 하강 0%.
- 첫 AI 산출물까지 리포 이력 중앙값 633일; L2→L3 전이는 14.9%(중앙값 154일); **L3→L4 전이 0건**.
- 수정 빈도와 성숙도의 연관은 산출물 개수를 통제하면 소멸(partial ρ=−0.072) — 즉 완화 효과와 연관된 것은 지속적 관리가 아니라 **한 번 잘 커밋된 내구성 있는 선택**이다.

## 1.4 인과 주장의 한계 (팀 설득 시 표현 주의)

저자 스스로 "hypothesis-generating"으로 규정: "성숙도는 관측적이므로 상관된 엔지니어링 규율이나 모델 역량이 격차의 일부를 설명할 수 있다." 고성숙 리포는 도입 전부터 활동량이 많았다. **안전한 문장: "커밋된 설정 없이 도입한 리포는 품질 저하가 2배로 나타나는 패턴에 놓인다(연관)"** — "커밋하면 절반이 된다(인과)"가 아니다.

## 1.5 사용자 저장소의 RAMP 자리매김 — 결정적 발견

- **llm_workflow 저장소 자체**: rules(CLAUDE.global.md·AGENTS.codex.md) + architecture(docs/requirements·design·decisions) → L2 충족. skills 4개(219–375줄, 논문의 skills 정의 200–600줄에 정확히 부합) → **L3 확정**. work-log(타임스탬프·수정 파일·커밋 SHA·결과)와 plan.md 계획 트리는 session-logs·flows에 근접 → **L4 논쟁 가능**. 기업 표본 상위 8.6% 이상.
- **그러나 설치 모델이 함정이다.** junction/symlink로 `~/.claude/`에 사용자 전역 설치하므로, **팀원들이 실제 작업하는 제품 리포에는 커밋된 AI 파일이 0개 = L1.** 논문의 완화 연관은 "리포에 버전 관리된 파일"에 대한 것이고, 커밋되어야 전 기여자에게 균일 적용된다.

# 2. Shared Organizational Memory — 팀 메모리 파이프라인 (SAP 프로덕션)

## 2.1 구조: 수집 → 큐레이션 → 소비

- **수집**: "fly-on-the-wall" — 모든 산출물이 아니라 **지정된 지식베이스 파일**(AGENTS.md, `.claude/` 등)의 편집만 관찰. PostToolUse(파일 쓰기 후 dirty 표시)·Stop(작업 종료 시) 훅 2종. diff를 준비해 **기여자 본인에게 전송 허가 요청**(리뷰 큐·관리자 승인 없음).
- **큐레이션**: Enrichment Agent(diff → **질문+답변+동작 예제+caveats**의 Q&A 항목, "근거 없는 주장 도입 금지"), Bucketing(태그), Security Scan(6범주 결정적 검사: 의존성·시크릿·코드·PII·워크플로우·근거 — "Any Unsafe dominates", 합성 테스트에서 unsafe 수용 0건), Collision Checker(중복 거부·시맨틱 링크), Trust Score(0–10, 베이지안 평균).
- **소비**: **자동 주입이 아니라 질의 기반** — 에이전트가 MCP로 검색(Fast/Normal/Deep 3티어, 질문·답변 별도 임베딩 0.7/0.3 융합).

## 2.2 배포 수치와 한계

기여 learnings 900건 → 저장 483건(53.7%), 큐레이션 메모리 1,144개(생산적 기여당 2.37개), 96.2%가 시맨틱 링크 보유(총 7,863개, 35개 도구에 걸침). 한계: "효과는 평가 중", trust score 미캘리브레이션, 선별된 내부 팀 한정. **46.3%가 걸러졌다는 것 자체가 큐레이션 없는 원문 공유의 잡음을 시사.**

# 3. Early Adoption — 1인 검토가 지배하는 현실

25,264 에이전틱 PR·2,361 리포(별 100+, 2025.5–7, Copilot·Codex·Claude Code). 관여 측정은 리뷰·토론·커밋·종결을 포괄.

- 지배 패턴: **"리뷰어 1인 + 커미터 1인 = 동일인" 19,488건(78.9%)** — 프롬프트한 사람이 검토하고 직접 수정. "수정 없이 수용" 9.8%. **다인 협업은 전부 합쳐 11.3%.**
- 도입 강도: 중앙값 리포는 3개월간 1–2건(탐색적 실험 수준). 소규모 팀(1–5명)이 평균 **50.2건**으로 중·대규모(5.6·6.7건)를 압도(η²=0.616). 참여자당 36건 초과는 1%(25개). 42%의 프로젝트는 기여자 5% 미만만 참여.
- 한계: 인기 공개 리포 한정, PR 건수는 크기·품질·리뷰 노력을 반영 못함.

# 5. 팀 배포 설계안

## 5.1 1단계 — 제품 리포를 L1에서 L2+로 (최우선, 근거 최강)

1. **각 제품 리포 루트에 rules 파일 커밋**: CLAUDE.global.md의 6줄 규칙을 리포별 `CLAUDE.md`+`AGENTS.md`로. (rules는 L2의 98.2%가 보유한 진입 산출물; L2+는 복잡도 증가 절반. 묶음 A의 "비표준 관행만" 원칙과 결합 — 개요 넣지 말 것.)
2. **전역 설치 → 리포 커밋 전환**: 훅 등록·스킬 참조를 리포 내 `.claude/` 설정으로. 커밋되어야 전 기여자 균일 적용 + RAMP 증거 기준 충족.
3. **스킬을 리포에서 참조 가능하게** (서브모듈 또는 복사): L3 산출물. 단 L3의 추가 완화 효과는 논문에서 미검증 — L2 확보 후의 증분 투자로 취급.
4. **유지보수 부담은 걱정하지 않는다**: 73.8% set-and-forget, 역행 0%. "한 번 잘 커밋"이 현실적 목표이고, 살아있는 decisions.md·work-log 관행은 이미 업계 규범을 상회.
5. **L4 오케스트레이션을 배포 전제로 삼지 않는다**: 기업 표본 L4 0개, L3→L4 전이 0건.

## 5.2 2단계 — work-log·decisions.md의 팀 메모리 승격 (SAP에서 빌릴 것/버릴 것)

**빌릴 것:**
- **캡처는 워크플로우의 부산물로.** 이미 훅 3종 + work-log 갱신 불변식이 있으므로, "work-log·decisions.md 변경 diff → 재사용 가능 항목 추출" 단계만 추가(Stop/PostToolUse 훅 재사용 — 묶음 B의 훅 인프라와 합류).
- **Q&A 변환(Enrichment).** work-log 원문은 작업 맥락에 묶여 있다. 팀 메모리 항목은 "질문 + 답변 + 동작 예제 + caveats"의 자기완결형으로 재작성. SAP에서 46.3%가 걸러진 것은 이 필터링이 실질적임을 보여줌.
- **기여자 본인 승인 + 자동 보안 게이트**(시크릿·PII 스캔 — 묶음 B의 S16 훅과 동일 지점). 리뷰 큐 없이 안전 확보.
- **시맨틱 링크**: decisions.md의 "대체·관련" 열이 이미 원형 — 팀 메모리 항목에도 같은 열 유지.

**버릴 것:** 벡터 검색·리랭커·trust score 인프라. 소규모 팀에 과잉이고 SAP조차 효과 미평가. **git 저장소 + grep 가능한 Markdown + 태그**로 시작. 단 SAP의 원칙 하나는 유지 — **자동 주입이 아니라 질의 기반**(세션 시작 훅에 주입량을 늘리지 말고, 필요할 때 검색하게).

구체 형태 제안: `docs/team-memory/` 디렉터리에 항목당 1파일(`TM-NNN-<슬러그>.md`: 질문/답변/예제/caveats/태그/관련), 색인은 decisions.md와 같은 등록부 방식.

## 5.3 3단계 — 리뷰 프로세스: 1인 감독 현실에서 시작

2인 리뷰 강제는 채택률만 죽인다(78.9% 현실 + 참여자당 36건 초과가 1%뿐인 저강도 도입기).

1. **기본은 1인(프롬프터=리뷰어) + 증거 강제.** wf-implement의 "실행하지 못한 검증은 성공이 아니다"와 검증 증거 링크 사슬이 1인 리뷰의 품질 바닥을 받친다 — 사람을 못 믿어도 증거는 검사할 수 있다. S9 Stop 게이트(묶음 B)가 이 바닥을 기계로 받친다.
2. **위험 기반 2인 격상.** §2.3의 외부·비가역 작업 목록(공개 인터페이스·데이터 모델·보안·마이그레이션)과 ADR/DCR 승인만 타인 approve 요구 — 새 개념 없이 기존 목록을 트리거로 재사용.
3. **자동 게이트를 제2 리뷰어로.** CI에서 시크릿·정책·정적 분석을 실행(SAP의 결정적 6범주 축소판). RAMP 산출물엔 CI가 없지만, 품질 지표(1.2)의 근거로 정당화된다.
4. **"수정 없이 수용"(9.8% 패턴)은 금지 대신 조건부**: work-log에 검증 증거가 없는 무수정 병합만 차단.
5. **승인 역할 분리**(기존 §8 어휘 재사용): 설계 승인권자 = 기준선 확정("문서 PR approve = 승인", APR에 실명), 외부 작업 승인권자 = 저장소 권한 보유자(§2.3의 별도 확인 규정이 그대로 역할 분리가 됨), 기여자 본인 = 팀 메모리 승격 opt-in.

## 5.4 배포 KPI

- **품질(주 지표)**: SonarQube류 인지 복잡도·경고·중복도를 도입 전후로 리포별 추적. 속도(커밋 수)는 설정과 무관하게 오르므로 성공 지표로 쓰지 않는다.
- **도입 건강도**: 참여율(기여자 중 에이전틱 PR 참여 비율 — 42%가 5% 미만인 현실 대비), 리포당 에이전틱 PR 수(중앙값 1–2가 기준선), 다인 관여 비율(11.3%가 기준선).
- **메모리 파이프라인**: 기여→저장 전환율(SAP 53.7%가 참조점), 항목당 링크 수, 검색 사용 빈도.
- 소규모 팀부터 시작(小팀이 50.2건으로 압도 — 도입 마찰이 낮은 곳에서 관측 데이터를 먼저 확보).
