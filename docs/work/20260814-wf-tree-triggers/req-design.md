## 문제와 목적

검수(2026-08-14)로 확인된 사실: wf-tree의 적용 시점(§1)은 전부 사용자 요청 기반이고, 유일한 자동 갱신 트리거(wf-implement §3.2 "계획을 트리로 구조화한 작업은…")는 트리가 이미 존재해야만 발동하는 조건부다. 트리를 최초로 만들라는 규정이 어느 스킬에도 없어 트리거 체인이 opt-in 데드락 상태이며, 실증적으로 이 저장소의 완료된 두 사이클(TASK-01~15) 동안 `## 계획 트리` 절이 한 번도 생성되지 않았다.

추적 결과 TASK가 생성·변경되는 세 경로(최초 계획, DCR 반영, 새 사이클)는 모두 wf-implement §3.2 계획 수립으로 수렴한다. 따라서 §3.2에 채택 결정과 최초 생성 트리거를 심으면 전 경로가 커버된다.

## 범위

### 포함

- `skills/wf-implement/SKILL.md` — §3.2 트리 채택 결정·최초 생성·재생성 트리거, §5 완료 조건 동기화 항목, 경계표 용어 정리
- `skills/wf-doc/references/templates.md` — plan 템플릿 노트에 채택 결정 소유자 명시, work-log 템플릿의 죽은 필드 제거
- `skills/wf-tree/SKILL.md` — §1 적용 시점에 워크플로우 이벤트 트리거 추가, frontmatter description 갱신

### 제외

- 포트폴리오(`docs/status.md`) 생성·승인 절차 변경 — wf-tree §8 현행 유지 (이번 문제는 작업 내부 트리의 트리거 부재)
- 루트 `SKILL.md`·`setup/AGENTS.codex.md`의 진입 문구 변경 — 두 파일 모두 저장소 스킬 파일을 직접 참조하므로 wf-implement §3.2의 링크만으로 새 경로가 작동한다. 진입 문구의 기존 서술(사용자 요청 기반)도 여전히 참이다
- 기존 완료 문서의 소급 수정 — 완료된 plan.md 사이클·work-log에 트리를 소급 생성하지 않는다
- C층 훅, B층 린트, 설치 스크립트 — 변경 없음

## 기능 요구사항

- FR-01 (채택 결정): wf-implement 계획 수립(§3.2)은 계획을 수립·갱신할 때 계획 트리 사용 여부를 결정해야 한다. 채택 기준: 작업이 3개 이상이거나, 분해(`상위:`)·OR-분기·작업 간 의존이 있거나, 작업이 포트폴리오에 속하면 사용한다. 그 외에는 생략할 수 있으며, 진행 중 조건을 충족하게 되면 그 시점부터 트리를 시작한다.
- FR-02 (최초 생성·재생성): 트리를 사용하는 계획은 TASK를 처음 작성하는 같은 변경에서 `## 계획 트리` 절을 wf-tree 렌더링 규칙으로 생성해야 하고, 이후 작업 목록·상태가 갱신될 때마다 같은 변경에서 재생성해야 한다(기존 §3.2 갱신 문장의 확장).
- FR-03 (완료 안전망): wf-implement 완료 조건(§5)에 "트리를 사용한 계획이면 계획 트리가 작업 목록과 동기화되었다" 항목이 있어야 한다.
- FR-04 (결정 소유자 명문화): wf-doc plan 템플릿 노트는 트리 사용 여부의 결정 소유자가 wf-implement 계획 수립임을 링크로 명시해야 한다.
- FR-05 (죽은 필드 제거): wf-doc work-log 템플릿의 `작업 트리 상태:` 필드를 제거한다. 근거: 어느 스킬도 기입 주체·의미를 규정하지 않는 죽은 필드이고(실사용 work-log 2건 모두 생략), git working tree 의미라면 재구성 가능 정보라 wf-implement §7 불변식(간결 유지)과 상충하며, 계획 트리 의미라면 plan.md와의 이중 소스가 된다.
- FR-06 (용어 구분): wf-implement에서 git working tree 의미로 쓰인 "작업 트리"(경계표 저장소 조사 행)를 "저장소 상태"로 바꿔 wf-tree의 "계획 트리"와 혼동을 없앤다.
- FR-07 (wf-tree 적용 시점): wf-tree §1과 frontmatter description에 "wf-implement 계획 수립이 트리 사용을 결정한 계획의 수립·갱신 시" 이벤트 트리거를 추가한다.

## 비기능 요구사항

- NFR-01 (경계 보존): 변경은 wf-tree 헌장의 소유권 경계(항목 의미·채택·상태는 내용 소유자, 트리 구조·렌더링 규칙은 wf-tree)를 바꾸지 않는다. §3.2에 추가하는 문장은 경계 요약이 아니라 호출 지시이므로 "상대 스킬에 별도 경계 요약을 두지 않는다" 원칙과 충돌하지 않는다.
- NFR-02 (하네스 중립): 추가·수정하는 모든 문구는 하네스 중립 어휘만 사용한다(특정 도구·제품 기능 언급 금지).
- NFR-03 (최소 변경): 변경 대상 절 밖의 문장·의미를 건드리지 않는 최소 diff로 구현한다.

## 인수 조건

- AC-01: wf-implement §3.2를 읽으면 (1) 트리 사용 결정 시점, (2) FR-01의 채택 기준, (3) 최초 생성과 상태 갱신 시 같은 변경 재생성 지시를 모두 확인할 수 있다.
- AC-02: wf-implement §5 완료 조건에 트리·작업 목록 동기화 항목이 존재한다.
- AC-03: wf-doc templates.md에서 (1) plan 템플릿 노트가 채택 결정을 wf-implement 계획 수립으로 링크하고, (2) work-log 템플릿에 `작업 트리 상태:` 필드가 없다.
- AC-04: `skills/` 전체에서 "작업 트리"를 검색하면 git working tree 의미의 잔존 사용이 0건이다(계획 트리와 구분되는 용어만 남음).
- AC-05: wf-tree §1에 wf-implement 계획 수립을 경유하는 이벤트 트리거 항목이 있고, description에도 반영되어 있다.
- AC-06 (실증): 이 작업 자체의 구현 계획이 새 규칙의 채택 기준을 충족하므로, 구현 단계에서 plan.md에 `## 계획 트리` 절이 `## 작업 목록` 바로 앞에 생성되고 TASK 상태 갱신 시 재생성됨을 관찰한다(신설 규칙의 자기 적용).

## 설계

- DES-01 (트리거 배치 — 단일 관문): 트리거는 wf-implement §3.2 계획 수립 한 곳에만 둔다. 최초 계획·DCR 반영([design-change.md §6](../../../skills/wf-design/references/design-change.md)이 §3.2 반환을 강제)·새 사이클의 세 경로가 모두 §3.2를 통과하므로 충분하다. 대안 비교와 기각 이유는 [ADR-003](./ADR-003-트리거-단일-관문.md).
- DES-02 (채택 기준): FR-01의 기준을 §3.2 본문에 그대로 기술한다. 기준은 계획 문서만으로 판정 가능해야 하며(작업 수·`상위:`·의존성·포트폴리오 존재), 판단 재량 문구("필요하면" 등)를 사용하지 않는다.
- DES-03 (문구 삽입 설계 — 구현 명세):
  1. `wf-implement/SKILL.md` §3.2: 진행 상태 갱신 문단 앞에 채택 결정·최초 생성 문단을 추가하고, 기존 "계획을 트리로 구조화한 작업은…" 문장을 "트리를 사용하는 계획은 작업 목록이나 상태를 갱신할 때 같은 변경에서 재생성한다"로 확장한다.
  2. `wf-implement/SKILL.md` §5: 완료 조건 목록에 동기화 항목 1행 추가.
  3. `wf-implement/SKILL.md` 경계표 "저장소 조사" 행: "작업 트리" → "저장소 상태".
  4. `wf-doc/references/templates.md`: plan 노트에 "트리 사용 여부는 wf-implement 계획 수립이 결정한다" 링크 문장 추가, work-log 템플릿에서 `- 작업 트리 상태:` 행 삭제.
  5. `wf-tree/SKILL.md` §1: 이벤트 트리거 불릿 추가("wf-implement 계획 수립이 트리 사용을 결정한 계획의 수립·갱신 시 — 같은 변경에서 생성·재생성"). description 끝에 동일 취지 한 문장 추가.
- DES-04 (죽은 필드 처리): 의미를 부여해 존치하는 대안을 기각하고 제거한다. 기각 이유: 계획 트리 의미 부여는 wf-tree 단일 소스 원칙(트리는 plan.md 작업 목록에서 파생)과 충돌하는 이중 소스를 만들고, git 의미 부여는 재구성 가능 정보의 스냅숏이라 낡은 기록이 오히려 재개를 오도한다.
- DES-05 (호환성): 규칙은 앞으로의 계획 수립·갱신에 적용한다. 완료된 과거 사이클 문서는 소급 수정하지 않는다(wf-tree §6 완료 상태 보존과 일관). 설치본은 정션 링크(`setup_claude.ps1` 확인: `~/.claude/skills` → 저장소 `skills/`)이므로 저장소 수정이 즉시 반영되며 별도 배포 단계가 없다. Codex 어댑터(`AGENTS.codex.md`)는 저장소 파일 직접 참조라 영향 없다.

## 위험

- RISK-01 (보일러플레이트): 모든 계획에 트리를 강제하면 작은 작업에 형식 부담 → FR-01 채택 기준(3개 이상 등)으로 완화. 기준 미달 계획은 생략 가능.
- RISK-02 (산문 규칙의 회귀 검증 불가): 스킬 텍스트는 자동 테스트가 없어 규칙 누락·오해가 늦게 발견될 수 있음 → FR-03 완료 조건 안전망 + AC-06 자기 적용 실증으로 완화.
- RISK-03 (경계 원칙과의 긴장): wf-tree 헌장 "상대 스킬에 경계 요약을 두지 않는다"와의 오해 소지 → NFR-01에 트리거는 경계 요약이 아님을 명시, wf-tree §1에도 역방향 참조를 두어 상호 발견 가능성 확보.

## 미해결 질문과 가정

- 가정 1: 채택 기준의 임계값(작업 3개 이상)은 이 저장소의 실사용(사이클당 6~9 TASK)에 비추어 보수적으로 잡았다. 승인 관문에서 조정 가능.
- 가정 2: 진입 문서(루트 SKILL.md, AGENTS.codex.md, 사용자 전역 CLAUDE.md)의 문구는 변경하지 않아도 새 트리거가 작동한다 — wf-implement를 읽는 순간 §3.2가 wf-tree를 지시하기 때문. 전역 CLAUDE.md는 저장소 밖이므로 어차피 범위 밖.
