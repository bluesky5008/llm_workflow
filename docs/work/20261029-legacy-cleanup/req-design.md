## 문제와 목적

사용자 요청(2026-10-29): 마켓플레이스 테스트를 「불필요한 것을 걷어내고 필수만」 남기고 싶다. 측정(저장소 밖 `D:/code/outputs/docs/marketplace-test-diet-2026-10-29/01-측정-보고.md`) 결과 백엔드 5,970건 중 라인 커버리지가 다른 한 테스트에 완전히 덮이는 테스트가 3,037건(54%), 파일 전체가 다른 파일에 덮이고 모든 테스트가 지배되는 A급 18파일 105건. 그런데 현행 규칙으로는 이 정리를 할 수 없다.

- 현행 재정비 관문(§3)은 **통합·DCR 승인 시점에, 이번 변경이 닿은 보호 스코프의 행**만 다룬다. 대장 전체를 범위로 하는 독립 작업 유형이 없다.
- 상태값은 `유지 · 대체 · 병합 · 격리 · 폐기` — 테스트를 **고쳐서 유지**(냄새 제거·mock→fake·subTest 통합)하는 전이가 없고, wf-implement §3.3은 진행 중 기존 테스트 수정을 금지한다.
- 4조건의 「유일 검증 아님」은 인수 조건 연결을 전제한다. 레거시 행은 AC 가 없다.
- 승인은 「완료 보고 관문에서 일괄」 한 가지다. 후보가 수백 건이면 건별 확인은 고무도장이 된다(04 R-16).

## 현재 상태 조사

### 확인된 사실

- 착수 HEAD `e1ffa64`, 워킹트리 clean. 열린 작업 없음(보류 1건 `20260814-multiuser-workflow`). 다음 ADR 번호 024.
- [verification-depth §2](../../../skills/wf-implement/references/verification-depth.md#2-상태와-전이): 상태 5종. `병합`·`폐기`는 관문 4조건, `대체`는 DCR 승인, `격리`는 즉시. "기존 행을 새로 쓴 테스트로 바꾸는 재생성은 … `병합`으로 보고 4조건" — 재생성은 있으나 **수정 후 같은 행 유지**는 없다.
- [§3 재정비 관문](../../../skills/wf-implement/references/verification-depth.md#3-재정비-관문): 시점 = 통합·DCR 승인. 증거 사다리 = ① 뮤테이션 kill 집합 보존 ② 커버리지 겹침 + 단언 대조 ③ 단언 대조. 분류 5종(`중복`·`동어반복`·`자명`·`신호 없음`·`고아`). 승인 = 완료 보고 관문의 일괄 응답.
- wf-implement SKILL.md:204 "진행 중에는 등록·격리 외의 전이와 기존 테스트의 수정·제외·삭제를 하지 않는다 — 정리는 통합의 재정비 관문에서만." 본문 2,793/2,850어절(K3 경고) — 본문 추가는 상쇄가 필요하다(선례 NFR-01 순증 0).
- 판독기 `regression_guard.py`(`state.startswith("유지")`)·`wf-common.ps1`(`StartsWith($kKeep)`)은 상태가 `유지`로 시작하는지만 본다. 새 상태값을 추가하면 그 행은 보호에서 빠진다.
- C층 가드 `wf-test-guard.ps1`(DES-06)은 Edit/Write 마다 `유지` 행 파일이면 `ask`. `wf-stop-gate.ps1`(DES-07)은 `regression_guard.py`를 호출하고, 위반 행 ID가 **열린 작업 기록의 `### 테스트 대장 변경` 절**에 있으면 통과한다(`recorded_ids`). 즉 배치 단위 기록이 이미 Stop 게이트의 「배치마다 1회」 역할을 하지만, PreToolUse 가드는 파일마다 묻는다. 04 D-6 결정: 「배치마다 1회. 승인 범위는 사람이 승인한 req-design 에서 읽고 plan.md 에서 읽지 않는다」 — 이것을 가드에 구현하려면 C층(DES-06) 변경 = DCR.
- 경량 경로 기계 조건(제품 코드 변경 ≤ 5파일)상 수십 파일 정리는 정식 경로다. 04 R-14 도 「판단과 사용자 승인이 많아 경량 경로에 맞지 않는다」.
- 이 저장소에 뮤테이션·커버리지 도구 없음(D-3: 수동 LLM 뮤턴트 시범). 마켓은 2026-10-29 측정에서 coverage.py 테스트별 컨텍스트로 지배 관계를 얻었고 뮤테이션은 없다.
- 선례: [REQ-DESIGN-legacy-onboarding](../20261028-legacy-onboarding/req-design.md)·ADR-023 — 새 상태값·열 없이 진입 경로와 괄호 표기만 추가, 판독 무변경(NFR-02), 본문 순증 0(NFR-01).
- 04 「레거시 정비 작업의 성공 기준 후보」: 배치마다 (1) kill 집합 합 ≥ 정비 전 (2) `유지` 전량 통과 (3) 제품 코드 diff 0 (4) 폐기·병합·리팩터 행마다 분류·증거·승인 (5) 실행 시간·격리 수 전후 기록.

### 해석

- R-14 는 새 워크플로우가 아니라 **정식 경로 작업의 한 종류**로 표현할 수 있다 — req-design 에 「대상 TST 범위·배치·성공 기준」 필수 절을 요구하고, verification-depth 에 「독립 재정비 작업」 절(시점·범위·제품 코드 동결·배치 TASK·관문 적용 방식)을 두면 된다.
- R-15 의 `리팩터`는 **새 상태값 없이** `유지` 를 유지한 채 재정비 기록·대장 변경 절에 「리팩터」 분류로 남기는 편이 판독 무변경(선례)과 맞다. 증거 = 같은 제품 SHA 에서 수정 전·후 통과 + kill 집합(또는 단언 집합) 비감소.
- 유일성(AC 없음)은 증거 사다리 ①(다른 행이 못 죽이는 뮤턴트)을 1순위로, 도구가 없으면 ③ 단언 대조 + 커버리지 유일 라인(마켓 측정의 `unique_lines`)을 **후보 선별 신호**로 쓰되 단독 근거로는 쓰지 않는 쪽이 §3 「겹침은 후보 신호」 원칙과 맞다.
- R-16 은 04 제안 그대로(`고아` 목록 일괄, 판단 분류는 배치별 행 승인) 가정으로 둘 수 있다 — 해석이 갈리지 않는다.

### 가정

- A-01 R-16 승인 계층: `고아`(파일·심볼 부재)는 목록 일괄 승인, `중복`·`동어반복`·`자명`·`신호 없음`·`리팩터`는 배치별 행 승인(04 제안). 결과를 바꾸지 않아 질문하지 않는다.
- A-02 제품 코드 동결: 재정비 작업은 테스트·대장·문서만 바꾼다. 제품 코드가 필요하면 별도 작업(04 R-14).
- A-03 성공 기준의 수치 목표(실행 시간 등)는 저장소별 req-design 이 정한다(04).
