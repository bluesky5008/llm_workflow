## 문제와 목적

사용자 요청(2026-10-29): 마켓플레이스 테스트를 「불필요한 것을 걷어내고 필수만」 남기고 싶다. 측정(저장소 밖 `D:/code/outputs/docs/marketplace-test-diet-2026-10-29/01-측정-보고.md`) 결과 백엔드 5,970건 중 라인 커버리지가 다른 한 테스트에 완전히 덮이는 테스트가 3,037건(54%), 파일 전체가 다른 파일에 덮이고 모든 테스트가 지배되는 A급 18파일 105건. 그런데 현행 규칙으로는 이 정리를 할 수 없다.

- 현행 재정비 관문(§3)은 **통합·DCR 승인 시점에, 이번 변경이 닿은 보호 스코프의 행**만 다룬다. 대장 전체를 범위로 하는 독립 작업 유형이 없다.
- 상태값은 `유지 · 대체 · 병합 · 격리 · 폐기` — 테스트를 **고쳐서 유지**(냄새 제거·mock→fake·subTest 통합)하는 처분이 없고, wf-implement §3.3은 진행 중 기존 테스트 수정을 금지한다.
- 4조건의 「유일 검증 아님」은 인수 조건 연결을 전제한다. 레거시 행은 AC 가 없다.
- 승인은 「완료 보고 관문에서 일괄」 한 가지다. 후보가 수백 건이면 건별 확인은 고무도장이 된다(04 R-16).

## 현재 상태 조사

### 확인된 사실

- 착수 HEAD `e1ffa64`, 워킹트리 clean. 열린 작업 없음(보류 1건 `20260814-multiuser-workflow`). 다음 ADR 번호 024.
- [verification-depth §2](../../../skills/wf-implement/references/verification-depth.md#2-상태와-전이): 상태 5종. `병합`·`폐기`는 관문 4조건, `대체`는 DCR 승인, `격리`는 즉시. "기존 행을 새로 쓴 테스트로 바꾸는 재생성은 … `병합`으로 보고 4조건" — 재생성은 있으나 **수정 후 같은 행 유지**는 없다.
- [§3 재정비 관문](../../../skills/wf-implement/references/verification-depth.md#3-재정비-관문): 시점 = 통합·DCR 승인. 증거 사다리 = ① 뮤테이션 kill 집합 보존 ② 커버리지 겹침 + 단언 대조 ③ 단언 대조. 분류 5종(`중복`·`동어반복`·`자명`·`신호 없음`·`고아`). 승인 = 완료 보고 관문의 일괄 응답.
- wf-implement SKILL.md:204 "진행 중에는 등록·격리 외의 전이와 기존 테스트의 수정·제외·삭제를 하지 않는다 — 정리는 통합의 재정비 관문에서만." 본문 2,793/2,850어절(K3 경고, 여유 57) — 본문 추가는 포인터 수준이어야 한다(선례 NFR-01 순증 0).

- C층 가드 `wf-test-guard.ps1`(DES-06)은 Edit/Write 마다 `유지` 행 파일이면 `ask`. `wf-stop-gate.ps1`(DES-07)은 `regression_guard.py`를 호출하고, 위반(테스트 파일 변경·`유지` 행 축소) 행 ID가 **열린 작업 기록의 `### 테스트 대장 변경` 절**에 있으면 통과한다(`recorded_ids`). 즉 배치 단위 기록이 이미 Stop 게이트의 「배치마다 1회」 역할을 하지만, PreToolUse 가드는 파일마다 묻는다. 04 D-6 결정: 「배치마다 1회. 승인 범위는 사람이 승인한 req-design 에서 읽고 plan.md 에서 읽지 않는다」 — 이것을 가드에 구현하려면 C층(DES-06) 변경 = DCR.
- 경량 경로 기계 조건(제품 코드 변경 ≤ 5파일)상 수십 파일 정리는 정식 경로다. 04 R-14 도 「판단과 사용자 승인이 많아 경량 경로에 맞지 않는다」. 경량 경로의 제품 코드 정의는 「`docs/` 밖 전부」라 테스트 파일도 제품 코드에 든다 — 재정비 작업의 「제품 코드 동결」은 테스트 코드를 뺀 정의가 따로 필요하다. 기계 조건 (c)에 테스트 파일 정의(`test`/`tests` 디렉터리 또는 `test_*`·`*_test.*`·`*.test.*`·`*Tests.*`)가 있다.
- 이 저장소에 뮤테이션·커버리지 도구 없음(D-3: 수동 LLM 뮤턴트 시범, [ADR-017](../20261026-test-quality/ADR-017-변경-범위-뮤테이션.md)). 마켓은 2026-10-29 측정에서 coverage.py 테스트별 컨텍스트로 지배 관계·유일 라인(`unique_lines`)을 얻었고 뮤테이션은 없다.
- 선례: [REQ-DESIGN-legacy-onboarding](../20261028-legacy-onboarding/req-design.md)·ADR-023 — 새 상태값·열 없이 진입 경로와 괄호 표기만 추가, 판독 무변경(NFR-02), 본문 순증 0(NFR-01). 대장 템플릿 노트: 「묶음 안의 개별 테스트가 전이 대상이 되면 그 테스트만 새 행으로 분리」.
- 04 「레거시 정비 작업의 성공 기준 후보」: 배치마다 (1) kill 집합 합 ≥ 정비 전 (2) `유지` 전량 통과 (3) 제품 코드 diff 0 (4) 폐기·병합·리팩터 행마다 분류·증거·승인 (5) 실행 시간·격리 수 전후 기록.
- 재사용 후보 자산: §3 4조건·증거 사다리·분류 5종, `### 테스트 대장 변경` 표(5열)와 Stop 게이트의 `recorded_ids`, 재정비 기록 표(5열), TASK `completed` 전이의 `유지` 전량 실행·SHA 갱신 규칙, §4 냄새 체크리스트(리팩터 분류 어휘), 역공학 10단계 RR 항목, `test_regression_guard.py`의 tmp git 픽스처.

### 해석

- R-14 는 새 워크플로우가 아니라 **정식 경로 작업의 한 종류**로 표현할 수 있다 — req-design 에 「대상 TST 범위·배치·성공 기준」 필수 절을 요구하고, verification-depth 에 「독립 재정비 작업」 절(시점·범위·제품 코드 동결·배치 TASK·관문 적용 방식)을 두면 된다.
- R-15 의 `리팩터`는 **새 상태값 없이** `유지` 를 유지한 채 대장 `비고`·재정비 기록·대장 변경 절에 「리팩터」 분류로 남기는 편이 판독 무변경(선례)과 맞다. 증거 = 같은 제품 SHA 에서 수정 전·후 통과 + kill 집합(또는 단언 집합) 비감소.
- 유일성(AC 없음)은 증거 사다리 ①(다른 행이 못 죽이는 뮤턴트)을 1순위로, 도구가 없으면 ③ 단언 대조 + 커버리지 유일 라인(마켓 측정의 `unique_lines`)을 **후보 선별 신호**로 쓰되 단독 근거로는 쓰지 않는 쪽이 §3 「겹침은 후보 신호」 원칙과 맞다.
- R-16 은 04 제안 그대로(`고아` 목록 일괄, 판단 분류는 배치별 행 승인) 가정으로 둘 수 있다 — 해석이 갈리지 않는다.

### 가정

- A-01 R-16 승인 계층: `고아`(파일·심볼 부재)는 목록 일괄 승인, `중복`·`동어반복`·`자명`·`신호 없음`·`리팩터`는 배치별 행 승인(04 제안). 결과를 바꾸지 않아 질문하지 않는다.
- A-02 제품 코드 동결: 재정비 작업은 테스트·대장·문서만 바꾼다. 제품 코드가 필요하면 별도 작업(04 R-14).
- A-03 성공 기준의 수치 목표(실행 시간 등)는 저장소별 req-design 이 정한다(04).

| FR-04 | `리팩터` 처분 | `유지` 행의 테스트를 고쳐서 `유지`로 두는 처분. 새 상태값이 아니다 — 대장 행 `상태`는 `유지` 그대로, `비고`에 `리팩터(분류, 일시)`, `### 테스트 대장 변경`의 `현재 상태 → 제안` 열에 `유지 → 유지(리팩터)`. 분류는 §4 냄새 이름, `대역 교체`(mock→fake), `통합`(한 행 안의 케이스를 합치되 각 케이스의 단언이 보존됨 — 행 간 흡수는 `병합`) 중 하나와 사유. `리팩터`의 경계는 **단언 보존**이다 — 수정 전 단언마다 같거나 더 강한 단언이 수정 후에 남으면 `리팩터`(강화 허용), 단언을 없애거나 약화하거나 기대값을 바꾸면 §2 의 재생성이며 `병합`으로 4조건을 거친다. `리팩터`에는 유일성 조건이 없다(행이 남으므로). 증거는 **같은 제품 코드 SHA 에서 수정 전·후 모두 통과** + kill 집합 비감소(도구 또는 수동 뮤턴트 표본 — 수정 전 kill 을 수정 후에도 전부 kill) 또는 단언 대조(수정 전 단언마다 같거나 더 강한 단언이 수정 후에 있음). 독립 재정비 작업 안에서만 허용하며 기능 작업 진행 중의 기존 테스트 수정 금지(§3.3)는 그대로다. 수정 전에 실패 중인 행은 대상이 아니다(§6 충돌 출구) — 주의 ④의 「통과시키려는 수정」과 다르다 |
| FR-05 | 인수 조건 없는 행의 유일성 판정 | `보호 스코프`에 인수 조건이 없는 행의 「유일 검증 아님」은 순서대로 판정한다: ① 뮤테이션 — 다른 행이 죽이지 못하는 뮤턴트를 이 행이 죽이면 유일(도구가 없으면 보호 스코프에 수동 뮤턴트 1~3개) ② 역공학 10단계의 RR 항목에 연결돼 있으면 그 항목의 다른 검증 유무 ③ 단언 대조 — 흡수 행이 이 행의 단언 전부를 같거나 더 강하게 가지면 유일 아님. 커버리지 지배·유일 라인 0 은 후보 선별 신호이며 단독 근거가 아니다. 어느 증거도 대지 못하면 `유지`. 유일하면 대체 행을 먼저 등록한다(기존 4조건). `보호 스코프`가 `미확정`인 행은 ①(뮤턴트 둘 곳 없음)·③(흡수 행 대조 불가)을 쓸 수 없으므로 `고아` 외의 전이가 불가하다 — 배치 착수 측정(FR-03 (a))에서 스코프를 먼저 채운다 |
| FR-06 | 승인 계층 | `고아` 행은 배치 목록으로 일괄 승인(응답 한 번). 판단 분류(`중복`·`동어반복`·`자명`·`신호 없음`·`리팩터`)는 배치별 행 단위 승인 — 요청은 행마다 분류·증거·유일성 판정을 한 줄로 적은 표, 응답은 행 ID 를 특정한다(「전부」·「X 제외 전부」도 행 전부에 대한 응답으로 기록). 응답 인용을 `### 테스트 대장 변경` `승인` 열과 재정비 기록 `승인` 칸에 `배치 N 승인(YYYY-MM-DD, "응답 인용")`로 적고, 승인 뒤에만 대장을 바꾼다. 승인 범위는 FR-01 절의 대상 TST 범위를 넘지 못한다 |
| FR-07 | 기록 | 재정비 기록에 배치마다 시점 `재정비 작업` 1행 — 행 수, 분류별 건수, `리팩터` 수, 실행 시간·`격리` 수 전후값, 승인. 작업 통합의 재정비 관문은 그와 별도로 시점 `통합` 1행(변경 없음이라도) |
| FR-08 | 본문 트리거 | wf-implement §3.3의 기존 테스트 수정 금지문에 독립 재정비 작업 예외 링크, §3.6에 독립 재정비 작업 포인터 1문장 — 승인 단위(배치별)와 대장 반영 시점(배치 승인 뒤)이 통합 관문과 다르다는 것을 본문이 말해야 한다(verification-depth 는 본문과 다르면 본문 우선). 규칙 본체는 references |
