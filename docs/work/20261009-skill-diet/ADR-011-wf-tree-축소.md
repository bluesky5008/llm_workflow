## 요약

- 결정: wf-tree의 분기 템플릿은 **필수 게이트 3종**(`release` → 부모 `approve`, `migrate` → 롤백 준비 + `verify`, 포트폴리오 최초 생성 → `approve`)만 본문에 남기고 비게이트 7행은 삭제한다. 노드 유형 표·자체 검토 문항·예시 트리는 references로 옮긴다. ASCII 렌더링은 `scripts/render.py`가 목록에서 생성하며 손으로 그리거나 고치지 않는다. 작업 내부 트리의 분해 깊이에 상한(2단계)을 둔다.
- 핵심 이유: 실증 근거는 계획 구조화(분해·DAG)와 상태 추적을 지지하지만, 트리 다이어그램 자체와 절차 자동 제안은 지지하지 않고 비용 근거만 있다. 비게이트 제안은 wf-implement·wf-design 규정의 중복 표현이며, 목록 없는 노드를 트리에 만들어 단일 소스 원칙과 충돌한다.
- 주요 단점: 트리가 더 이상 "누락 항목을 알려 주는" 역할을 하지 않는다. Python 부재 환경은 손 렌더로 돌아간다. 저장소 사이클 6개 중 4개가 wf-tree 정비였던 이력에 또 하나가 더해진다 — 대신 이후 정비 대상 자체가 준다.

## 배경

wf-tree 판정 보고서(2026-08-27)는 wf-tree를 기능 5개로 나눠 판정했다 — ① 계획 구조화 찬성(TDP 토큰 −82%, LoopsBench), ② 상태 추적 찬성(PushBench 30% → 69~78%), ③ 사람용 시각화는 "상태 있는 목록"까지만 지지(Cocoa), ④ 에이전트용 시각화 근거 없음 + 비용 근거(Heavy Implementation Pipeline), ⑤ 분기 템플릿은 비가역 게이트만 찬성(Plan Compliance "태스크 특화 단계 추가 시 저하"). 사이클 1(2026-10-09, plan-relocation)이 ④의 대부분 — 자동 재생성·완료 스냅숏·Mermaid — 을 제거했다. 남은 것은 ⑤의 비게이트 제안, 노드 유형 표(218어절)·렌더 세칙(342어절)·자체 검토(102어절)의 본문 잔류, 렌더의 수작업, 깊이 무제한이다.

현행 계획 트리 3개(plan-relocation·worklog-diet·test-lifecycle)에는 목록에 없는 자식("테스트: … (선행)", "롤백 준비: … (필수)")이 손으로 그려져 있다. 분기 템플릿 제안이 목록 항목 없이 트리에만 존재한 결과이며, §5 단일 소스 원칙("트리는 목록에서 파생")과 어긋난다. LoopsBench가 지목한 실제 병목은 의존 간선 복원(F1 0.71)인데, 현행 §9에는 의존 복원을 검토하는 문항이 없다.

## 결정

대안 C를 채택한다.

1. **분기 템플릿(§4 → `## 4. 필수 게이트`)**: 본문에 3행만 남긴다 — `release` 노드 생성 시 부모에 `approve` 필수(wf-implement §2.3), `migrate` 노드 생성 시 롤백 준비 + `verify` 필수(wf-implement §3.2), 포트폴리오 최초 생성 시 `approve` 필수(§8). "필수 게이트는 생략을 제안하지 않으며 사용자가 명시적으로 제외하면 사실과 이유를 계획에 기록한다"는 문장은 유지. **삭제하는 7행**(근거 규정이 이미 본문에 있어 중복): `design` → `review`+`approve`(wf-design §4.5·§8) · 대안 2개 이상 → `decide`(wf-design §3.3) · `implement` → `test`(선행)+`review`(wf-implement §2.4·§3.3·§3.5) · 버그 수정 → 재현 `test`(wf-implement §3.3) · 공개 인터페이스 변경 → `document`+`verify`(wf-implement §3.3) · 기준선 충돌 → `change` 분기(wf-implement §4.2) · 신뢰 경계 입력 → 보안 `test`(wf-implement §2.4). `change`·`question` 등 노드 유형 자체는 references 표에 남는다.
2. **노드 유형(§3)**: 15유형 표와 생태계 매핑을 `references/node-templates.md`로. 본문은 "노드 유형은 references 표의 15종을 쓰고 새 유형을 만들지 않는다. ★ 게이트 유형은 `approve`·`release`·`migrate`다" 2문장.
3. **렌더링(§7)**: 매체(Markdown 목록 + ASCII) 1문단과 생성 시점 절은 본문 유지. 표기 어휘·완료 시점 파생·접기·뷰 세칙은 `references/rendering.md`로, 생성은 `scripts/render.py`로. 본문 트리거: "트리를 생성·재생성할 때는 `scripts/render.py`를 실행한다. 손으로 그리거나 고치지 않는다. Python을 쓸 수 없으면 references/rendering.md의 표기로 손 렌더하고 generated 주석에 그 사실을 적는다." 트리는 `상위:` 필드가 있는 목록 항목만 그린다 — 목록에 없는 노드를 트리에 두지 않는다.
4. **깊이 상한(§2)**: "깊이는 제한하지 않는다"를 "작업 내부 트리는 작업 → TASK → 하위 항목의 2단계까지 분해한다. 더 깊은 분해가 필요하면 TASK를 분할한다"로 교체(값은 [Q-03](./req-design.md#가정과-미해결-질문)). render.py `--depth` 기본값이 같은 값이며 초과 시 경고.
5. **자체 검토(§9)**: 문항을 references로 옮기고 트리거만 남긴다. 문항에 S12 "파일 겹침·심볼 참조로 검출한 `depends:` 후보가 목록에 반영되었거나 제외 이유가 있는가"를 추가한다(의미 규칙은 wf-implement §3.2가 소유).
6. **description**: "노드 유형별 분기 템플릿으로 누락되기 쉬운 항목(승인 관문·리뷰·롤백 준비 등)을 제안하되"를 "필수 게이트(승인·릴리스·전환 검증)의 누락을 막되"로 고친다.

## 이유

- 근거가 지지하는 실체는 목록의 `상위:`·`depends:`·상태 필드와 재개 시점의 활성 경로 뷰다(판정 §3). 트리는 그 표현이지 원천이 아니므로 표현 규칙은 스크립트와 references에 있어야 한다(ADR-010 R2·R4).
- 비게이트 제안은 정보를 더하지 않고 노드 수만 늘린다(Plan Compliance·Skills Harmful 과잉 절차 62.6%). 현행 트리의 목록 없는 자식이 그 증거다.
- 의존 복원은 "트리를 그리는 것"보다 계획 품질에 직접 닿는 병목이다(LoopsBench). 문항 1개의 비용으로 보강한다.
- 과분해는 지침과 실행의 불일치를 만든다(Horizon Gap). 저장소의 계획 3개가 모두 2단계 이내였으므로 상한 2는 현행 관행을 고정하는 것이다.

## 결과와 감수할 단점

- wf-tree 본문은 약 1,850 → ≤ 1,200어절. 역할은 "필드 규칙 + 게이트 3종 + 포트폴리오 관문 + 스크립트 호출"로 좁아진다.
- 분기 템플릿이 제안하던 항목은 이제 계획 수립자가 wf-implement §3.2·§3.3을 읽고 스스로 목록에 넣어야 한다. 이는 규정의 중복 제거이지 의무의 삭제가 아니다.
- 현행 트리 3개(완료 기록)는 동결이라 다시 그리지 않는다. 새 규칙은 이 작업의 plan.md부터 적용한다.
- 손 렌더 예외 경로가 남는다. generated 주석의 표시로 손 렌더 여부를 추적한다.

## 후속 작업

- render.py의 활성 경로 뷰가 세션 재개에 실제로 쓰이는지 — 훅 `resume.md`가 뷰를 주입할지는 묶음 A에서 검토.
- 깊이 상한·게이트 3종이 두 사이클 운용 후에도 맞는지 재검토(경량 경로로 조정).
