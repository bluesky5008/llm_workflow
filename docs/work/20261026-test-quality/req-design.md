## 현재 상태 조사 (wf-design §4.1)

### 사실

- **verification-depth §1** 통합 행: "전체 테스트 스위트 1회 + `유지` 행 전량 + 재정비 관문 / 작업당 1회". 끝 문장 "전량 실행은 `completed` 전이·통합·재개 세 시점 밖에 두지 않는다". 뮤테이션 언급 없음.
- **§2** 상태 표: `병합`은 "관문 4조건 + 중복 증거", `격리`는 "같은 SHA에서 결과 불일치, 또는 실행 환경 원인 … 즉시". 표 뒤 문단: "`유지` 행을 통과시키려고 테스트를 수정·제외·삭제하는 것은 §3.4 위반. 의미 충돌은 §6의 출구". 기존 테스트를 새로 쓴 테스트로 **바꾸는 것(재생성)**의 취급은 없다. 격리의 원인 진단 순서도 없다.
- **[ADR-009](../20261009-test-lifecycle/ADR-009-테스트-재정비-관문.md)**(approved) 결정 1은 진행 중 기존 테스트의 수정·제외·삭제를 금지하고, 결정 2(b)는 중복 증거를 "커버리지 겹침 또는 뮤테이션 동치"로 정했다. 감수할 단점에 "도구 부재 저장소에서는 중복을 수동 대조로 기록".
- **§3** 4조건 표 `증거` 행: "중복: 커버리지 겹침 또는 뮤테이션 동치(도구가 없으면 단언 대조 기록)" — 세 증거가 대등한 `또는`이고 순서가 없다. 1단계 Missing은 "새 동작에 필요한데 없음 → 추가"뿐, 입력 신호가 없다.
- **§4** 냄새 표 6행(Assertion Roulette, Magic Number, Lazy Test, Conditional Logic, Empty / Trivial, Duplicate Assert). Empty / Trivial의 징후 "단언이 없거나 non-null·true 확인뿐"이 Print-only(출력만, 단언 없음)를 이미 포함한다. Over-mock·Mirror에 해당하는 행은 없다.
- **§5** "결과 요약은 다섯 필드를 고정으로": 총계·기준·명령·커버리지·산출물. [templates.md 결과 요약](../../../skills/wf-doc/references/templates.md#작업-기록-work-log)(527~533행)과 노트(571행 "다섯 필드 … 필수")가 같은 5필드. `lint_worklog.py`·`regression_guard.py`·훅은 결과 요약 필드를 검사하지 않는다(grep 0건).
- **§6** 명세·테스트 충돌(사이클 1, R-04): `유지` 행 실패 + 통과에 의미 변경이 필요 → 구현 정지, `차단 요인` 기록, (a) 테스트 오류 → Breaking·재정비 관문, (b) 요구사항 변경 → DCR·`대체`.
- **wf-implement §2.4** 테스트 작성 기준 5항목 중 첫째 "구조가 아니라 동작을 검증한다(협력자 전부 mock 금지)", 둘째 "결정적이다(시계·난수는 테스트가 주입)". 대역을 쓸 경계와 fake/mock 우선순위는 없다. 끝에 §4 링크.

### 해석

- **재생성과 §6의 관계.** 재생성은 두 경우로 갈린다. 기존 행이 **실패 중**이면 재생성은 "통과시키려고 수정"이므로 §6 출구가 먼저다. 기존 행이 **통과 중**인데 새로 쓴 테스트로 바꾸려면, 새 테스트가 옛 테스트의 보호를 이어받는지가 쟁점이라 `병합`(4조건)과 같다. 어느 경우도 재생성이 §6을 우회하는 길이 되면 안 된다.
- **뮤테이션 실패와 §2·§6.** 뮤턴트를 적용하면 `유지` 행이 실패하는 것이 정상(kill)이다. 이 실패를 회귀 사건·검증 실패·§6 충돌로 기록하면 안 되므로 명시적 분리 규칙이 필요하다.
- **살아남은 뮤턴트는 Missing 입력.** survived는 실패가 아니라 "검증이 없는 동작"의 신호이므로 §3 1단계 Missing의 입력이며, §6(실패 시 출구)과 겹치지 않는다.
- **§0 원칙과의 정합.** 뮤테이션은 변경 파일의 관련 행만 뮤턴트 수만큼 실행하고 통합에 1회뿐이라 "전량 실행 시점을 늘리지 않는다"를 어기지 않는다.
- **뮤턴트 복원 확인.** 통합은 [종결 ① 구현 커밋](../../../skills/wf-implement/references/closing.md#2-순서) 전이라 워킹트리가 이미 dirty다. `git diff --quiet`로는 복원을 확인할 수 없어, 적용 전후 파일 해시 비교가 필요하다.
- **Print-only는 Empty / Trivial의 하위 징후다.** 별행으로 두면 냄새 표 자체에 Duplicate 냄새가 생긴다. 징후 문구에 이름을 넣어 검색되게 한다.
- **"대체"의 동음 충돌.** §2 상태값 `대체`가 있으므로 테스트 대역(test double)은 "대역"으로 쓴다.
- **본문 어절 여유 0.** §2.4 문장 교체는 같은 절에서 상쇄해야 한다. §3.4의 필드 열거는 공백 없는 한 토큰이라 "뮤테이션"을 넣어도 어절이 늘지 않는다.
- **이 작업 자체의 뮤테이션은 N/A가 된다.** 바꾸는 파일이 전부 Markdown이다. 따라서 R-08의 시범(render.py·lint_worklog.py)은 규칙의 "변경 범위" 적용이 아니라 절차 검증용 별도 VER로 둔다.

### 가정

- 수동 LLM 뮤턴트는 같은 세션의 에이전트가 기존 테스트를 읽은 상태에서 만든다(별도 모델·도구 없음). 뮤턴트의 질 평가는 시범 결과로만 한다.
- mutmut은 Windows 네이티브 실행을 지원하지 않는 것으로 알려져 있다(WSL 필요). 이 저장소에서 미검증 — Q-01 (B)를 고르면 TASK에서 먼저 확인한다.

| FR-08 | 뮤턴트 실패 분리 | 뮤턴트 적용 중의 테스트 실패는 kill이며 검증 결과의 `실패`, 회귀 사건, §6 충돌로 기록하지 않는다. 뮤턴트는 테스트 파일을 바꾸지 않고, 복원 후 파일이 적용 전과 같음을 확인하며, 커밋하지 않는다 |
| FR-09 | 속성 기반 테스트(선택) | 불변식이 분명한 순수 로직(파서·직렬화·변환)에 속성 기반 테스트를 선택지로 제시한다. 의무가 아니다(R-09) |
| FR-10 | 속성 테스트 시범 | `render.py`의 파싱·렌더 불변식 2~3개를 결정적(고정 시드, 시간 제한 없음) 속성 테스트로 검증하고 TST-05에 등록한다. `hypothesis`가 없으면 조용히 건너뛰지 않고 실패해야 한다(Q-02 (B)) |
