## 배경

현행 품질 신호는 통과 여부와 커버리지뿐이다. 커버리지는 실행 여부만 보이고 단언의 힘은 보이지 않으며, 스위트 크기와 뮤테이션 점수의 상관은 r=0.031로 거의 없다. 에이전트가 쓴 테스트는 mock 추가와 출력만 하는 테스트가 많다. 테스트를 읽은 LLM이 만든 뮤턴트는 79~88%가 실제 결함형이라 도구 없이도 신호를 낼 수 있다(입력 [R-08](../../research/20261025-aidlc-trends/04_test_action_items.md)).

## 영향을 받는 요구사항과 제약

- verification-depth §0 원칙: 전량 실행 시점(`completed` 전이·통합·재개)을 늘리지 않는다.
- wf-implement §2.4: 요청되지 않은 새 의존성을 추가하지 않는다(결정 사다리).
- 하네스·언어 중립. 이 저장소의 대장은 PowerShell(TST-01)과 pytest(TST-02·04·05)가 섞여 있고 뮤테이션 도구는 미설치.
- 뮤턴트 적용 중의 실패는 회귀 보호(§2 회귀 사건, §6 충돌 출구, 종료 정합 검사)와 섞이면 안 된다.

## 고려한 대안

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 통합 1회, 변경 코드 파일만. 있는 도구, 없으면 수동 뮤턴트 1~3개. 목표 비율 없음. survived → Missing 입력 | 새 의존·새 실행 시점 없음, 신호를 관문 판단에 바로 씀 | 수동 뮤턴트는 표본이 작고 질이 작성자에 달림 |
| B | A + 뮤테이션 점수 목표(예: 70%) | 기준이 명확 | 동치 분류·쉬운 뮤턴트로 맞추는 게이밍 유인, 커버리지 비율을 완료 조건에서 뺀 현행 원칙(§3.4)과 충돌 |
| C | 도구(mutmut 등)를 규칙으로 요구 | 표본이 크고 재현 가능 | 언어별 도구 필요, PowerShell 대상 없음, 새 의존이 모든 저장소에 강제됨 |
| D | 매 TASK `completed` 전이마다 실행 | 이른 신호 | 실행 비용이 TASK 수에 비례, §0 원칙과 충돌 |
| (현행) | 뮤테이션 없음. 병합 증거에 "뮤테이션 동치"만 언급 | — | 단언의 힘을 볼 신호가 없음 |

## 결정

A를 채택한다. 대상은 작업 착수 SHA 이후 바뀐 코드 파일(문서·테스트 제외)이며, 그 파일의 관련 행(없으면 전체 스위트)으로 뮤턴트를 하나씩 실행한다. 도구는 저장소에 이미 있을 때만 쓰고, 없으면 기존 테스트를 읽은 상태에서 실제 결함형 수동 뮤턴트 1~3개를 쓴다. 뮤턴트는 테스트 파일을 바꾸지 않고, 복원은 적용 전후 `git hash-object` 일치로 확인하며, 커밋하지 않는다. 뮤턴트로 인한 실패는 kill이며 검증 실패·회귀 사건·§6 충돌이 아니다. 결과는 결과 요약 여섯째 필드에 적고, survived와 동치는 위치·변이·이유를 `### 테스트 대장 변경`에 Missing 후보로 적는다.

## 이유

- 기존 실행 시점(통합) 안에서 변경 파일만 보므로 비용이 작업 크기에 비례하고 대장 크기에 비례하지 않는다.
- 목표 비율이 없으면 동치 분류로 숫자를 맞출 유인이 작고, survived 하나하나가 관문의 구체적 입력이 된다.
- "있는 도구만"은 결정 사다리 5단계와 같은 규칙이라 저장소별 도구 도입은 그 저장소의 별도 결정으로 남는다(이 저장소는 Q-01).

## 결과와 감수할 단점

- 수동 뮤턴트 1~3개는 점수가 아니라 표본 신호다. 숫자를 저장소 간·작업 간 비교하지 않는다.
- 문서만 바꾸는 작업은 `N/A`다.
- 보호 대상 파일(훅 등)을 뮤턴트로 바꾸면 편집 확인 훅이 확인을 묻는다 — 감수.
