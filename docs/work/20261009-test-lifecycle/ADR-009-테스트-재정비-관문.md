## 요약

- 결정: 테스트 대장의 `병합`·`폐기` 전이는 **재정비 관문**에서만 일어난다. 관문 시점은 통합(§3.6)과 DCR 승인 두 곳이다. 관문은 (a) 변경이 닿은 보호 스코프의 테스트를 Breaking·Stale·Missing으로 분류하고, (b) 폐기·병합 후보에 4조건(분류 5종 명시, 증거, 유일 검증 아님, 사용자 승인)을 전부 요구하며, (c) 결과를 work-log에 기록하고 완료 보고 관문에서 일괄 승인받는다. TASK 진행 중에는 등록·격리만 허용하고 기존 테스트의 수정·제외·삭제를 금지한다.
- 핵심 이유: 에이전트는 실행 실패 신호 없이는 정리를 하지 않고(TEBench, stale F1 약 36%), 반대로 통과를 위해 테스트를 지우기도 한다(Kent Beck 보고). 두 결함은 **시점**으로 양립시킨다 — Green을 만드는 동안은 금지, 사이클 경계의 관문에서만 증거·승인과 함께 허용. 입증 책임은 삭제 쪽에 둔다.
- 주요 단점: 관문이 형식적으로 통과할 수 있다. 사용자 승인이 관문마다 필요하다 — 완료 보고 관문과 합쳐 1회로 묶는다.

## 배경

보관 브랜치 설계의 회귀 의무 목록은 상태 어휘(`유지·대체·폐기·보류`)를 두었지만 `대체`는 "DCR 승인과 같은 변경에서", `폐기`는 "제거 작업의 completed 전이에서"로만 규정해 **누가 언제 어떤 증거로 폐기를 제안하는지**가 없었다. 결과는 사용자가 관찰한 "증가 방향만 있다"다.

조사 정리는 세 근거를 모았다. (1) TEBench(arXiv 2605.06125): 코딩 에이전트 7개 구성이 Breaking 테스트는 고치지만 Stale(통과하나 더 이상 검증하지 않음)은 F1 약 36% — 실행 신호가 없으면 정리가 일어나지 않으므로 명시적 분류 문항이 유일한 트리거다. (2) tessl 삭제 기준: 분류 5종(duplicate·tautology·trivial·dead-signal·orphan)과 "전부 성립해야 삭제, 아니면 유지"의 관문, "한 번도 실패한 적 없는 테스트는 하중을 받고 있을 가능성"으로 취급. (3) Kent Beck·AGENTS.md 실무: 에이전트가 통과를 위해 테스트를 지우므로 "삭제 금지"가 널리 쓰이는 규칙 — 정리 요구와 양립시키려면 시점을 분리해야 한다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. 관문 없음(현행·보관 설계) | 변경 없음 | 증가 방향만 남음. 요구 7 미해결 | — |
| B. 매 TASK `completed` 전이에서 폐기 허용 | 정리가 자주 일어남 | Green 직후의 삭제 유혹과 시점이 겹친다. TASK마다 사용자 승인이 필요해 관문이 잦음 | 낮음 |
| C. 통합 + DCR 승인 시점의 관문, 4조건 + 사용자 승인 (채택) | "삭제 금지"와 "정리 필요"를 시점으로 양립. 승인은 완료 보고 관문과 합쳐 1회. DCR은 보호 스코프의 의미가 바뀌는 유일한 공식 사건이라 `대체`의 자연 시점 | 사이클 중간의 stale은 통합까지 남는다(§3.5 문항으로 후보만 미리 표시). 형식적 통과 위험 | 중간 — §3.6 한 문단, §3.5 문항 2개, references 표 |
| D. 커버리지 기반 자동 최소화(그리디) | 사람 판단 불필요 | 도구·언어 의존, 커버리지는 결함 탐지력의 충분한 지표가 아님(Yoo & Harman), 수치 게이밍 | 높음 |
| E. 달력 주기(분기별) 정리 | 예측 가능 | 워크플로우 사건과 무관해 트리거가 없음. 세션 경계가 불규칙한 에이전트 작업에 맞지 않음 | 낮음 |

## 결정

대안 C를 채택한다.

1. **시점.** 통합(§3.6)과 DCR 승인. 세션 재개는 실행만 하고 전이는 하지 않는다. TASK 진행 중(Green·Refactor·리뷰)에는 등록(`completed` 전이)과 격리(같은 SHA 불일치 즉시)만 허용하며 기존 테스트의 수정·제외·삭제는 §3.4 "인수 조건을 완화하지 않는다"의 위반으로 본다.
2. **절차.** (a) 자체 리뷰 §3.5 문항으로 변경이 닿은 보호 스코프의 테스트를 Breaking(수정)·Stale(대체 또는 폐기 후보)·Missing(추가)으로 분류한다. (b) 폐기·병합 후보는 4조건을 검토한다 — 분류 5종(중복·동어반복·자명·신호 없음·고아) 중 하나로 명시, 증거(중복은 커버리지 겹침 또는 뮤테이션 동치, 동어반복은 구현을 바꿔도 통과하는 실험, 고아는 보호 스코프가 현재 트리에 없음), 어떤 인수 조건의 유일한 검증이 아님(유일하면 대체 테스트를 먼저 등록), 사용자 승인. 하나라도 미달이면 `유지`. (c) 제안을 work-log `### 테스트 대장 변경` 표에 적고 완료 보고 관문에서 일괄 승인받은 뒤 대장과 `## 재정비 기록`을 갱신한다.
3. **보존.** "한 번도 실패한 적 없음"은 단독 폐기 사유가 아니다. 전이된 행은 삭제하지 않고 상태·분류·이유·일시를 남긴다.

## 이유

정리가 일어나지 않는 원인(실행 신호 부재)과 정리가 잘못 일어나는 원인(통과 압력)은 같은 행위자의 반대 방향 결함이다. 절차 하나로 둘을 풀려면 "언제"가 핵심이다 — 통과 압력이 없는 사이클 경계에서, 실행 신호 대신 명시적 분류 문항으로 후보를 만들고, 삭제 쪽에 입증 책임을 지운다. 4조건은 tessl의 실무 기준을 따르되 원문 미확인 부분(조사 정리 §5)은 자체 설계임을 밝힌다. 사용자 승인을 완료 보고 관문에 합치는 것은 1인 저장소에서 관문 수를 늘리지 않기 위해서다.

## 결과와 감수할 단점

- 사이클 중간에 발견한 stale 테스트는 통합까지 `유지`로 남는다. §3.5 문항이 후보를 work-log에 미리 표시하므로 손실은 시점 지연뿐이다.
- 관문이 "변경 없음"만 반복할 수 있다(RISK-01) → `## 재정비 기록`에 매 관문 결과를 남겨 두 사이클 후 통계로 검토.
- 증거 기준 중 커버리지 겹침·뮤테이션 동치는 도구가 필요하다. 도구 부재 저장소에서는 동어반복 실험·고아 판정만 가능하며 중복은 수동 대조로 기록한다(NFR-04).
