# ADR-007: 검증 결과의 3튜플 앵커

> 문서 유형: `adr`
> 작업 ID: `20261009-test-lifecycle`
> 상태: `approved`
> 기준선: `v1` ([REQ-DESIGN-test-lifecycle](./req-design.md) 기준선에 포함, 승인일 2026-10-09)
> 작성일: 2026-10-09
> 최종 갱신: 2026-10-09
> 관련 문서: [REQ-DESIGN-test-lifecycle: 요구사항·설계](./req-design.md), [ADR-008: 테스트 대장의 저장소 관통 배치](./ADR-008-테스트-대장-저장소-관통.md)

## 요약

- 결정: 검증 결과의 귀속 단위를 **(테스트 집합, 커밋 SHA, 실행 명령)** 3튜플로 정한다. 세 값이 같고 워킹트리가 clean이면 재실행 대신 인용하고, 하나라도 다르면 별개의 검증으로 취급한다. 실패 분류 "이번 변경으로 발생"은 마지막 성공 SHA 이후의 변경을 근거로 판정한다.
- 핵심 이유: 회귀검사의 중복 실행과 결과 부정합이 같은 결함 — 결과가 무엇에 묶여 있는지 불명 — 에서 나온다. 귀속 단위를 고정하면 "이미 한 검증인가"와 "이 실패는 무엇 때문인가"가 같은 데이터로 판정된다. 테스트 대장의 `마지막 성공(SHA)`·`격리`(같은 SHA 불일치) 판정도 이 앵커를 전제한다.
- 주요 단점: 행마다 SHA·명령 기록 부담. 인용 규칙이 검증 생략의 구실이 될 수 있다 — §3.5 자체 리뷰 문항으로 보완, 기계 강제는 후속 Stop 훅.

## 배경

현행 wf-implement §3.4는 "각 인수 조건에 대해 검증 방법, 결과와 증거를 기록한다"고 하고 합본 템플릿은 증거 열에 "로그·테스트명·아티팩트"를 예시한다. 어느 쪽도 **어느 커밋에서, 어떤 명령으로** 실행했는지를 요구하지 않는다. 2026-09 기준선 측정(보관 브랜치 `02_baseline_llm_workflow.md`)에서 검증 행 35개 중 SHA 기록 실질 0건, 명령 기록 2건이었다.

이 결함의 결과는 두 갈래다. (1) 같은 검증을 이미 했는지 판정할 근거가 없어 안전하게 다시 돌린다. (2) 이전에 성공한 검증이 재실행에서 실패할 때 §3.4의 4분류를 적용할 근거가 없다 — "기존 실패"는 마지막 성공 시점을 알아야 판정할 수 있다. 이 사이클에서는 셋째가 더해진다. (3) 테스트 대장의 `격리` 전이(같은 SHA에서 결과 불일치)와 재개 시 전량 재실행 조건(마지막 성공 SHA ≠ HEAD)은 앵커 없이는 정의할 수 없다.

보관 브랜치의 ADR-004가 같은 결정을 내렸으나 main에 없다. main 이력의 ADR-004는 다른 결정(TASK 식별자 작업 범위 발행)이므로 새 번호로 재발행한다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. 현행 유지 — 결과와 자유 형식 증거만 기록 | 변경 없음 | 중복 실행과 부정합의 원인이 그대로. 대장의 격리·재개 조건을 정의할 수 없음 | — |
| B. 커밋 SHA만 앵커 | 기록 부담 최소, "어느 코드에서"는 해결 | 같은 SHA에서 다른 명령(다른 가상환경·플래그·부분집합)의 결과를 구분 못함 — 환경 불일치와 집합 비결정이 남음 | 낮음 |
| C. 3튜플 — 집합·SHA·명령 (채택) | 중복 판정과 부정합 판정에 필요한 세 축을 전부 고정. 명령이 환경을 대리하므로 별도 환경 기록 불필요 | 행마다 세 값 기록. 인용 남용 위험 | 낮음 — 열 추가와 규칙 한 문단 |
| D. 실행 로그 전문 첨부 | 재현 정보 완전 | wf-doc "큰 로그를 붙이지 않는다" 원칙과 린트 L4·L9 위반 | 높음 |
| E. 결과를 외부 도구(pytest cache, CI)에 위임 | 문서 부담 없음 | 하네스 의존(NFR-04 위반), 세션 경계에서 문서가 정본이라는 §7 원칙과 충돌 | 중간 |

## 결정

대안 C를 채택한다. 합본 템플릿의 검증 표에 `분류` 열을 추가하고 증거 열에 SHA·명령을 필수로 한다(형식은 wf-doc). wf-implement §3.4에 귀속·인용·별개 판정 규칙을 한 문단으로 두고, 실패 분류의 SHA 근거 규칙을 덧붙인다. 테스트 대장의 각 행도 같은 3튜플(명령·마지막 성공 SHA)을 기록한다.

인용 조건은 **세 값 일치 + 워킹트리에 미커밋 변경 없음**이다. 미커밋 변경이 있으면 SHA가 같아도 코드가 다르므로 인용할 수 없다.

## 이유

중복 실행과 부정합이 동일 결함의 두 얼굴이라는 것이 진단의 핵심이다. 귀속 단위가 있으면 "이미 한 검증인가"(→ 인용)와 "이 실패는 무엇 때문인가"(→ 마지막 성공 SHA 이후의 변경)가 같은 데이터로 판정된다. 명령을 튜플에 넣는 이유는 환경 차이를 별도 서술 없이 잡기 위해서다 — 명령이 다르면 환경이 다른 것으로 본다. 이는 "실행하지 못한 검증은 성공으로 간주하지 않는다"(§2.5)를 한 단계 구체화한 것이지 새 철학이 아니다.

## 결과와 감수할 단점

- 검증 표 행마다 SHA·명령을 적어야 한다. 명령은 대장에서 복사하므로 실질 부담은 SHA 한 값이다.
- 인용 규칙은 검증 생략의 구실이 될 수 있다 → §3.5 자체 리뷰에 "인용한 검증의 SHA가 HEAD와 같고 워킹트리가 clean인가" 문항(RISK-06). 기계 강제는 후속 Stop 훅.
- 기존 완료 기록은 앵커가 없으므로 인용 대상이 아니다. 대장 신설 시 자산 3묶음을 다시 돌려 첫 앵커를 만든다(DES-09).
