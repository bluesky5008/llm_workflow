## 문제와 목적

사용자 요청(2026-10-26): 05의 사이클 A를 wf-design 정식 경로로 착수. 현행 wf-design은 질문 여부를 원칙 한 문장(§2 :80)으로만 정하고, 언제·무엇을 점검해 묻는지 절차가 없다. 모델은 지시 없이는 거의 묻지 않고, 묻게 하면 불충분 명세 과제가 최대 74% 개선된다(Ambig-SWE 2502.13069 `[노트]`). 가장 모호한 목표에서도 58.5%가 실행하며 그때 안전 성공률은 8.6%다(UnderSpecBench 2607.02294 `[재확인 10-26]`). 반대로 과잉 질문은 해결률을 떨어뜨리고 비용을 2배로 만든다(2605.07937 `[노트]`). §4.5 일관성 검토는 작성자 자신만 하며, 근거를 강제한 검토자+비평자가 단일 검토자보다 F1이 높고 근거 없는 적대 검토는 오히려 낮다(2608.18167 `[재확인 10-26]`, F1 0.533 > 0.495 > 0.457).

### 해석

- **질문 단계는 §4.1 끝과 §4.2 사이가 자리다.** §4.1 :119가 이미 "사용자 결정이 필요한 질문"을 조사 산출물로 정하므로, 그 문장에 "설계 초안 전에 질문 단계로 점검한다"를 잇고 규칙 본체는 references로 보내면 새 개념 없이 기존 규칙의 강화가 된다(05 §0).
- **질문 표 열 고정은 답의 위치를 하나로 만드는 것이 핵심이다.** 열이 다섯 가지인 것보다 답이 세 곳에 흩어지는 것이 추적을 깨뜨린다. `답` 열 하나로 모으고 승인 기록과 같은 인용 규칙을 쓰면 승인 게이트의 응답 인용 관행과도 맞는다.
- **D-04와 뮤테이션은 겹치지 않는다.** 시점(승인 전 / 통합), 대상(설계 문서 / 코드 파일, 문서 제외), 신호(근거 인용 지적 / 실행 kill 수), 소비자(승인 요청 / 재정비 관문)가 모두 다르다. 서로 입력을 주고받지 않는다. 구현 단계 적대 검토만 뮤테이션·재정비·인수 테스트 맥락 분리(R-10)와 겹칠 수 있는데 이번 범위 밖이다.
- **D-03은 기존 두 출구의 빈칸을 채운다.** §6은 테스트가 실패한 뒤, DCR §2는 설계가 틀렸을 때의 출구다. "둘 다 맞을 수 있어 고를 수 없음"은 어느 쪽에도 없어 추측 구현으로 새는 경로다(ImpossibleBench 2510.20270 `[노트]`: 중단 출구 제공 시 우회 54%→9%).
- **묻는 시점의 예외(FR-04)는 05 D-01(4) "답을 반영한 뒤 설계 초안"을 완화한다.** 근거: 이 저장소 req-design 11건 중 10건이 질문을 승인 관문에서 함께 물었고(plan-relocation만 승인 요청 전 질문), 초안 전 별도 왕복은 승인 피로(S26)를 키운다. 대신 예외 조건을 "영향 행 열거 가능 + 구조 불변"으로 좁혀 구조를 바꾸는 질문은 초안 전에 묻게 한다. 이 완화를 받아들일지는 Q-01에 포함해 묻는다.
- **어절 순증 0은 이관 한 건으로 가능하다.** 추가는 §2 교체(±0)·§4.1 1문장·§4.5 1문장으로 약 30~40어절, §6.2 예시 코드 블록(35어절)을 templates로 옮기면 상쇄된다. §8 승인 요약 1행은 이미 references(`approval-request.md`)라 본문 변경이 없다.

### 가정

- 적대 검토 1회 비용은 작성 비용의 수 배(05: 약 4.5배 토큰)지만 정식 경로 작업 빈도(이 저장소 하루 1~3건)에서 감수 가능하다 — 다음 작업 1~2건에서 기록(후속).
- Claude Code 서브에이전트는 부모 대화 맥락을 받지 않는다 — 프롬프트로 전달한 것만 본다. 이 작업 설계 단계의 시험 실행(아래 [적대 검토](#적대-검토))에서 확인한다.
