## 문제와 목적

실사용에서 확인된 증상 두 가지: (1) 사이클 안에서 TASK가 누적될수록 회귀검사 수행 시간이 늘어난다. (2) 앞서 성공으로 기록된 검증이 재실행에서 실패하는 등 결과 부정합이 간헐적으로 발생한다.

조사([플랜 §2.0](../20260919-aidlc-research/01_solution_plan.md))에서 현행 규정으로부터 원인을 도출했다. 시간 증가는 **중복**(TASK당 Red·Green·Refactor·§3.3 근접 검증·§3.4·§3.5 재수행·§3.6 최종까지 최대 7~8회 실행, 생략 조건 없음)과 **전량**("변경 영역" 판단이 에이전트 재량이라 전체 스위트로 기움)의 곱이다. 부정합은 네 원인 — 결과에 커밋 앵커 없음, 실행 집합 비결정, 실행 명령 미고정, 세션 경계의 기억 소실 — 이 하나로 환원된다: **검증 결과가 "무엇을·어느 코드에서·어떻게 실행했는지"에 묶여 있지 않다.**

[기준선 1차 측정](../20260919-aidlc-research/02_baseline_llm_workflow.md)이 이를 확인했다: 검증 행 35개 중 커밋 SHA 기록 실질 0건, 실행 명령 기록 2건, §3.4 실패 분류 어휘 사용 0건. 규정은 있으나 기록 형식이 강제하지 않는다.

이 작업은 규칙을 더하는 방향이 아니라 **결과의 귀속을 고정하고 실행 집합을 시점별로 고정**하는 방향으로 해결한다. 근거 논문은 [플랜 §4](../20260919-aidlc-research/01_solution_plan.md)에 대응표가 있다.

## 기능 요구사항

| ID | 항목 | 내용 |
|---|---|---|
| FR-01 | 3튜플 앵커 | 검증 결과는 (테스트 집합, 커밋 SHA, 실행 명령)에 귀속되어야 한다. 셋이 같고 워킹트리에 미커밋 변경이 없으면 재실행 대신 기록을 인용할 수 있고, 하나라도 다르면 별개의 검증이며 이전 결과를 현재 상태의 근거로 쓰지 않는다 |
| FR-02 | 증거 필수 항목 | 검증 표의 증거에 커밋 SHA와 실제 실행한 명령이 있어야 한다. 없으면 그 검증은 인용 가능한 기록이 아니다 |
| FR-03 | 실패 분류 강제 | 검증 표에 `분류` 열이 있어 실패 시 §3.4의 4분류(이번 변경/기존/환경/원인 미확인) 중 하나를 기록해야 한다. "이번 변경으로 발생한 실패"의 판정 근거는 마지막 성공 SHA 이후의 변경이며, 마지막 성공 기록이 없으면 "기존 실패"로 분류할 수 없다 |
| FR-04 | 테스트 맵 | 계획 수립 전에 변경 예정 파일→관련 테스트 매핑을 `test-map.md`로 생성하고 사전 실행해 현재 상태를 기록해야 한다. 맵의 각 행에는 실행 명령이 실제 형태로 있어야 한다. 맵에 없는 파일은 "관련 테스트 없음"을 명시한다 |
| FR-05 | 시점별 실행 집합 | Green·Refactor 후·자체 리뷰 후에는 테스트 맵의 관련 테스트를, TASK `completed` 전이·통합·세션 재개 시에는 회귀 의무 목록을, 통합 시에는 전체 스위트를 1회 실행해야 한다. Refactor 후와 리뷰 후 실행은 코드가 바뀐 경우에만 한다 |
| FR-06 | 회귀 의무 목록 | TASK를 `completed`로 바꿀 때 그 TASK가 남긴 유지 테스트를 work-log의 회귀 의무 목록에 추가하고 목록 전량의 성공 증거(SHA)를 기록해야 한다. 목록의 테스트가 이전 성공에서 실패로 바뀌면 회귀 사건이며, 테스트를 수정·제외해 통과시키지 않는다 |
| FR-07 | 진입 조건 | 의무 목록에 추가하는 테스트는 같은 커밋에서 반복 통과(횟수는 Q-02)해야 한다. 미충족 테스트는 `보류(결정성 미확인)`으로 표기하고 통합의 전체 스위트에서만 실행한다 |
| FR-08 | 재개 시 재실행 | 세션 재개(§3.1)에서 의무 목록의 마지막 성공 SHA가 HEAD와 다르면 목록을 전량 재실행하고 결과를 기록해야 한다. 같으면 인용한다 |
| FR-09 | 계층 표 트리거 | wf-implement 본문에는 "검증 단계·깊이·시점은 `references/verification-depth.md`를 따른다"는 트리거 문장이 있고, 표를 참조하지 않은 생략은 이유를 기록해도 유효하지 않다 |
| FR-10 | 자기 적용 | 이 작업의 work-log가 회귀 의무 목록 절과 새 검증 표 형식(SHA·명령·분류)을 사용해야 한다 |

| ID | 항목 | 내용 |
|---|---|---|
| DES-01 | 3튜플 앵커 | 검증 결과의 귀속 단위를 (테스트 집합, 커밋 SHA, 실행 명령)으로 정한다. 인용 조건은 세 값 일치 + 워킹트리 clean. 상세와 대안 비교는 [ADR-004](./ADR-004-검증-결과-3튜플-앵커.md) |
| DES-02 | 테스트 맵 위치·형식 | 작업 폴더의 별도 파일 `docs/work/<작업-ID>/test-map.md`, wf-doc 문서 유형 `test-map`. 계획 전 생성·구현 중 갱신·grep 대상이라 시간순 서술인 work-log와 분리한다. 표: `\| 변경 예정 파일 \| 관련 테스트 \| 실행 명령 \| 근거 \| 사전 실행 (SHA·결과) \|`. 생성 방법 기본값은 Q-01 |
| DES-03 | 시점별 실행 집합 | Red = 새 테스트 1개 / Green = 새 테스트 + 맵 / Refactor 후·리뷰 후 = 맵(코드 변경 시만) / `completed` 전이 = 의무 목록 / 통합 = 전체 스위트 1회 + 의무 목록 / 재개 = 의무 목록(SHA 상이 시). 플랜 §2.1 표를 그대로 채택하되 **`s1-s3` 보고서의 S2 초안(Green·Refactor에서도 의무 목록 전량)은 시간 증가 원인이 되어 채택하지 않는다** |
| DES-04 | 의무 목록 형식·상태 | work-log `## 회귀 의무 목록` 표: `\| 발행 TASK \| 테스트·명령 \| 보호 스코프 \| 마지막 성공 (일시·SHA) \| 상태 \| 비고 \|`. 상태 어휘 `유지 \| 대체(→DCR/TASK) \| 폐기(이유) \| 보류(결정성 미확인)`. 표 아래에 `마지막 전량 재실행: 일시 — 성공 N / 실패 N / 미수행 N`. 진입 조건은 같은 SHA에서 N회 통과(Q-02) |
| DES-05 | 규칙 배치 | 의미 규칙(귀속·시점·진입·회귀 사건)은 wf-implement 본문 해당 절에 한 문장~한 문단으로. **표**(계층 표·깊이 표·예산 규칙)는 `references/verification-depth.md`로 분리하고 본문에는 트리거 문장만. 이 파일이 wf-implement의 첫 references이며 사이클 3 다이어트의 선행 사례가 된다 |
| DES-06 | 실패 분류 열 | verification 표를 `\| 검증 ID \| 인수 조건 \| 방법·명령 \| 결과 \| 분류 \| 증거 \|`로 확장. `분류`는 결과가 `실패`일 때 필수, 어휘는 §3.4의 4분류 고정. 성공·미수행은 `—` |
| DES-07 | 명령 고정 | 실행 명령은 test-map 행과 의무 목록 행에 실제 실행 형태(환경 활성화·작업 디렉터리·플래그 포함, 예: `.venv\Scripts\python -m pytest tests/test_x.py -q`)로 기록한다. §3.4에 "기록된 형태로 실행하며 다른 형태로 실행했다면 별개의 검증"을 규정. `docs/quality-gates.md`는 사이클 2 |
| DES-08 | 검증 깊이 표 병합 | `verification-depth.md`의 경로별 깊이 표는 `s1-s3` §2.6 초안을 채택하되 행에 "회귀 의무 목록" 항목을 DES-03과 일치시킨다. 예산 신호 규칙(threshold 수신 후 새 전체 검증 금지, `미수행 — 예산 신호 후 인계` 기록)은 같은 파일 |
