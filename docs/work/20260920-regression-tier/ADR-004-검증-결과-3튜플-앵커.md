# ADR-004: 검증 결과의 3튜플 앵커

## 요약

- 결정: 검증 결과의 귀속 단위를 **(테스트 집합, 커밋 SHA, 실행 명령)** 3튜플로 정한다. 세 값이 같고 워킹트리가 clean이면 재실행 대신 인용하고, 하나라도 다르면 별개의 검증으로 취급한다.
- 핵심 이유: 회귀검사의 시간 증가(중복 실행)와 결과 부정합(앵커 없는 기록)이 같은 결함 — 결과가 무엇에 묶여 있는지 불명 — 에서 나온다. 귀속 단위를 고정하면 하나의 규칙이 두 문제를 동시에 푼다.
- 주요 단점: 기록 부담이 는다(행마다 SHA·명령). 인용 규칙이 남용되면 검증 생략의 구실이 된다 — §3.5 리뷰 항목과 사이클 2의 Stop 훅으로 보완.

## 배경

현행 wf-implement §3.4는 "각 인수 조건에 대해 검증 방법, 결과와 증거를 기록한다"고 하고 wf-doc verification 템플릿은 증거 열에 "로그·테스트명·아티팩트"를 예시한다. 어느 쪽도 **어느 커밋에서, 어떤 명령으로** 실행했는지를 요구하지 않는다. 기준선 측정에서 35개 검증 행 중 SHA 기록 실질 0건, 명령 기록 2건이 확인됐다.

이 결함의 결과는 두 갈래다. (1) 같은 검증을 이미 했는지 판정할 근거가 없어 안전하게 다시 돌린다 — TASK당 최대 7~8회 실행. (2) 이전에 성공한 검증이 재실행에서 실패할 때 §3.4의 4분류(이번 변경/기존/환경/원인 미확인)를 적용할 근거가 없다 — "기존 실패"는 마지막 성공 시점을 알아야 판정할 수 있다. LoopsBench(arXiv 2608.00267)는 이를 "루프가 완료 의무를 통보받지 못한다"로, Skills Harmful(2608.11888)은 환경 상태 불일치(ESM)로 각각 관찰했다.

## 영향을 받는 요구사항과 제약

- [FR-01·02·03](./req-design.md#기능-요구사항) — 귀속, 증거 필수 항목, 실패 분류 근거
- [NFR-03](./req-design.md#비기능-요구사항) — 커밋 SHA는 형상관리 전제. 워크플로우가 이미 git을 전제(§2.2 변경 범위, §3.1 미커밋 변경 확인)하므로 새 의존이 아니다
- [NFR-04](./req-design.md#비기능-요구사항) — 기존 기록에 소급 적용하지 않는다

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| A. 현행 유지 — 결과와 자유 형식 증거만 기록 | 변경 없음 | 중복 실행과 부정합의 원인이 그대로. 기준선 측정이 결함을 실증 | — |
| B. 커밋 SHA만 앵커 | 기록 부담 최소, "어느 코드에서"는 해결 | 같은 SHA에서 다른 명령(다른 가상환경·플래그·테스트 부분집합)으로 돌린 결과를 구분 못함 — 환경 불일치(원인 E)와 집합 비결정(원인 D)이 남음 | 낮음 |
| C. 3튜플 — 집합·SHA·명령 (채택) | 중복 판정과 부정합 판정에 필요한 세 축을 전부 고정. 명령 문자열이 환경을 대리하므로 별도 환경 기록 불필요 | 행마다 세 값 기록. 인용 남용 위험 | 낮음 — 열 추가와 규칙 한 문단 |
| D. 실행 로그 전문 첨부 | 재현 정보 완전 | wf-doc "큰 diff나 로그를 붙이지 말고 위치를 연결한다" 원칙 위반, 기록 비대 | 높음 |
| E. 테스트 결과를 외부 도구(pytest cache, CI)에 위임 | 워크플로우 문서 부담 없음 | 하네스 의존(NFR-03 위반), 세션 경계·컴팩션에서 문서가 정본이라는 §7 원칙과 충돌 | 중간 |

## 결정

대안 C를 채택한다. verification 표에 `분류` 열을 추가하고 증거 열에 SHA·명령을 필수로 한다(형식은 wf-doc). wf-implement §3.4에 귀속·인용·별개 판정 규칙을 한 문단으로 두고, 실패 분류의 SHA 근거 규칙을 덧붙인다. 테스트 맵과 회귀 의무 목록의 각 행도 같은 3튜플을 기록한다.

인용 조건은 **세 값 일치 + 워킹트리에 미커밋 변경 없음**이다. 미커밋 변경이 있으면 SHA가 같아도 코드가 다르므로 인용할 수 없다.

## 이유

시간 증가와 부정합이 동일 결함의 두 얼굴이라는 것이 진단의 핵심이다. 귀속 단위가 있으면 "이미 한 검증인가"(→ 인용)와 "이 실패는 무엇 때문인가"(→ 마지막 성공 SHA 이후의 변경)가 같은 데이터로 판정된다. 명령을 튜플에 넣는 이유는 환경 차이를 별도 서술 없이 잡기 위해서다 — 명령이 다르면 환경이 다른 것으로 본다. 이는 이 저장소의 기존 원칙("실행하지 못한 검증은 성공으로 간주하지 않는다", "대화에만 남긴 검증 결과는 세션이 끝나면 추적할 수 없다")을 한 단계 구체화한 것이지 새 철학이 아니다.

## 결과와 감수할 단점

- 검증 표 행마다 SHA·명령을 적어야 한다. 명령은 테스트 맵·의무 목록에서 복사하므로 실질 부담은 SHA 한 값이다.
- 인용 규칙은 검증 생략의 구실이 될 수 있다 → §3.5 자체 리뷰에 "인용한 검증의 SHA가 HEAD와 같고 워킹트리가 clean인가" 항목 추가(RISK-03). 기계 강제는 사이클 2 Stop 훅.
- 기존 완료 기록은 앵커가 없으므로 인용 대상이 아니다. 새 사이클에서 그 테스트를 다시 돌리면 그것이 첫 앵커가 된다.
