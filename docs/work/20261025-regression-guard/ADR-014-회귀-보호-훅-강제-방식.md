## 배경

- 강제할 규칙은 이미 있다(wf-implement 주의 ④, §3.3 진행 중 수정 금지). 위반은 텍스트로만 금지되어 있다.
- 증거: 명세와 모순되는 테스트 앞에서 프런티어 모델 49~54%가 우회, 보호된 평가 경로가 우회 감소의 최대 기여(약 41.5%), 명시적 중단 출구가 우회를 54%→9%로 감소, 자기 보고 F1 13.2%([대조 문서 §2.1](../../research/20261025-aidlc-trends/00_trends_vs_workflow.md#21-최신-증거)).
- 정당한 수정도 있다: 테스트 자체의 오류, DCR로 의미가 바뀐 테스트(`대체`), 재정비 관문의 병합·폐기.
- 훅 능력: PreToolUse는 `allow | deny | ask`를 반환, `deny`는 권한 우회 모드에서도 유지. Stop은 `decision: block`으로 1회 계속시킬 수 있고 `stop_hook_active`로 재진입을 안다.
- 대상 하네스: Claude·Codex 외에 사내 에이전트(SEMCo-Work)에서도 동작해야 한다(사용자, 2026-10-25). 다른 하네스의 확장점은 미확인이고, 게이트 설정 파일의 위치도 하네스마다 다르다.

## 영향을 받는 요구사항과 제약

- C층 NFR-01 fail-open — 기존 3훅은 오류 시 무출력 통과.
- C층 NFR-02 하네스 중립 — 훅은 스킬 규칙의 포인터.
- C층 NFR-03 성능 — PreToolUse는 매 편집마다 실행.
- 셸 편집은 PreToolUse의 Edit/Write 매처에 보이지 않는다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 규칙만 유지(현행) | 변경 0 | 증거상 우회가 흔하고 자기 보고로는 드러나지 않음 |
| B. PreToolUse `deny`만 | 편집 도구 경로를 확실히 차단 | 정당한 수정마다 수동 해제 필요, 셸 편집은 못 봄 |
| **C. PreToolUse `ask` + Stop diff 검사 (채택)** | 정당한 수정은 사람 확인으로 진행, 셸 편집은 종료 시 드러남 | 자동 승인 모드에서 `ask`의 도달 여부 미확인(조건부 `deny`로 보완), 기록 행만 쓰는 우회는 관문 승인에 의존 |
| D. Bash 명령도 PreToolUse에서 파싱 | 셸 편집도 사전 차단 | 명령 파싱은 오탐·미탐이 많고(`sed`, 리다이렉션, 스크립트 실행) 성능 부담. Stop diff가 더 단순하고 확실 |
| F. 종료 판정을 Claude Stop 훅(PS1) 안에 구현(최초 초안) | 의존성 PS 5.1뿐 | 다른 하네스가 재사용 불가, 하네스마다 판정 재구현 |
| E. Stop에서 `유지` 행 재실행 | 실제 통과 확인 | 전량 실행 시점을 3시점으로 제한한 원칙([verification-depth §1](../../../skills/wf-implement/references/verification-depth.md#1-시점별-실행-집합)) 위반, 종료마다 비용 |

## 결정

1. **편집 시점:** PreToolUse(`Edit|Write|MultiEdit|NotebookEdit`) 훅이 대상 경로를 대장 `유지` 행의 `테스트 파일`(및 Q-02 채택 시 설정 파일)과 대조해 일치하면 `permissionDecision: "ask"`와 이유를 반환한다. 입력 `permission_mode`가 권한 자동 승인 계열이고 `ask`가 사람에게 닿지 않는 것이 확인되면 그 모드에서만 `deny`.
2. **종료 시점:** 하네스 중립 B층 스크립트(`regression_guard.py`, Python 표준 라이브러리 + git)가 `유지` 행마다 `git diff --name-only <마지막 성공 SHA>`(커밋 + 워킹트리)로 테스트 파일 변경을 찾고, HEAD 대비 `유지` 행의 축소(격리 전환·삭제·`테스트 파일` 변경)도 찾아, 열린 작업 기록의 `### 테스트 대장 변경`에 그 행 ID가 없으면 위반을 보고한다. Claude Stop 훅은 이 스크립트를 호출해 위반 시 `decision: block`을 1회 반환하는 래퍼다. `stop_hook_active`가 참이면 통과. 테스트는 실행하지 않는다.
3. **실패 정책:** PreToolUse 가드는 **대장이 있는데 읽지 못하면 `ask`**(fail-to-ask). 대장이 없으면 무출력(무관 저장소). Stop 훅은 기존 NFR-01대로 오류 시 통과(fail-open) — 종료를 오류로 막으면 세션이 갇히고, 1차 장치가 이미 있다.
4. **메시지:** 두 훅의 이유 문구는 `messages/*.md`에 두고 스킬 규칙(주의 ④, 충돌 출구 §6, 재정비 관문)을 가리키는 포인터만 담는다.
5. **보호 3층:** ① 공통 핵심 — 대장 `유지` 테스트 파일과 대장 축소, 판정은 하네스 중립 스크립트. ② 어댑터 확장 — 그 하네스의 게이트 설정 파일을 어댑터가 선언(Claude: `settings*.json` 전역·프로젝트). ③ 편집 시점 확인 — ①·②의 대상에 대해 하네스별 훅(매 편집 지연 때문에 어댑터가 같은 대장 판독 규칙으로 직접 구현). 종료 확장점이 없는 하네스는 ①을 완료 보고 전 또는 git pre-commit에서 실행한다. 훅 스크립트 자신은 보호하지 않는다(이 저장소의 상시 개발 대상, git 리뷰로 갈음).

## 이유

- 우회 감소 효과는 "평가 경로 보호"에서 가장 크고, 정당한 수정이 존재하므로 차단보다 사람 개입이 비용 대비 낫다.
- 두 겹은 서로의 구멍을 메운다: 편집 도구 경로는 사전에, 셸 경로는 사후에.
- fail-open은 "주입 포기"가 유일한 실패 결과인 훅을 위한 원칙이었다. 가드의 실패 결과가 "보호 포기"이면 원칙의 전제가 다르다.

## 결과와 감수할 단점

- 의도적 우회를 완전히 막지 못한다 — 에이전트가 대장 변경 기록 행을 써서 Stop을 통과할 수 있다. 대신 변경이 기록되어 완료 보고 관문의 4조건 승인 대상이 된다(조용한 변경 → 공개된 변경).
- C층 훅이 처음으로 권한 결정을 반환한다. 설계 문서의 출력 계약이 넓어진다.
- 테스트 수정이 많은 작업에서는 확인이 잦다. 배치 단위 확인은 레거시 정비 사이클의 과제(D-6).
- 셸로 게이트 설정 파일을 고치는 경로와, 대장 축소를 커밋해 HEAD 비교를 피하는 경로는 막지 못한다. 설정 파일은 저장소 밖이고, 커밋은 사용자 지시로만 수행된다는 실행 승인 규칙에 의존한다.
- Claude 종료 검사가 Python에 의존한다. Python이 없으면 종료 검사만 꺼진다(fail-open).
- 대장 판독기가 둘(PS1·Python)이다. 공유 견본 대장으로 판독 결과 일치를 테스트에 고정한다.
